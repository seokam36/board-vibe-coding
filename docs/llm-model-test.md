# S17-a 로컬 LLM 모델 실측

2026-11-14, 집 PC(RTX 4070 Ti 12GB, RAM 32GB), Ollama 0.40.16. 측정 스크립트는 [llm-bench.mjs](llm-bench.mjs)이고, 실행하려면 Ollama를 켜고 `node docs/llm-bench.mjs`를 친다.
예문은 전부 가짜 중고 글이다. 실제 회원 글은 쓰지 않았다.

## 결론
- **쓸 모델: `qwen3:8b`** (Apache 2.0). 정확도가 가장 높고, 셋 중 **유일하게 도구 호출(tools)을 지원**한다(S17-e에 필요).
- 생각 과정(think)은 끄고 쓴다(`think: false`). 켜면 답 전에 영어로 된 긴 생각이 붙어서 느려진다.
- **서버 시간 제한은 60초로 시작한다.** 모델이 메모리에 올라가 있으면 답이 0.1~3초 걸리고, 올라가 있지 않으면 첫 호출에 모델 올리는 시간 2~3초가 더해진다. 그래픽카드 첫 실행이나 PC를 켠 직후에는 30초 넘게 걸린 적이 있다(gemma3 26초, qwen3 첫 실행 33초). 운영 nginx 기본 대기 시간도 60초다.

## 측정 방법
1. 가짜 중고 글 5개(함정 포함)를 "[지시문] + [게시글] + [질문]" 모양으로 `/api/chat`에 보낸다. RAG를 흉내 낸 것이다.
2. 질문 6개의 답을 정답표와 비교한다(사람이 채점, temperature 0.2).
3. 검색 도구(`search_market_items`: keyword·maxPrice·tradeType)를 주고 질문 2개를 보내, AI가 조건을 맞게 채워 부르는지 본다.
4. 속도: 모델을 내린 뒤 첫 질문(올리는 시간 포함)과 이후 질문, 초당 토큰(tok/s). qwen3를 CPU로만 돌린 값과도 비교한다.

## 트러블슈팅: 그래픽카드가 있는데 CPU로 돌았다
- 증상: `ollama ps`가 `100% CPU`이고, 그래픽카드 메모리 사용량이 0이었다. 오류 없이 조용히 CPU로 넘어갔다.
- 기록: `%LOCALAPPDATA%\Ollama\server.log`에 `llama-server --list-devices failed: exit status 0xc0000005`가 남아 있었다. CUDA 12, CUDA 13, ROCm, Vulkan 모두 같은 오류였다.
- 재현: `GGML_BACKEND_PATH=...\cuda_v12\ggml-cuda.dll`로 `llama-server.exe --list-devices`를 직접 실행하니 같은 오류(-1073741819)가 났다. CPU 부품은 정상이었다.
- 원인: `C:\Windows\System32\msvcp140.dll`이 **14.24**(오래된 Visual C++ 런타임)였다. Ollama의 GPU 부품은 14.44로 만들어져 있다. 오래된 런타임을 먼저 불러와서 충돌한 것으로 본다(증상이 비슷한 이슈: ollama/ollama#16957).
- 해결: Microsoft Visual C++ 재배포 패키지(x64) 최신판을 설치(14.44)하고 Ollama를 다시 켰다. 그 뒤 `RTX 4070 Ti` 인식, `offloaded 37/37 layers to GPU`, `100% GPU`가 확인됐다. 그래픽카드 첫 실행만 33초로 느렸고, 그다음부터는 정상 속도였다.
- 노트북이나 다른 PC에서도 Ollama가 CPU로 돌면 System32의 msvcp140.dll 버전부터 확인한다.

## 도구 호출 재실측 (S17-e1)

2026-11-15, 같은 집 PC, `qwen3:8b`만. 스크립트는 [llm-bench-e1.mjs](llm-bench-e1.mjs), 실행은 `node docs/llm-bench-e1.mjs`(약 1분, Ollama를 켜 둔다). 원문 결과는 [bench-e1-result.json](bench-e1-result.json)(25KB)에 있다.
S17-a 실측은 도구의 tradeType 값을 `SALE`·`SHARE`로 잘못 썼다(실제는 `SALE`·`FREE`). 그래서 다시 쟀다. 예문은 전부 가짜 글이다.

### 결론 (쉬운 말)
- **판정: C안(구조화 출력)으로 간다.** 도구 호출은 24번 중 **11번** 맞았다(합격선 22번). 맞는 걸로 쳐 주는 너그러운 채점으로도 14번이라 합격선에 한참 모자란다.
- 구조화 출력(AI에게 "이 모양의 JSON으로만 답해"라고 시키는 방법)은 24번 중 **15번**(너그럽게 21번) 맞았다. JSON이 깨진 적은 **0번**이라 `think: false`에서도 모양은 잘 지켜진다. 도구 호출은 "도구를 불러야 할 때 안 부르고" 마음대로 답한 경우가 7번(자전거 1, 밥솥 3, 노트북 3) 있었고, 그중 5번은 없는 글 번호를 지어냈는데, 구조화 출력은 항상 JSON이 나와서 이런 일이 없었다.
- 둘 다 같은 약점이 있다. **"3만 원 이하 자전거"처럼 판매·나눔을 말하지 않았는데 AI가 마음대로 `tradeType: SALE`을 넣었다**(도구 3번, 구조화 3번 전부). 그러면 무료 나눔 자전거가 검색에서 빠진다. 서버에서 AI가 준 tradeType을 그대로 믿지 말고(예: 질문에 "나눔·무료"가 있을 때만 쓰기) 걸러야 한다.
- **글은 5건씩 주는 걸 추천**한다. 정답 12/15(5건) 대 6/15(10건). 10건을 주면 "자전거 있어?"에서 나눔 글을 3번 다 빠뜨렸고, "10만 원 넘는 자전거"에서도 틀렸다. 시간은 둘 다 평균 0.4초로 차이가 없었다.
- **"모두 빠짐없이 검토해서 답해" 한 줄은 효과가 있었다.** 10건에서 "자전거 있어?" 답에 나눔 글이 지시문 없을 때 0/3, 있을 때 3/3 들어갔다(판매 글은 둘 다 3/3). 지시문에 넣을 만하다.
- **시간은 60초 안에 충분히 든다.** 2턴 왕복(도구 호출 -> 결과 돌려주기 -> 답)이 데워진 상태에서 약 2초, 모델을 내린 뒤 첫 호출(콜드)에서 5.0초였다. 가짜 검색 결과만 근거로 답했고 지어낸 건 없었다. 다만 예외가 있었다: 아래 "예상 밖 관찰"의 무한 반복.

### 측정 방법 (서버와 같게)
- 서버(`OllamaLlmClient`)처럼 **`think: false`, temperature 등 옵션은 지정하지 않았다**(모델 기본값). S17-a 스크립트의 temperature 0.2는 서버와 달라서 이번엔 뺐다. 그래서 같은 질문도 실행마다 조금씩 달라질 수 있다(아래 "예상 밖 관찰").
- 도구: `search_market_items`(keyword 필수, maxPrice·tradeType 선택, tradeType은 `SALE`·`FREE`). 시스템 지시문은 `ChatService.SYSTEM_PROMPT`를 도구 방식에 맞게 고친 것(스크립트의 `TOOL_SYSTEM`). 글 목록 모양과 RAG 지시문(`RAG_SYSTEM`)은 `ChatService`와 같다.
- 모든 호출에 65초 제한을 걸었다(서버 제한 60초와 비슷하게). 넘으면 실패로 기록한다.
- **채점**:
  - 도구 호출 "엄격": 도구를 불렀고, keyword에 핵심 단어가 들어 있고(영어 질문은 `rice`/`cooker`/`밥솥` 중 하나), maxPrice가 기대 숫자와 같고(없어야 하면 없음), tradeType이 기대와 같아야(없어야 하면 없음) O. 안 불러야 하는 "안녕"은 안 부르면 O.
  - "너그러움": 질문에 "파는/팔아"가 있는 2개 질문(냉장고, 밥솥)은 `SALE`을 넣어도 O로 쳐 준다. 그 밖의 채점은 같다.
  - 기대값: "자전거 있어?"=keyword만 / "3만 원 이하 자전거 있어?"=자전거+30000 / "무료 나눔 전공책 있어?"=전공책+FREE / "Is there a rice cooker under 30000 won?"=rice cooker+30000 / "5만원 이하 냉장고 파는 사람"=냉장고+50000 / "밥솥 팔아?"=밥솥 / "노트북 나눔해?"=노트북+FREE.
  - 글 5건/10건: 준 글 안에서 질문에 꼭 들어가야 할 글 번호를 다 말하고, 들어가면 안 되는 글 번호를 말하지 않고, 준 목록에 없는 번호를 지어내지 않으면 O.

### 예상 밖 관찰
- **maxPrice는 항상 숫자**(`30000`)로 왔다(9번 모두 number). `arguments`도 항상 문자열이 아닌 **객체**였다(도구를 부른 14번 모두 object). 그래도 서버는 문자열 `"30000"`이 와도 받도록 만드는 게 안전하다. 키 순서는 매번 달랐다(`tradeType`이 맨 앞에 오기도 함).
- **도구를 안 부르고 지어내기**: "노트북 나눔해?"는 도구를 3번 다 안 부르고 `#1034567890: 노트북을 무료(나눔) 중이에요...`처럼 **없는 글 번호를 지어냈다**. "밥솥 팔아?"도 3번 다 안 불렀다. 도구 방식은 AI가 부를지 말지를 마음대로 정해서 이런 일이 생긴다. 도구를 안 불렀는데 글 번호가 보이면 서버가 버려야 한다.
- **끝없이 반복해서 멈춘 적 있음**: 같은 질문 "노트북 나눔해?"를 이 표를 얻기 전 시험 실행 2번에서 1번은 **290초 걸린 뒤 `prediction aborted, token repeat limit reached`**, 다른 1번은 Node의 기본 대기 시간(5분) 초과로 스크립트가 죽었다. 이 때문에 스크립트에 65초 제한을 넣었다. 표를 얻은 마지막 실행에서는 일어나지 않았다(0.5~0.9초에 지어낸 답). 서버의 60초 제한이 꼭 필요하다는 근거다.
- 스크립트를 3번 돌렸다(처음 것은 도구 호출 엄격 12/24, 두 번째는 위의 5분 대기로 중간에 죽음, 마지막이 11/24). 어느 쪽이든 합격선 22에는 한참 못 미친다. 이 문서의 표는 마지막 실행 값이다.
- 같은 질문의 3번이 거의 똑같이 나온 칸이 많다. 특히 "3만 원 이하 자전거" 3번 다 SALE을 넣은 것은 우연이 아니라 모델의 습관이다.
- 5건·10건 모두 "3만 원 이하 자전거 있어?"에서 0/3이었다. 답이 `#201, #205, #209, #210`처럼 번호만 늘어놓는 짧은 목록이라, 35,000원짜리(#201) 같은 3만 원 넘는 글을 섞고 예약중 #204를 빠뜨렸다. S17-a에서도 확인한 대로 **가격 조건은 AI가 아니라 서버 검색이 걸러야 한다**.
