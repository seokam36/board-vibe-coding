# Notion 학습 기록 가이드

메인 대화가 단계가 끝날 때마다 Notion에 학습 기록을 남긴다. 대화 내용(사용자 질문, 트러블슈팅)이 필요하므로 서브에이전트에 맡기지 않는다.

## 위치
- 상위 페이지 "바이브 코딩": https://app.notion.com/p/40b4115beefb815dbc1dd0033d060d93
- 그 안의 "학습 리뷰" 데이터베이스: collection://1121b459-f685-4a8c-9525-f0efade5bbc5

## 구조: 큰 기능(파트)마다 카드 하나
- 카드는 S0, S1, S2, ... 처럼 큰 기능마다 하나. 단계(S2-a 등)마다 카드를 만들지 않는다.
- 카드 속성: 제목, 번호(파트 순서), 단계(예: "S3 (S3-a ~ ...)"), 태그, 한 줄 요약. 날짜는 쓰지 않는다.
- 카드 본문: 📌 파트 요약(회색 콜아웃) → 🗺 단계 한눈에 보기(단계 | 한 줄 요약 표) → 📂 단계별 기록
- 각 단계 기록은 카드 안의 **하위 페이지**로 만든다.

## 단계가 끝나면
1. 해당 파트 카드 안에 단계 하위 페이지를 만든다. 새 파트면 카드부터 만든다.
2. 카드의 "단계 한눈에 보기" 표에 그 단계 줄을 추가하고, 필요하면 태그·한 줄 요약을 넓힌다.
3. 상위 페이지 "진행 현황"은 큰 파트만 한 줄씩 적는다(괄호에 한 것/남은 것). 단계는 적지 않는다. 파트 안의 단계가 모두 끝나야 체크한다.
4. 아키텍처가 바뀌면 상위 페이지의 mermaid 다이어그램도 고친다.

## 단계 하위 페이지 본문 (순서대로)
1. 📌 한 줄 요약 (회색 콜아웃)
2. 목차
3. 🧠 이번에 배운 개념 — 쉬운 비유, 표
4. ❓ 내가 헷갈렸던 질문과 답 — 사용자가 실제로 한 질문마다 토글 하나
5. ⚙️ 서버 안에서 일어나는 일 — 이 단계의 대표 요청 1~2개가 서버 안에서 지나가는 길(필터 → 컨트롤러 → 서비스 → 리포지토리 → DB/Redis)을 **ASCII 흐름도(코드 블록)**로 먼저 그리고, 그 아래에 **실제 코드 조각(5~20줄, 파일 이름 주석 포함)**을 코드 블록으로 붙인 뒤 "코드 | 해설" 표로 한 줄씩 풀어 쓴다(2026-11-07 사용자 요청: 파일 이름만 나열하지 말고 코드를 붙여서). 코드 블록 첫 줄에 `// 클래스: CommentService.create() (comment/service/CommentService.java)`처럼 클래스·메서드 이름 주석을 달고, 소제목에도 클래스명을 `코드` 서식으로 쓴다. 흐름 섹션 머리에는 "관련 클래스: A → B → C" 한 줄, 해설 표의 코드 칸에도 클래스명을 앞에 붙인다(2026-11-07 사용자 요청: 어느 클래스 코드인지 식별이 안 됨). 소제목에 `Comment.java`를 그냥 쓰면 Notion이 웹 주소로 자동 링크하니 꼭 `코드` 서식으로. 왜 그 순서인지(예: 404를 403보다 먼저 보는 이유)도 한 줄. 프론트 단계는 "브라우저가 서버에 무엇을 보내고 서버가 어떻게 답하는지" 위주로 쓴다. 전체 흐름 설명 페이지(Artifact "로그인 놀이공원")가 있으면 링크하고, 새 장면이 생기면 그 페이지도 갱신한다
6. 🤔 왜 이 기술을 썼나 — 선택 | 대안 | 고른 이유 표 + 면접 답변 한 문단(콜아웃). 면접에서 중요해서 필수
7. 🛠 프로젝트에 이렇게 적용했다 — 결정 | 이유 표
8. 🔗 다음에 볼 것

흐름을 설명하는 섹션(⚙️ 서버 안에서 일어나는 일, 🔄 흐름)에는 흐름도를 하나 이상 넣는다(2026-11-05 사용자 요청: 눈으로 보여야 이해된다). 백엔드 로직 흐름(요청이 필터 → 컨트롤러 → 서비스 → 리포지토리 → DB/Redis로 지나가는 길, 서비스 안의 검사 순서와 401/403/404/409 같은 갈림길)도 포함한다. **흐름도는 mermaid가 아니라 ASCII 코드 블록**으로 그린다(2026-11-07 사용자 요청: mermaid flowchart TD의 마름모 분기는 세로로 너무 커진다). 실패 갈림길은 마름모 대신 `──틀림→ 400`처럼 간선 옆에 짧게. 예:

```
POST /posts/7/comments
   ├─ Security: CSRF 403 → 로그인 401
   ├─ Service: 회원? 401 → 글? 404
   ▼
201 {…}
```

표 구조(erDiagram)처럼 작은 그림만 mermaid를 써도 된다. mermaid를 쓸 땐 `flowchart LR` + 노드 6개 이하.

백엔드가 아닌 단계(배포·CI·인프라·워크플로·셸 스크립트, 프론트)는 워크플로 흐름 위주로 쓴다(2026-11-05 사용자 요청: 백엔드 아닌 부분은 흐름만 알면 됨). 📌 요약 → 🔄 흐름(버튼을 누르면 어떤 순서로 무엇이 일어나는지, 실패하면 어떻게 되는지) → ❓ 질문(있을 때만) → 🔗 다음에 볼 것만 둔다. 스크립트 옵션·인용·권한 같은 세부, 기술 선택 표, 면접 답변은 넣지 않는다.

트러블슈팅 콜아웃과 예상 질문 섹션은 쓰지 않는다(2026-11-04 사용자 요청: 코드를 아직 몰라서 읽어도 이해가 안 됨). 코드 설명은 ⚙️ 섹션에 쉬운 말로만 쓴다.

## 주의
- 셸 명령어는 넣지 않는다. 이모지·색은 최소로, 짧게 쓴다.
- 서버 IP, 계정 ID, DB 사용자명·비밀번호는 절대 쓰지 않는다.
- 이 파트 묶음 방식은 Notion에만 적용한다. backlog·CLAUDE.md·에이전트 구조는 바꾸지 않는다.
