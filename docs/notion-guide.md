# Notion 학습 기록 가이드

메인 대화가 단계가 끝날 때마다 Notion에 학습 기록을 남긴다. 대화 내용(사용자 질문, 트러블슈팅)이 필요하므로 서브에이전트에 맡기지 않는다.

## 위치
- 상위 페이지 "바이브 코딩": https://app.notion.com/p/40b4115beefb815dbc1dd0033d060d93
- 그 안의 "학습 리뷰" 데이터베이스: collection://1121b459-f685-4a8c-9525-f0efade5bbc5

## 구조: 큰 기능(파트)마다 카드 하나
- 카드는 S0, S1, S2, ... 처럼 큰 기능마다 하나. 단계(S2-a 등)마다 카드를 만들지 않는다.
- 카드 속성: 제목, 번호(파트 순서), 단계(예: "S3 (S3-a ~ ...)"), 태그, 한 줄 요약. 날짜는 쓰지 않는다.
- 카드 본문: 📌 파트 요약(회색 콜아웃) → 🗺 단계 한눈에 보기(단계 | 한 줄 요약 표) → 📂 단계별 기록
- 각 단계 기록은 카드 안의 **하위 페이지**로 만든다.

## 단계가 끝나면
1. 해당 파트 카드 안에 단계 하위 페이지를 만든다. 새 파트면 카드부터 만든다.
2. 카드의 "단계 한눈에 보기" 표에 그 단계 줄을 추가하고, 필요하면 태그·한 줄 요약을 넓힌다.
3. 상위 페이지 "진행 현황"은 큰 파트만 한 줄씩 적는다(괄호에 한 것/남은 것). 단계는 적지 않는다. 파트 안의 단계가 모두 끝나야 체크한다.
4. 아키텍처가 바뀌면 상위 페이지의 mermaid 다이어그램도 고친다.

## 큰 기능(S번호)이 끝나면: 🧭 파트 전체 정리
단계를 지나면서 설계가 여러 번 바뀌기 때문에(예: S17은 도구 호출 → 양식 4칸 → 3칸 → 2칸), 단계 페이지만 읽으면 최종 모습이 안 보인다. 그래서 파트가 끝나면(배포 확인까지) 카드 본문의 "🗺 단계 한눈에 보기" 아래에 **🧭 파트 전체 정리** 섹션을 한 번 만든다(2026-11-15 사용자 요청, 예시는 S17 카드).

1. 메인 대화가 끝난 파트의 변경 전체를 review 에이전트에 넘겨 파트 전체 코드 리뷰를 받고, 실제 코드를 읽어 아래를 쓴다. 채팅에도 그림으로 같이 보여 준다.
2. 섹션 내용 (순서대로, 해당 없는 건 뺀다)
   - **처음 계획 → 최종 모습**: 단계마다 무엇이 왜 바뀌었는지 ASCII 흐름도(단계 이름 · 문제 · 바꾼 것, 실측 숫자가 있으면 같이) + 교훈 한두 줄
   - **최종 흐름 (뼈대)**: 지금 코드 기준 대표 메서드를 10~20줄로 줄인 코드(클래스·메서드 이름 주석)
   - **검사·안전장치 순서**: 요청이 지나가는 순서와 갈림길(401/403/400/429/503/504 등)을 ASCII로
   - **클래스 표**: 클래스 | 하는 일
   - **파트 전체 코드 리뷰**: 필수 / 권장 / 나중 개수 + "구분 | 내용" 표(잘된 점, 권장, 나중). 리뷰 수정은 사용자 승인 뒤에만 한다
3. 이미 쓴 단계 페이지는 고치지 않는다(그때의 기록). 최종 모습은 이 섹션에만 쓴다.
4. 파트가 끝난 뒤 정리 단계(예: 리뷰 권장 반영)가 생기면 이 섹션의 리뷰 표에 "반영함" 한 줄을 덧붙인다.

## 단계 하위 페이지 본문 (순서대로)
1. 📌 한 줄 요약 (회색 콜아웃)
2. 목차
3. 🧠 이번에 배운 개념 — 쉬운 비유, 표
4. ❓ 내가 헷갈렸던 질문과 답 — 사용자가 실제로 한 질문마다 토글 하나
5. ⚙️ 서버 안에서 일어나는 일 — 이 단계의 대표 요청 1~2개가 서버 안에서 지나가는 길(필터 → 컨트롤러 → 서비스 → 리포지토리 → DB/Redis)을 **ASCII 흐름도(코드 블록)**로 먼저 그리고, 그 아래에 **실제 코드 조각(5~20줄, 파일 이름 주석 포함)**을 코드 블록으로 붙인 뒤 "코드 | 해설" 표로 한 줄씩 풀어 쓴다(2026-11-07 사용자 요청: 파일 이름만 나열하지 말고 코드를 붙여서). 코드 블록 첫 줄에 `// 클래스: CommentService.create() (comment/service/CommentService.java)`처럼 클래스·메서드 이름 주석을 달고, 소제목에도 클래스명을 `코드` 서식으로 쓴다. 흐름 섹션 머리에는 "관련 클래스: A → B → C" 한 줄, 해설 표의 코드 칸에도 클래스명을 앞에 붙인다(2026-11-07 사용자 요청: 어느 클래스 코드인지 식별이 안 됨). 흐름 섹션 머리에는 "📦 = 라이브러리(Spring·Java 등)가 준 것" 안내와 "이름 | 누가 만듦 | 하는 일" 표를 두고, 코드|해설 표에서도 직접 만든 게 아닌 클래스·메서드에는 📦를 붙인다(2026-11-15 사용자 요청: 어디까지가 우리 코드인지 구분이 안 됨). 소제목에 `Comment.java`를 그냥 쓰면 Notion이 웹 주소로 자동 링크하니 꼭 `코드` 서식으로. 왜 그 순서인지(예: 404를 403보다 먼저 보는 이유)도 한 줄. (프론트만 바꾸는 단계는 이 틀 대신 아래 "프론트 단계 페이지 틀".) 전체 흐름 설명 페이지(Artifact "로그인 놀이공원")가 있으면 링크하고, 새 장면이 생기면 그 페이지도 갱신한다
6. 🤔 왜 이 기술을 썼나 — 선택 | 대안 | 고른 이유 표 + 면접 답변 한 문단(콜아웃). 면접에서 중요해서 필수
7. 🛠 프로젝트에 이렇게 적용했다 — 결정 | 이유 표
8. 🔗 다음에 볼 것

흐름을 설명하는 섹션(⚙️ 서버 안에서 일어나는 일, 🔄 흐름)에는 흐름도를 하나 이상 넣는다(2026-11-05 사용자 요청: 눈으로 보여야 이해된다). 백엔드 로직 흐름(요청이 필터 → 컨트롤러 → 서비스 → 리포지토리 → DB/Redis로 지나가는 길, 서비스 안의 검사 순서와 401/403/404/409 같은 갈림길)도 포함한다. **흐름도는 mermaid가 아니라 ASCII 코드 블록**으로 그린다(2026-11-07 사용자 요청: mermaid flowchart TD의 마름모 분기는 세로로 너무 커진다). 실패 갈림길은 마름모 대신 `──틀림→ 400`처럼 간선 옆에 짧게. 예:

```
POST /posts/7/comments
   ├─ Security: CSRF 403 → 로그인 401
   ├─ Service: 회원? 401 → 글? 404
   ▼
201 {…}
```

표 구조(erDiagram)처럼 작은 그림만 mermaid를 써도 된다. mermaid를 쓸 땐 `flowchart LR` + 노드 6개 이하.

## 단계 종류별로 쓰는 법
- **백엔드**: 위 "단계 하위 페이지 본문"대로 코드 위주(⚙️ 흐름도 + 실제 코드 + 코드|해설 표 + 📦 표시).
- **운영**(배포·서버 설정·도메인·DNS·인증서·CI·워크플로·셸 스크립트): 코드보다 **무엇이 어떻게 바뀌었는지** 운영 위주로 쓴다(2026-11-19 사용자 요청, 예시는 S22 카드). 아래 "운영 단계 페이지 틀".
- **프론트**만 바꾸는 단계: **무엇을 작업했는지만** 짧은 단계 페이지로 남긴다(2026-11-20 사용자 요청으로 바뀜. 전에는 안 썼음: 2026-11-08). 아래 "프론트 단계 페이지 틀". 백엔드·운영이 섞인 단계는 그쪽 방식으로 쓴다. 2026-11-08 이전의 화면 단계(UI1~UI3 등)는 소급해서 쓰지 않는다.

## 프론트 단계 페이지 틀 (순서대로, 해당 없는 건 뺀다)
백엔드 페이지보다 가볍게, "무엇을 작업했나"가 한눈에 보이게 쓴다. 기술 선택 표·면접 답변은 넣지 않는다.
1. 📌 한 줄 요약 (회색 콜아웃) — 무엇을, 왜 바꿨는지 + 실기기·브라우저에서 확인했는지
2. 🔄 무엇이 바뀌었나 — 전/후 표(| | 전 | 후 |: 사용자가 보는 동작 위주. 예: "하이코리아 누르면 → 반응 없음 / 폰 브라우저가 열림")
3. 🛠 작업한 것 — "파일 | 한 일" 표(새 파일·바꾼 파일, 파일 이름은 `코드` 서식) + 추가한 패키지 | 이유
4. 🔧 핵심 코드 — 대표 코드 1~2개(5~20줄, 첫 줄에 파일 이름 주석) + "코드 | 해설" 표, 패키지가 준 것은 📦
5. 🗺 흐름 — 버튼을 누르면 어떤 순서로 무엇이 일어나는지 ASCII 한 개(```text)
6. ❓ 내가 헷갈렸던 질문과 답 — 실제 질문이 있을 때만, 질문마다 토글 하나
7. 🔗 다음에 볼 것 — 남은 확인, 다음 단계

## 운영 단계 페이지 틀 (순서대로, 해당 없는 건 뺀다)
1. 📌 한 줄 요약 (회색 콜아웃) — 무엇을, 왜 바꿨는지 + 운영에 실제로 반영됐는지
2. 🔄 무엇이 어떻게 바뀌었나 — **전/후 비교 표**(| | 전 | 후 |: 주소, 열린 문, 방화벽, 비밀 값, 비용 등)
3. 🗺 구성 그림 — 손님 → DNS → nginx → 앱처럼 이어지는 모습(ASCII 코드 블록)
4. 🔄 일어나는 순서 — 서버를 켤 때·배포할 때·전환할 때 차례로 무슨 일이 생기는지, 실패하면 어떻게 되는지(ASCII, `──실패→` 식 갈림길)
5. 👤 누가 어디서 — 콘솔(AWS·Cloudflare 등) / 서버 / 내 PC / GitHub / 에이전트 중 누가 무엇을 했는지 표
6. 💰 비용·비밀 값 — 돈이 드는 것, 비밀 값을 어디에 두는지, 새면 어떻게 하는지
7. 🚑 문제가 생기면 — "증상 | 먼저 볼 곳" 표 + 되돌리는 방법(자세한 절차는 저장소 docs/deploy.md 이름만)
8. ❓ 내가 헷갈렸던 질문과 답 — 실제 질문마다 토글 하나
9. 🔗 다음에 볼 것 — 남은 확인, 다음 단계

넣지 않는 것: 셸 명령어·스크립트 옵션 같은 세부(그건 docs/deploy.md에), 서버 IP·계정 ID·비밀 값, 기술 선택 표와 면접 답변(백엔드 페이지에만). 설정 파일은 꼭 필요한 몇 줄만, 한 줄 해설을 붙인다(예: `SERVER_FORWARD_HEADERS_STRATEGY: native` ← Spring이 nginx의 https 쪽지를 믿게).

운영 파트가 끝나면 🧭 파트 전체 정리도 위 2~7번을 **파트 전체 기준으로** 모으고, "처음 계획 → 최종 모습"(중간에 바뀐 결정, 예: 고정 IP → 켤 때 DNS 자동 고침)과 단계마다 받은 리뷰 요약(단계 | 필수 | 권장 | 대표 내용)을 넣는다. 파트 전체 코드 리뷰를 새로 돌리는 대신 단계 리뷰 요약으로 대신할 수 있다.

트러블슈팅 콜아웃과 예상 질문 섹션은 쓰지 않는다(2026-11-04 사용자 요청: 코드를 아직 몰라서 읽어도 이해가 안 됨). 코드 설명은 ⚙️ 섹션에 쉬운 말로만 쓴다.

## 주의
- 셸 명령어는 넣지 않는다. 이모지·색은 최소로, 짧게 쓴다.
- 서버 IP, 계정 ID, DB 사용자명·비밀번호는 절대 쓰지 않는다.
- 이 파트 묶음 방식은 Notion에만 적용한다. backlog·CLAUDE.md·에이전트 구조는 바꾸지 않는다.
