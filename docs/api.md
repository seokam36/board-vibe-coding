# API 명세

게시판 API 목록. 새 API를 만들거나 바꾸면 이 문서에 이어서 적는다.
에러 응답 본문은 Spring 기본 형식을 쓰고, 상태코드가 중요하다.
브라우저(프론트엔드) 허용 주소는 환경변수 `CORS_ALLOWED_ORIGINS`로 설정한다(기본값 `http://localhost:5173`, 쉼표로 여러 개).
허용되지 않은 주소에서 브라우저로 요청하면 403이 반환된다 (curl 등 브라우저가 아닌 요청은 CORS 대상이 아님).

배포 환경(EC2)에서는 nginx를 거치므로 API가 `/api` 아래에 있다 (예: `/api/posts`, `/api/posts/1`). nginx가 `/api`를 떼고 백엔드에 전달하므로 이 문서의 URL 자체는 그대로다.
헬스체크는 `/actuator/health` 그대로 쓴다 (`/api` 없음). 로컬 브라우저도 Vite 프록시 `/api`를 쓴다(`refresh_token` 쿠키 Path=`/api/auth`가 붙으려면 필요). curl 등은 `http://localhost:8080`에 직접 요청해도 된다.
글 작성 응답의 `Location` 헤더는 백엔드 기준(`/posts/{id}`)이며 nginx가 바꾸지 않는다. 배포 환경에서 API로 따라가려면 앞에 `/api`를 붙인다 (현재 프론트는 `Location`을 사용하지 않음).

## CSRF 보호 (모든 POST/PUT/DELETE 공통)

S4-a부터 Spring Security가 켜져 있어서, **POST/PUT/DELETE는 `X-XSRF-TOKEN` 헤더가 없으면 `403`** 이다 (GET은 필요 없음).
1. 앱 시작 시 `GET /csrf`를 한 번 호출하면 `XSRF-TOKEN` 쿠키가 설정된다.
2. 이후 POST/PUT/DELETE마다 그 쿠키 값을 `X-XSRF-TOKEN` 헤더에 실어 보낸다 (axios는 같은 주소 요청에서 자동으로 해 준다).

서버는 세션(`JSESSIONID`)을 만들지 않는다. 로그인이 필요한 경로는 인증 없이 부르면 `401`이다 (허용 목록 밖의 없는 경로도 404가 아니라 401).
글 API는 **목록·단건 조회(GET)만 로그인 없이** 쓸 수 있다. 작성·수정·삭제(POST/PUT/DELETE)는 로그인(`access_token` 쿠키)이 필요하고, 토큰이 없거나 만료·변조되면 `401`이다.
조회(GET)는 만료되거나 변조된 `access_token` 쿠키가 붙어 와도 정상(200)이다.
수정·삭제는 **본인이 쓴 글만** 가능하다. 남의 글, 그리고 작성자가 없는 글(S4-d 이전에 쓴 글)은 `403`이다.
쓰기 요청은 아래 순서로 검사하고 먼저 걸리는 오류를 돌려준다: CSRF 403 → 로그인 안 됨 401 → 본문 검증 400 → 없는 글 404 → 본인 글 아님 403.

## 게시글 (Post)

| 기능 | 메서드 | URL | 성공 | 실패 |
|------|--------|-----|------|------|
| 작성 | POST | `/posts` | 201 | 400, 401, 403 |
| 단건 조회 | GET | `/posts/{id}` | 200 | 404, 400 |
| 목록 조회 | GET | `/posts` | 200 | - |
| 수정 | PUT | `/posts/{id}` | 200 | 400, 401, 403, 404 |
| 삭제 | DELETE | `/posts/{id}` | 204 | 400, 401, 403, 404 |

### 응답 필드

| 필드 | 타입 | 설명 |
|------|------|------|
| id | 숫자 | 게시글 번호 |
| title | 문자열 | 제목 |
| content | 문자열 | 본문 |
| createdAt | 문자열 | 작성 시각 (예: `2026-11-01T01:30:00.123456Z`) |
| author | 객체 또는 null | 글쓴이 `{ "id": 숫자, "nickname": 문자열 }`. 로그인 아이디(username)는 숨긴다. 작성자가 없는 글(S4-d 이전에 쓴 글)은 `null` |

시간대: UTC(Z). 소수점 자릿수는 가변(최대 6자리). 화면에 보여줄 때 한국 시간으로 변환한다.

### 1. 게시글 작성 `POST /posts`

로그인 필요. 글쓴이는 로그인한 사용자로 정해지며, 요청 본문에 `author`·`authorId` 같은 값을 보내도 무시한다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 공백만 있으면 안 됨, 최대 100자, 제어 문자(NUL) 불가 |
| content | O | 공백만 있으면 안 됨, 길이 제한 없음, 제어 문자(NUL) 불가 |

요청 예시

```json
{
  "title": "첫 글",
  "content": "안녕하세요"
}
```

성공 응답 `201 Created` (헤더 `Location: /posts/1`)

```json
{
  "id": 1,
  "title": "첫 글",
  "content": "안녕하세요",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  }
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | title/content가 비었거나 공백만 있음, title이 100자 초과, NUL 문자 포함, JSON 형식이 잘못됨 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효하지만 그 사용자가 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 2. 게시글 단건 조회 `GET /posts/{id}`

요청 예시: `GET /posts/1`

성공 응답 `200 OK`

```json
{
  "id": 1,
  "title": "첫 글",
  "content": "안녕하세요",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  }
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 404 | 없는 id (예: `/posts/999`) |
| 400 | id가 숫자가 아님 (예: `/posts/abc`) |

### 3. 게시글 목록 조회 `GET /posts`

최신순(id 내림차순)으로 전체를 돌려준다. 페이징 없음. 글이 없으면 빈 배열 `[]`. 로그인 없이 호출 가능. (아래 예시의 두 번째 글처럼 작성자가 없는 옛 글은 `author`가 `null`)

성공 응답 `200 OK`

```json
[
  {
    "id": 2,
    "title": "두 번째 글",
    "content": "내용",
    "createdAt": "2026-11-01T01:35:00Z",
    "author": {
      "id": 1,
      "nickname": "길동이"
    }
  },
  {
    "id": 1,
    "title": "첫 글",
    "content": "안녕하세요",
    "createdAt": "2026-11-01T01:30:00.123456Z",
    "author": null
  }
]
```

### 4. 게시글 수정 `PUT /posts/{id}`

로그인 필요, 본인이 쓴 글만 가능. 제목과 본문을 모두 새 값으로 바꾼다 (일부만 바꾸는 PATCH는 없음). `createdAt`은 바뀌지 않는다.

요청 본문 (작성과 같은 규칙, 둘 다 필수)

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 공백만 있으면 안 됨, 최대 100자, 제어 문자(NUL) 불가 |
| content | O | 공백만 있으면 안 됨, 길이 제한 없음, 제어 문자(NUL) 불가 |

요청 예시: `PUT /posts/1`

```json
{
  "title": "수정한 제목",
  "content": "수정한 내용"
}
```

성공 응답 `200 OK`

```json
{
  "id": 1,
  "title": "수정한 제목",
  "content": "수정한 내용",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  }
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | title/content가 비었거나 공백만 있음, title이 100자 초과, NUL 문자 포함, JSON 형식이 잘못됨, id가 숫자가 아님 (남의 글이어도 본문이 잘못되면 403이 아니라 400) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id·숫자 아닌 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인이 쓴 글이 아님 (작성자가 없는 글 포함) |
| 404 | 없는 id (예: `/posts/999`) |

검사 순서: 400(본문) → 404 → 403. 즉 본문이 올바르고 글이 있어야 본인 글인지 확인한다.

### 5. 게시글 삭제 `DELETE /posts/{id}`

로그인 필요, 본인이 쓴 글만 가능. DB에서 글을 완전히 지운다 (복구 불가).

요청 예시: `DELETE /posts/1`

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 (예: `/posts/abc`) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id·숫자 아닌 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인이 쓴 글이 아님 (작성자가 없는 글 포함) |
| 404 | 없는 id (이미 삭제된 id 포함) |

## CSRF 토큰 (Csrf)

### 6. CSRF 쿠키 발급 `GET /csrf`

`XSRF-TOKEN` 쿠키를 설정한다. 로그인 없이 호출 가능.

성공 응답 `200 OK` (헤더 `Set-Cookie: XSRF-TOKEN=...; Path=/`)

```json
{
  "headerName": "X-XSRF-TOKEN"
}
```

`headerName`은 토큰을 실어 보낼 헤더 이름이다. 헤더에는 **쿠키에 설정된 값 그대로**를 쓴다.

## 회원 (Auth)

### 7. 회원가입 `POST /auth/signup`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다. 가입만 하고 로그인은 되지 않는다(로그인은 `POST /auth/login`).
비밀번호는 `{bcrypt}` 접두어가 붙은 해시로만 저장되며 응답에 포함되지 않는다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| username | O | 영문 소문자·숫자·밑줄(`_`)만, 4~20자 (대문자·공백·한글 불가) |
| nickname | O | 한글(가-힣)·영문 대소문자·숫자·밑줄(`_`)만, 2~20자 (공백 불가, 대소문자 구분: `Kim`과 `kim`은 다른 닉네임) |
| password | O | 8~64자, 공백만 있으면 안 됨, UTF-8로 72바이트 이하 (한글은 글자당 3바이트라 24자까지) |

요청 예시

```json
{
  "username": "user01",
  "nickname": "길동이",
  "password": "password123"
}
```

성공 응답 `201 Created`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이"
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | username/nickname/password가 비었거나 규칙 위반, JSON 형식이 잘못됨 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 이미 있는 username 또는 nickname (둘을 구분해 알려 주지 않음. 동시에 같은 아이디·닉네임으로 가입해도 한 명만 성공) |

### 8. 로그인 `POST /auth/login`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다.
성공하면 액세스 토큰(JWT, HS256)을 `access_token` 쿠키로 내려준다. 쿠키: `HttpOnly; Path=/; SameSite=Lax; Max-Age=900` (HTTPS 환경에서는 `Secure`도 붙음). 세션(JSESSIONID)은 만들지 않는다.
리프레시 토큰도 `refresh_token` 쿠키로 함께 내려준다. 값은 랜덤 문자열(서버 Redis에는 해시만 저장), 쿠키: `HttpOnly; Path=/api/auth; SameSite=Lax; Max-Age=604800`(7일, HTTPS 환경에서는 `Secure`도 붙음). 경로는 브라우저 기준이며 설정 `app.cookie.refresh-path`로 바꾼다. 여러 기기에서 동시에 로그인할 수 있다(로그인마다 별도 토큰).
토큰 클레임: `sub`=사용자 id, `username`, `iat`, `exp`(발급 15분 후).
만료되거나 변조된 `access_token` 쿠키가 붙어 와도 이 API는 정상 동작한다.

요청 본문: `{ "username": "user01", "password": "password123" }` (둘 다 필수, 빈 값 불가. 형식 검사는 가입에서만 한다)

성공 응답 `200 OK` + `Set-Cookie: access_token=...` + `Set-Cookie: refresh_token=...`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이"
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | username/password가 비었거나 JSON 형식이 잘못됨 |
| 401 | 아이디 또는 비밀번호가 틀림 (없는 아이디와 틀린 비밀번호 모두 같은 401 응답이라 본문으로 구분할 수 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 9. 로그아웃 `POST /auth/logout`

CSRF 헤더 필요. `refresh_token` 쿠키가 있으면 서버(Redis)의 리프레시 토큰을 삭제하고, `access_token`·`refresh_token` 쿠키를 둘 다 지운다(`Max-Age=0`). 로그인하지 않았거나 토큰이 만료돼도 항상 성공한다.

성공 응답 `204 No Content` + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

실패

| 상태코드 | 언제 |
|----------|------|
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 10. 내 정보 `GET /auth/me`

`access_token` 쿠키가 필요하다 (Authorization 헤더는 사용하지 않음). 토큰에는 닉네임이 없어서 매번 DB에서 회원을 읽어 응답한다.

성공 응답 `200 OK`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이"
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 쿠키가 없음, 토큰이 만료됨, 서명이 변조됨, 토큰은 유효하지만 회원이 DB에 없음 (리다이렉트(302)는 하지 않음) |

### 11. 토큰 재발급 `POST /auth/refresh`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다. 요청 본문은 없다.
`refresh_token` 쿠키(브라우저가 Path=`/api/auth` 요청에 자동으로 붙임)로 새 액세스 토큰과 새 리프레시 토큰을 받는다.
리프레시 토큰은 한 번만 쓸 수 있다(회전): 쓰면 옛 토큰은 바로 지워지고, 같은 토큰을 다시 쓰면 401이다.
만료되거나 변조된 `access_token` 쿠키가 붙어 와도 이 API는 정상 동작한다.
주의: 실패(401) 응답이 두 쿠키를 지우므로, 클라이언트는 재발급 요청을 동시에 하나만 보내야 한다(여러 요청이 동시에 401을 받아도 재발급은 한 번만, S4-e 화면에서 처리).

성공 응답 `200 OK` + `Set-Cookie: access_token=...` + `Set-Cookie: refresh_token=...` (쿠키 속성은 로그인과 같음)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이"
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 쿠키가 없음, 모르는 토큰, 이미 사용한 토큰, 만료됨, 사용자가 삭제됨 (이유는 구분해서 알려주지 않음). 응답에 두 쿠키 삭제 `Set-Cookie`(`Max-Age=0`)가 붙음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

## 내 정보 변경 (Users)

둘 다 로그인(`access_token` 쿠키)과 CSRF 헤더(`X-XSRF-TOKEN`)가 필요하다. 검사 순서: CSRF(403) → 로그인(401) → 본문 형식(400) → 그 밖의 검사.
단, 토큰은 유효하지만 회원이 DB에 없고 본문도 잘못된 경우에는 400이 먼저 나온다.

### 12. 닉네임 변경 `PUT /users/me/nickname`

요청 본문

```json
{ "nickname": "새닉네임" }
```

| 필드 | 규칙 |
|------|------|
| nickname | 한글·영문·숫자·밑줄 2~20자, 공백 불가, 대소문자 구분 (가입과 같은 규칙). 비밀번호 확인은 받지 않음 |

성공 응답 `200 OK` (자기 현재 닉네임 그대로 보내도 200)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "새닉네임"
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 닉네임이 비었거나 규칙 위반, JSON 형식이 잘못됨 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 다른 회원이 이미 쓰는 닉네임 (동시에 같은 닉네임으로 바꾸려는 경우도 포함) |

### 13. 비밀번호 변경 `PUT /users/me/password`

요청 본문

```json
{ "currentPassword": "oldPassw0rd", "newPassword": "newPassw0rd" }
```

| 필드 | 규칙 |
|------|------|
| currentPassword | 비어 있으면 안 됨, 64자·UTF-8 72바이트 이하 (맞는지는 서버가 확인) |
| newPassword | 8~64자, 공백만은 불가, UTF-8 72바이트 이하 (가입과 같은 규칙) |

성공하면 비밀번호를 바꾸고 이 회원의 모든 리프레시 토큰을 지운다(모든 기기 로그아웃). 클라이언트는 새 비밀번호로 다시 로그인해야 한다.

성공 응답 `204 No Content` (본문 없음) + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

실패 (비밀번호·토큰은 그대로. 단 아래 500 예외 참고)

| 상태코드 | 언제 |
|----------|------|
| 400 | 값이 비었음, newPassword가 규칙 위반, JSON 형식이 잘못됨, 현재 비밀번호가 틀림, 새 비밀번호가 현재 비밀번호와 같음 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

주의: 현재 비밀번호가 틀려도 401이 아니라 400이다(401이면 프론트가 토큰 재발급을 시도하기 때문).
예외: 비밀번호를 바꾼 뒤 Redis(리프레시 토큰 삭제) 실패로 500이 나면 비밀번호는 이미 바뀌었을 수 있다. 새 비밀번호로 로그인해 볼 것.

### 14. 회원 탈퇴 `DELETE /users/me`

요청 본문 (DELETE지만 본문이 있다. `Content-Type: application/json`)

```json
{ "password": "myPassw0rd" }
```

| 필드 | 규칙 |
|------|------|
| password | 비어 있으면 안 됨, 64자·UTF-8 72바이트 이하 (맞는지는 서버가 확인) |

성공 응답 `204 No Content` (본문 없음) + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

검사 순서: CSRF(403) -> 로그인(401) -> 본문 형식(400) -> 회원이 DB에 있는지(없으면 401) -> 비밀번호 확인(틀리면 400) -> 삭제.

탈퇴하면
- 회원 정보가 지워지고, 이 회원의 모든 리프레시 토큰도 지워진다(모든 기기 로그아웃).
- 이 회원이 쓴 글은 **지워지지 않고** 작성자만 없어진다(`author`가 `null`). 작성자 없는 글은 아무도 수정·삭제할 수 없다(403).
- 같은 아이디·닉네임으로 다시 가입할 수 있다(새 회원이며 옛 글과는 이어지지 않는다).
- 탈퇴 전에 받은 액세스 토큰으로 `GET /auth/me`, `POST /posts` 등을 부르면 401이다. 탈퇴 전 리프레시 토큰으로 재발급해도 401이다.
- 글 작성 요청과 탈퇴가 거의 동시에 일어나 글이 저장되지 못한 경우에도 401이다(500 아님).

실패 (회원·글은 그대로. 단 아래 500 예외 참고)

| 상태코드 | 언제 |
|----------|------|
| 400 | 비밀번호가 비었음·64자/UTF-8 72바이트 초과, JSON 형식이 잘못됨, 비밀번호가 틀림 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

주의: 비밀번호가 틀려도 401이 아니라 400이다(401이면 프론트가 토큰 재발급을 시도하기 때문).
예외: 회원을 지운 뒤 Redis(리프레시 토큰 삭제) 실패로 500이 나면 회원은 이미 삭제된 상태다. 남은 리프레시 토큰으로 재발급을 요청해도 회원이 DB에 없어 401이므로 다시 로그인되지는 않는다.
