# API 명세

게시판 API 목록. 새 API를 만들거나 바꾸면 이 문서에 이어서 적는다.
에러 응답 본문은 Spring 기본 형식을 쓰고, 상태코드가 중요하다.
브라우저(프론트엔드) 허용 주소는 환경변수 `CORS_ALLOWED_ORIGINS`로 설정한다(기본값 `http://localhost:5173`, 쉼표로 여러 개).
허용되지 않은 주소에서 브라우저로 요청하면 403이 반환된다 (curl 등 브라우저가 아닌 요청은 CORS 대상이 아님).

배포 환경(EC2)에서는 nginx를 거치므로 API가 `/api` 아래에 있다 (예: `/api/posts`, `/api/posts/1`). nginx가 `/api`를 떼고 백엔드에 전달하므로 이 문서의 URL 자체는 그대로다.
헬스체크는 `/actuator/health` 그대로 쓴다 (`/api` 없음). 로컬 브라우저도 Vite 프록시 `/api`를 쓴다(`refresh_token` 쿠키 Path=`/api/auth`가 붙으려면 필요). curl 등은 `http://localhost:8080`에 직접 요청해도 된다.
글 작성 응답의 `Location` 헤더는 백엔드 기준(`/posts/{id}`)이며 nginx가 바꾸지 않는다. 배포 환경에서 API로 따라가려면 앞에 `/api`를 붙인다 (현재 프론트는 `Location`을 사용하지 않음).

## CSRF 보호 (모든 POST/PUT/DELETE 공통)

S4-a부터 Spring Security가 켜져 있어서, **POST/PUT/DELETE는 `X-XSRF-TOKEN` 헤더가 없으면 `403`** 이다 (GET은 필요 없음).
1. 앱 시작 시 `GET /csrf`를 한 번 호출하면 `XSRF-TOKEN` 쿠키가 설정된다.
2. 이후 POST/PUT/DELETE마다 그 쿠키 값을 `X-XSRF-TOKEN` 헤더에 실어 보낸다 (axios는 같은 주소 요청에서 자동으로 해 준다).

서버는 세션(`JSESSIONID`)을 만들지 않는다. 로그인이 필요한 경로는 인증 없이 부르면 `401`이다 (허용 목록 밖의 없는 경로도 404가 아니라 401).
글 API는 **목록·단건 조회(GET)만 로그인 없이** 쓸 수 있다. 작성·수정·삭제(POST/PUT/DELETE)는 로그인(`access_token` 쿠키)이 필요하고, 토큰이 없거나 만료·변조되면 `401`이다.
조회(GET)는 만료되거나 변조된 `access_token` 쿠키가 붙어 와도 정상(200)이다.
수정은 **본인이 쓴 글만** 가능하다. 남의 글, 그리고 작성자가 없는 글(S4-d 이전에 쓴 글)은 관리자도 `403`이다.
삭제는 **본인 또는 관리자**가 할 수 있다(관리자는 작성자가 없는 글도 지울 수 있다). 남의 글을 일반 회원이 지우면 `403`이다.
관리자 확인: 토큰의 `role`이 `ADMIN`이면 서버가 DB에서 회원을 다시 읽는다(회원이 없으면 `401`, DB의 role이 `USER`면 `403`). 토큰은 최대 15분 묵을 수 있어서다. 관리자 지정은 API가 없고 DB에서 직접 한다(`UPDATE users SET role = 'ADMIN' WHERE username = '...'`). 가입으로는 만들 수 없다.
쓰기 요청은 아래 순서로 검사하고 먼저 걸리는 오류를 돌려준다: CSRF 403 → 로그인 안 됨 401 → 본문 검증 400 → 없는 글 404 → 본인 글 아님 403.
단, 관리자 토큰의 회원 재확인(401·403)은 글·댓글이 있는지 확인(404)한 다음에 한다.

### 학교 인증 규칙 (S10-d, 글쓰기·댓글·공감·신고 공통)
학교 인증을 안 한 회원은 **읽기만** 가능하다. 아래 "만들기"(글쓰기·댓글·공감·신고, 그리고 비자 후기 작성·비자 일정 등록 `PUT /users/me/visa-plan`·물건 글 올리기 `POST /market-items`)는 학교 인증(`verifiedSchool`)을 마친 회원이, **인증한 학교의 글에만** 할 수 있다(관리자도 예외 없음).
- 글쓰기 `POST /posts`: 본문의 `schoolId`가 인증한 학교와 같아야 한다.
- 댓글 작성, 공감 누르기, 글·댓글 신고: 대상 글(댓글이면 그 댓글의 글)의 학교가 인증한 학교와 같아야 한다. 학교가 없는 옛 글에는 아무도 할 수 없다(읽기만). 중고 글 신고도 중고 글의 학교가 인증한 학교와 같아야 한다.
- 비자 후기 작성 `POST /visa-reviews`: 인증한 학교가 후기의 학교로 자동 복사된다. 학교를 본문으로 받지 않아 "다른 학교 403"은 없고 미인증만 403이다. (검사 순서: CSRF 403 → 로그인 401 → 본문 400 → 회원 없음 401 → 미인증 403 → 날짜 400)
- 실패는 모두 `403`이다(`401`은 프론트가 토큰 재발급을 돌리므로 쓰지 않는다). 미인증과 다른 학교(학교 없는 글 포함) 모두 403이며 응답 본문으로는 구분할 수 없다. 화면은 `/auth/me` 등 회원 응답의 `verifiedSchool`과 글의 학교를 비교해 먼저 막는다. CSRF 실패도 403이다.
- 인증 여부는 토큰이 아니라 매번 DB로 확인한다(인증 직후 토큰 재발급 없이 바로 반영).
- 검사 순서: CSRF 403 → 로그인 401 → 본문 400 → 회원이 DB에 있는지(없으면 401) → 미인증 403 → (글쓰기: 없는 학교 400) / (그 외: 없는 글·댓글 404) → 다른 학교 403 → (그 뒤의 자기 것 400·중복 409).
- 인증과 무관한 것: 글·댓글·비자 후기·물건 글 수정·삭제(본인·관리자 규칙 그대로), 비자 일정 조회·삭제, 공감 취소, 모든 GET, 관리자 신고 API, 회원 API.

## 게시글 (Post)

| 기능 | 메서드 | URL | 성공 | 실패 |
|------|--------|-----|------|------|
| 작성 | POST | `/posts` | 201 | 400, 401, 403 |
| 단건 조회 | GET | `/posts/{id}` | 200 | 404, 400 |
| 목록 조회 | GET | `/posts` | 200 | 400, 404 |
| 수정 | PUT | `/posts/{id}` | 200 | 400, 401, 403, 404 |
| 삭제 | DELETE | `/posts/{id}` | 204 | 400, 401, 403, 404 |

### 응답 필드

| 필드 | 타입 | 설명 |
|------|------|------|
| id | 숫자 | 게시글 번호 |
| title | 문자열 | 제목 |
| content | 문자열 | 본문 |
| createdAt | 문자열 | 작성 시각 (예: `2026-11-01T01:30:00.123456Z`) |
| author | 객체 또는 null | 글쓴이 `{ "id": 숫자, "nickname": 문자열 }`. 로그인 아이디(username)는 숨긴다. 작성자가 없는 글(S4-d 이전에 쓴 글)은 `null` |
| school | 객체 또는 null | 학교 `{ "id": 숫자, "name": 문자열 }`. 학교가 없는 글(S7-a 이전에 쓴 글)은 `null` |
| category | 객체 | 말머리 `{ "code": 문자열, "name": 문자열 }` (예: `{ "code": "CHAT", "name": "잡담" }`). S7-a 이전에 쓴 글은 `CHAT` |
| commentCount | 숫자 | 댓글 수. 조회할 때 센다 (S8-b). 없으면 0 |
| likeCount | 숫자 | 공감 수. 조회할 때 센다 (S8-b). 없으면 0 |

말머리 코드는 `CHAT`(잡담), `QUESTION`(질문), `CAMPUS_LIFE`(학교생활) 세 가지다.

`commentCount`·`likeCount`는 표에 칸을 두지 않고 조회할 때 센다. 단건 조회는 쿼리 3번(글·댓글 수·공감 수), 목록은 글 수와 상관없이 3번 고정(글 1 + 댓글 수 group by 1 + 공감 수 group by 1). 작성(POST) 응답은 항상 `0`·`0`, 수정(PUT) 응답은 현재 값이다. 내가 공감했는지는 여기 담지 않고 로그인 전용 `GET /posts/{id}/likes/me`로 따로 확인한다.

시간대: UTC(Z). 소수점 자릿수는 가변(최대 6자리). 화면에 보여줄 때 한국 시간으로 변환한다.

### 1. 게시글 작성 `POST /posts`

로그인 필요. 글쓴이는 로그인한 사용자로 정해지며, 요청 본문에 `author`·`authorId` 같은 값을 보내도 무시한다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 공백만 있으면 안 됨, 최대 100자, NUL 문자 불가 |
| content | O | 공백만 있으면 안 됨, 길이 제한 없음, NUL 문자 불가 |
| schoolId | O | `GET /schools`에 있는 학교 id. 없는 id면 400 |
| category | O | `CHAT`, `QUESTION`, `CAMPUS_LIFE` 중 하나. 그 밖의 문자열이면 400 |

요청 예시

```json
{
  "title": "첫 글",
  "content": "안녕하세요",
  "schoolId": 1,
  "category": "CHAT"
}
```

성공 응답 `201 Created` (헤더 `Location: /posts/1`)

```json
{
  "id": 1,
  "title": "첫 글",
  "content": "안녕하세요",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  },
  "school": {
    "id": 1,
    "name": "경희대학교"
  },
  "category": {
    "code": "CHAT",
    "name": "잡담"
  },
  "commentCount": 0,
  "likeCount": 0
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | title/content가 비었거나 공백만 있음, title이 100자 초과, NUL 문자 포함, schoolId·category가 없음, 없는 학교 id, 없는 말머리 코드, JSON 형식이 잘못됨, category를 숫자로 보냄(예: `0`도 400) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효하지만 그 사용자가 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, `schoolId`가 인증한 학교와 다름 (위 "학교 인증 규칙") |

### 3. 게시글 목록 조회 `GET /posts`

최신순(id 내림차순)으로 돌려준다. 페이징 없음. 글이 없으면 빈 배열 `[]`. 로그인 없이 호출 가능. (아래 예시의 두 번째 글처럼 작성자·학교가 없는 옛 글은 `author`·`school`이 `null`이고 `category`는 `CHAT`)

쿼리 파라미터 (둘 다 선택, 같이 주면 두 조건을 모두 만족하는 글만)

| 이름 | 설명 |
|------|------|
| `schoolId` | 그 학교 글만. 학교 없는 옛 글은 포함되지 않는다 |
| `category` | 그 말머리 글만 (`CHAT`, `QUESTION`, `CAMPUS_LIFE`) |

- 파라미터 없이 부르면 학교 없는 옛 글까지 전체를 돌려준다.
- 값이 비어 있으면(`?schoolId=&category=`) 조건을 안 건 것과 같다.
- 존재하는 학교인데 글이 없으면 `200`과 `[]`.
- 예: `GET /posts?schoolId=1`, `GET /posts?category=QUESTION`, `GET /posts?schoolId=1&category=QUESTION`

실패

### 4. 게시글 수정 `PUT /posts/{id}`

로그인 필요, 본인이 쓴 글만 가능. 제목·본문·말머리를 모두 새 값으로 바꾼다 (일부만 바꾸는 PATCH는 없음). `createdAt`은 바뀌지 않는다.
**학교는 바꿀 수 없다.** 요청 본문에 `schoolId`를 보내도 무시한다(에러 아님).

요청 본문 (title·content는 작성과 같은 규칙, 셋 다 필수)

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 공백만 있으면 안 됨, 최대 100자, NUL 문자 불가 |
| content | O | 공백만 있으면 안 됨, 길이 제한 없음, NUL 문자 불가 |
| category | O | `CHAT`, `QUESTION`, `CAMPUS_LIFE` 중 하나. 그 밖의 문자열이면 400 |

요청 예시: `PUT /posts/1`

```json
{
  "title": "수정한 제목",
  "content": "수정한 내용",
  "category": "QUESTION"
}
```

성공 응답 `200 OK`

```json
{
  "id": 1,
  "title": "수정한 제목",
  "content": "수정한 내용",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  },
  "school": {
    "id": 1,
    "name": "경희대학교"
  },
  "category": {
    "code": "QUESTION",
    "name": "질문"
  },
  "commentCount": 0,
  "likeCount": 0
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | title/content가 비었거나 공백만 있음, title이 100자 초과, NUL 문자 포함, category가 없거나 없는 말머리 코드, JSON 형식이 잘못됨, category를 숫자로 보내도 400, id가 숫자가 아님 (남의 글이어도 본문이 잘못되면 403이 아니라 400) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id·숫자 아닌 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (작성자가 없는 글 포함, 관리자도 수정할 수 없음) |
| 404 | 없는 id (예: `/posts/999`) |

검사 순서: 400(본문) → 404 → 403. 즉 본문이 올바르고 글이 있어야 본인 글인지 확인한다.

### 5. 게시글 삭제 `DELETE /posts/{id}`

로그인 필요, 본인 또는 관리자만 가능. DB에서 글을 완전히 지운다 (복구 불가). 그 글의 댓글·공감·신고(글과 댓글에 달린 신고 모두)도 함께 삭제된다.

요청 예시: `DELETE /posts/1`

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 (예: `/posts/abc`) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id·숫자 아닌 id도 401. 남의 글을 관리자 토큰으로 지우려는데 그 회원이 DB에 없는 경우도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |
| 404 | 없는 id (이미 삭제된 id 포함). 본인과 관리자가 동시에 지우면 늦은 쪽이 404 |

## 학교·말머리 (School, Category)

글을 쓸 때 고를 선택지 목록. 둘 다 로그인 없이 호출 가능하고, 만료되거나 변조된 `access_token` 쿠키가 붙어 와도 200이다.

### 5-1. 학교 목록 `GET /schools`

학교를 이름순으로 돌려준다. 캠퍼스 구분은 없다. 학교는 DB 마이그레이션으로 넣어 두며(경희대·고려대·성균관대·연세대·한양대) 추가·수정 API는 없다.

성공 응답 `200 OK`

```json
[
  { "id": 1, "name": "경희대학교", "emailDomains": ["khu.ac.kr"] },
  { "id": 3, "name": "성균관대학교", "emailDomains": ["g.skku.edu", "skku.edu"] }
]
```

`emailDomains`는 그 학교의 인증용 메일 도메인(정렬됨, 도메인이 없으면 `[]`). 글 응답의 `school`에는 들어 있지 않다(`id`, `name`만).

### 5-2. 말머리 목록 `GET /categories`

성공 응답 `200 OK`

```json
[
  { "code": "CHAT", "name": "잡담" },
  { "code": "QUESTION", "name": "질문" },
  { "code": "CAMPUS_LIFE", "name": "학교생활" }
]
```

`code`를 글 작성·수정 요청의 `category`에 보낸다.

## 댓글 (Comment)

글에 다는 평댓글(대댓글 없음). 목록 조회(GET)만 로그인 없이 쓸 수 있고(만료·변조된 `access_token` 쿠키가 붙어 와도 200), 작성·수정·삭제는 로그인과 CSRF 헤더가 필요하다.
쓰기 검사 순서는 글과 같다: CSRF 403 → 로그인 401 → 본문 400 → 없는 글·댓글 404 → 본인 댓글 아님 403. 작성(POST)만 그 사이에 학교 인증 403(미인증 → 없는 글 404 → 다른 학교 글 403)이 들어간다("학교 인증 규칙" 참고).
단, 토큰은 유효하지만 회원이 DB에 없고 본문도 잘못된 경우에는 400이 먼저 나온다.

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 목록 | GET | `/posts/{postId}/comments` | 공개 | 200 | 400, 404 |
| 작성 | POST | `/posts/{postId}/comments` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404 |
| 수정 | PUT | `/comments/{id}` | 본인 | 200 | 400, 401, 403, 404 |
| 삭제 | DELETE | `/comments/{id}` | 본인·관리자 | 204 | 400, 401, 403, 404 |

### 응답 필드 (CommentResponse)

| 필드 | 타입 | 설명 |
|------|------|------|
| id | 숫자 | 댓글 번호 |
| postId | 숫자 | 댓글이 달린 글 번호 |
| content | 문자열 | 내용 |
| createdAt | 문자열 | 작성 시각 (글과 같은 UTC 형식) |
| author | 객체 또는 null | 댓글쓴이 `{ "id": 숫자, "nickname": 문자열 }`. 작성자가 탈퇴했으면 `null` |

### 5-3. 댓글 목록 `GET /posts/{postId}/comments`

id 오름차순(오래된 댓글이 먼저). 페이징 없음. 댓글이 없으면 `[]`.

```json
[
  {
    "id": 1,
    "postId": 3,
    "content": "첫 댓글",
    "createdAt": "2026-11-07T01:30:00.123456Z",
    "author": { "id": 1, "nickname": "길동이" }
  }
]
```

실패: 400(postId가 숫자가 아님), 404(없는 글)

### 5-4. 댓글 작성 `POST /posts/{postId}/comments`

작성자는 로그인한 사용자로 정해진다(본문에 `author`를 보내도 무시).

요청 본문: `{ "content": "첫 댓글" }`

| 필드 | 필수 | 규칙 |
|------|------|------|
| content | O | 공백만 있으면 안 됨, 1~1000자, NUL 문자 불가 |

성공 응답 `201 Created` (헤더 `Location: /comments/1`) + 위 CommentResponse 한 건

| 상태코드 | 언제 |
|----------|------|
| 400 | content가 비었거나 공백만 있음, 1000자 초과, NUL 문자 포함, JSON 형식이 잘못됨, postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 작성 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 글이 인증한 학교의 글이 아님(학교 없는 글 포함) |
| 404 | 없는 글 (작성 도중 글이 삭제된 경우 포함) |

### 5-5. 댓글 수정 `PUT /comments/{id}`

내용만 새 값으로 바꾼다(작성 시각·작성자는 그대로). 본문 규칙은 작성과 같다. 성공 시 `200 OK` + CommentResponse.

| 상태코드 | 언제 |
|----------|------|
| 400 | content 규칙 위반, JSON 형식이 잘못됨, id가 숫자가 아님 (남의 댓글이어도 본문이 잘못되면 403이 아니라 400) |
| 401 | 로그인 안 됨 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 댓글이 아님 (작성자가 없는 댓글 포함) |
| 404 | 없는 댓글 |

### 5-6. 댓글 삭제 `DELETE /comments/{id}`

본인 또는 관리자만 가능(관리자는 작성자 없는 댓글도 가능). DB에서 댓글을 완전히 지운다. 이 댓글에 달린 신고도 함께 삭제된다. 성공 시 `204 No Content`.

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 |
| 401 | 로그인 안 됨 (남의 댓글을 관리자 토큰으로 지우려는데 그 회원이 DB에 없는 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 댓글이 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |
| 404 | 없는 댓글 (이미 삭제된 id 포함). 본인과 관리자가 동시에 지우면 늦은 쪽이 404 |

## 공감 (Like)

글에만 누를 수 있다(댓글 공감 없음). 한 회원이 한 글에 한 번만, 취소할 수 있다. 개수는 글 응답의 `likeCount`로 공개되고(비로그인도 봄), 아래 3개는 모두 로그인이 필요하다(공개 경로 아님).
쓰기 검사 순서: CSRF 403 -> 로그인 401 -> (누르기만) 미인증 403 -> 없는 글 404 -> (누르기만) 다른 학교 글 403 -> 상태 충돌 409. 학교 인증은 "학교 인증 규칙" 참고.
공감은 본문이 없어서 @Valid 검사가 없다. 토큰은 유효하지만 회원이 DB에 없으면 바로 401이고, 경로의 postId가 숫자가 아니면 그 전에 400이 먼저 나온다.

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 공감 | POST | `/posts/{postId}/likes` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 공감 취소 | DELETE | `/posts/{postId}/likes` | 로그인 | 200 | 400, 401, 403, 404 |
| 내가 공감했는지 | GET | `/posts/{postId}/likes/me` | 로그인 | 200 | 400, 401, 404 |

### 5-7. 공감 `POST /posts/{postId}/likes`

요청 본문 없음. 성공 응답 `201 Created`: 처리 후 개수를 다시 센 값.

```json
{ "likeCount": 1, "liked": true }
```

| 상태코드 | 언제 |
|----------|------|
| 400 | postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 누르는 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 글이 인증한 학교의 글이 아님(학교 없는 글 포함) |
| 404 | 없는 글 (누르는 도중 글이 삭제된 경우 포함) |
| 409 | 이미 공감한 글. 같은 회원이 동시에 여러 번 눌러도 한 번만 성공하고 나머지는 409 |

### 5-8. 공감 취소 `DELETE /posts/{postId}/likes`

성공 응답 `200 OK`: 처리 후 개수.

```json
{ "likeCount": 0, "liked": false }
```

| 상태코드 | 언제 |
|----------|------|
| 400 | postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 404 | 없는 글, 또는 내가 공감하지 않은 글 |

### 5-9. 내가 공감했는지 `GET /posts/{postId}/likes/me`

성공 응답 `200 OK`

```json
{ "liked": true }
```

| 상태코드 | 언제 |
|----------|------|
| 400 | postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (공개 경로가 아니므로 쿠키가 없거나 만료·변조면 401, 토큰은 유효하지만 회원이 DB에 없는 경우도 401) |
| 404 | 없는 글 |


탈퇴하면 그 회원의 공감은 DB가 함께 지운다(`likeCount`가 1 줄어든다). 글을 지우면 그 글의 공감도 함께 지워진다.

## 신고 (Report)

회원이 글·댓글·중고 글을 신고한다. 신고 사유 목록(GET)만 로그인 없이 쓸 수 있고(만료·변조된 `access_token` 쿠키가 붙어 와도 200), 신고하기는 로그인과 CSRF 헤더가 필요하다.
관리자의 신고 목록·기각은 아래 "관리자(Admin)" 절. 일반 회원이 신고를 조회·취소하는 API는 없다.
검사 순서: CSRF 403 -> 로그인 401 -> 본문 400 -> 회원이 DB에 있는지(없으면 401) -> 미인증 403 -> 없는 대상 404 -> 다른 학교 글 403 -> 자기 글·댓글·중고 글 400 -> 중복 409. ("학교 인증 규칙" 참고)

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 사유 목록 | GET | `/report-reasons` | 공개 | 200 | - |
| 글 신고 | POST | `/posts/{postId}/reports` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 댓글 신고 | POST | `/comments/{id}/reports` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 중고 글 신고 | POST | `/market-items/{id}/reports` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |

### 5-10. 신고 사유 목록 `GET /report-reasons`

성공 응답 `200 OK`

```json
[
  { "code": "SPAM", "name": "광고·스팸" },
  { "code": "ABUSE", "name": "욕설·비방" },
  { "code": "SEXUAL", "name": "음란·선정적" },
  { "code": "PRIVACY", "name": "개인정보 노출" },
  { "code": "OTHER", "name": "기타" }
]
```

`code`를 신고 요청의 `reason`에 보낸다.

### 5-11. 글 신고 `POST /posts/{postId}/reports`, 5-12. 댓글 신고 `POST /comments/{id}/reports`, 중고 글 신고 `POST /market-items/{id}/reports`

신고자는 로그인한 사용자로 정해진다(본문에 보내도 무시). 한 회원은 같은 글(댓글·중고 글)을 한 번만 신고할 수 있다. 자기 글·자기 댓글·자기 중고 글은 신고할 수 없다(중고 글이면 400 "자기 중고 글은 신고할 수 없습니다."). 중고 글 신고(S13-e)도 글 신고와 같은 규칙·검사 순서·응답이고, 응답의 `target`만 `{ "type": "MARKET_ITEM", "id": 5, "postId": null }`이다.

요청 본문: `{ "reason": "SPAM", "detail": "광고예요" }`

| 필드 | 필수 | 규칙 |
|------|------|------|
| reason | O | 사유 목록의 `code` 중 하나 |
| detail | X | 최대 300자, NUL 문자 불가. `OTHER`여도 선택. 없거나 빈 문자열·공백뿐이면 `null`로 저장 |

성공 응답 `201 Created`. 신고 한 건을 따로 조회하는 API가 없어서 `Location` 헤더는 없다.

```json
{
  "id": 1,
  "target": { "type": "POST", "id": 3, "postId": 3 },
  "reason": { "code": "SPAM", "name": "광고·스팸" },
  "detail": "광고예요",
  "status": "PENDING",
  "createdAt": "2026-11-08T03:00:00.123456Z"
}
```

- `target.type`은 `POST`·`COMMENT`·`MARKET_ITEM`, `target.id`는 신고된 글(댓글·중고 글)의 id, `target.postId`는 그 글의 id(글 신고면 `id`와 같다, 중고 글 신고면 `null`).
- `status`는 새 신고면 항상 `PENDING`(처리 대기). 기각되면 `DISMISSED`.

| 상태코드 | 언제 |
|----------|------|
| 400 | reason이 없거나 사유 목록에 없음, detail 300자 초과, detail에 NUL 문자 포함, JSON 형식이 잘못됨, reason을 숫자로 보냄(예: `0`도 400), id가 숫자가 아님, 자기 글·자기 댓글·자기 중고 글을 신고함 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 신고 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 대상 글(댓글이면 그 댓글의 글)이 인증한 학교의 글이 아님(학교 없는 글 포함) |
| 404 | 없는 글·댓글·중고 글 (신고 도중 삭제된 경우 포함) |
| 409 | 이미 신고한 대상. 같은 회원이 동시에 여러 번 보내도 한 번만 성공하고 나머지는 409 |

신고는 대상이 지워지면 함께 지워진다(글을 지우면 그 글의 댓글과, 글·댓글에 달린 신고도 모두 삭제. 중고 글을 지우면 그 글의 신고도 삭제). 신고자가 탈퇴해도 신고는 남고 신고자만 없어진다.

## 관리자 (Admin)

신고 목록 보기와 기각은 관리자만 쓸 수 있다. 신고된 글·댓글·중고 글을 지우는 건 새 API 없이 기존 `DELETE /posts/{id}`, `DELETE /comments/{id}`, `DELETE /market-items/{id}`를 관리자 계정으로 부른다. 화면은 S9-d.

### 접근 규칙 (`/admin/**` 공통)

| 상황 | 결과 |
|------|------|
| 로그인 안 됨 (쿠키 없음, 토큰 만료·변조) | 401 |
| 토큰의 `role`이 `ADMIN`이 아님 (`USER`, `role` 클레임이 없는 옛 토큰, 모르는 값 포함) | 403 |
| 토큰은 `ADMIN`인데 회원이 DB에 없음 (탈퇴) | 401 |
| 토큰은 `ADMIN`인데 DB의 role은 `USER` (강등됨) | 403 |

- 토큰의 `role`은 최대 15분(액세스 토큰 수명) 묵을 수 있다. 관리자로 지정한 뒤에는 **다시 로그인하거나 토큰이 재발급(`POST /auth/refresh`)돼야** 새 role이 토큰에 반영된다. 반대로 강등·탈퇴는 서버가 매번 DB로 다시 확인하므로 바로 막힌다.
- 관리자 지정은 API가 없고 DB에서 직접 한다 (위 "CSRF 보호" 절 아래 설명 참고).
- 검사 순서: CSRF 403(PUT) → 로그인 401 → 토큰 role 403 → 파라미터 400 → DB 재확인 401/403 → 없는 신고 404 → 이미 기각 409. GET은 CSRF 헤더가 필요 없고, PUT은 `X-XSRF-TOKEN` 헤더가 필요하다.

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 신고 목록 | GET | `/admin/reports` | 관리자 | 200 | 400, 401, 403 |
| 신고 기각 | PUT | `/admin/reports/{id}/dismiss` | 관리자 | 200 | 400, 401, 403, 404, 409 |

## CSRF 토큰 (Csrf)

### 6. CSRF 쿠키 발급 `GET /csrf`

`XSRF-TOKEN` 쿠키를 설정한다. 로그인 없이 호출 가능.

성공 응답 `200 OK` (헤더 `Set-Cookie: XSRF-TOKEN=...; Path=/`)

```json
{
  "headerName": "X-XSRF-TOKEN"
}
```

`headerName`은 토큰을 실어 보낼 헤더 이름이다. 헤더에는 **쿠키에 설정된 값 그대로**를 쓴다.

## 회원 (Auth)

회원 응답(가입·로그인·`/auth/me`·재발급·닉네임 변경 공통)의 `verifiedSchool`은 학교 인증을 마친 학교 `{ "id": 숫자, "name": 문자열 }`, 미인증이면 `null`이다(인증은 15·16번 API 참고). 아래 예시는 모두 미인증 회원이다.

### 7. 회원가입 `POST /auth/signup`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다. 가입만 하고 로그인은 되지 않는다(로그인은 `POST /auth/login`).
비밀번호는 `{bcrypt}` 접두어가 붙은 해시로만 저장되며 응답에 포함되지 않는다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| username | O | 영문 소문자·숫자·밑줄(`_`)만, 4~20자 (대문자·공백·한글 불가) |
| nickname | O | 한글(가-힣)·영문 대소문자·숫자·밑줄(`_`)만, 2~20자 (공백 불가, 대소문자 구분: `Kim`과 `kim`은 다른 닉네임) |
| password | O | 8~64자, 공백만 있으면 안 됨, UTF-8로 72바이트 이하 (한글은 글자당 3바이트라 24자까지) |

요청 예시

```json
{
  "username": "user01",
  "nickname": "길동이",
  "password": "password123"
}
```

성공 응답 `201 Created`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | username/nickname/password가 비었거나 규칙 위반, JSON 형식이 잘못됨 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 이미 있는 username 또는 nickname (둘을 구분해 알려 주지 않음. 동시에 같은 아이디·닉네임으로 가입해도 한 명만 성공) |

### 8. 로그인 `POST /auth/login`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다.
성공하면 액세스 토큰(JWT, HS256)을 `access_token` 쿠키로 내려준다. 쿠키: `HttpOnly; Path=/; SameSite=Lax; Max-Age=900` (HTTPS 환경에서는 `Secure`도 붙음). 세션(JSESSIONID)은 만들지 않는다.
리프레시 토큰도 `refresh_token` 쿠키로 함께 내려준다. 값은 랜덤 문자열(서버 Redis에는 해시만 저장), 쿠키: `HttpOnly; Path=/api/auth; SameSite=Lax; Max-Age=604800`(7일, HTTPS 환경에서는 `Secure`도 붙음). 경로는 브라우저 기준이며 설정 `app.cookie.refresh-path`로 바꾼다. 여러 기기에서 동시에 로그인할 수 있다(로그인마다 별도 토큰).
토큰 클레임: `sub`=사용자 id, `username`, `role`(`USER`|`ADMIN`), `iat`, `exp`(발급 15분 후). `role`이 없는 옛 토큰은 `USER`로 취급한다.
만료되거나 변조된 `access_token` 쿠키가 붙어 와도 이 API는 정상 동작한다.

요청 본문: `{ "username": "user01", "password": "password123" }` (둘 다 필수, 빈 값 불가. 형식 검사는 가입에서만 한다)

성공 응답 `200 OK` + `Set-Cookie: access_token=...` + `Set-Cookie: refresh_token=...`
(응답의 `role`은 `"USER"` 또는 `"ADMIN"`)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | username/password가 비었거나 JSON 형식이 잘못됨 |
| 401 | 아이디 또는 비밀번호가 틀림 (없는 아이디와 틀린 비밀번호 모두 같은 401 응답이라 본문으로 구분할 수 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 9. 로그아웃 `POST /auth/logout`

CSRF 헤더 필요. `refresh_token` 쿠키가 있으면 서버(Redis)의 리프레시 토큰을 삭제하고, `access_token`·`refresh_token` 쿠키를 둘 다 지운다(`Max-Age=0`). 로그인하지 않았거나 토큰이 만료돼도 항상 성공한다.

성공 응답 `204 No Content` + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

실패

| 상태코드 | 언제 |
|----------|------|
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 10. 내 정보 `GET /auth/me`

`access_token` 쿠키가 필요하다 (Authorization 헤더는 사용하지 않음). 토큰에는 닉네임이 없어서 매번 DB에서 회원을 읽어 응답한다.

성공 응답 `200 OK`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 쿠키가 없음, 토큰이 만료됨, 서명이 변조됨, 토큰은 유효하지만 회원이 DB에 없음 (리다이렉트(302)는 하지 않음) |

### 11. 토큰 재발급 `POST /auth/refresh`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다. 요청 본문은 없다.
`refresh_token` 쿠키(브라우저가 Path=`/api/auth` 요청에 자동으로 붙임)로 새 액세스 토큰과 새 리프레시 토큰을 받는다.
리프레시 토큰은 한 번만 쓸 수 있다(회전): 쓰면 옛 토큰은 바로 지워지고, 같은 토큰을 다시 쓰면 401이다.
만료되거나 변조된 `access_token` 쿠키가 붙어 와도 이 API는 정상 동작한다.
주의: 실패(401) 응답이 두 쿠키를 지우므로, 클라이언트는 재발급 요청을 동시에 하나만 보내야 한다(여러 요청이 동시에 401을 받아도 재발급은 한 번만, S4-e 화면에서 처리).

성공 응답 `200 OK` + `Set-Cookie: access_token=...` + `Set-Cookie: refresh_token=...` (쿠키 속성은 로그인과 같음)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 쿠키가 없음, 모르는 토큰, 이미 사용한 토큰, 만료됨, 사용자가 삭제됨 (이유는 구분해서 알려주지 않음). 응답에 두 쿠키 삭제 `Set-Cookie`(`Max-Age=0`)가 붙음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

## 내 정보 변경 (Users)

이 절의 API(12~14번)는 모두 로그인(`access_token` 쿠키)과 CSRF 헤더(`X-XSRF-TOKEN`)가 필요하다. 검사 순서: CSRF(403) → 로그인(401) → 본문 형식(400) → 그 밖의 검사.
단, 토큰은 유효하지만 회원이 DB에 없고 본문도 잘못된 경우에는 400이 먼저 나온다.

### 12. 닉네임 변경 `PUT /users/me/nickname`

요청 본문

```json
{ "nickname": "새닉네임" }
```

| 필드 | 규칙 |
|------|------|
| nickname | 한글·영문·숫자·밑줄 2~20자, 공백 불가, 대소문자 구분 (가입과 같은 규칙). 비밀번호 확인은 받지 않음 |

성공 응답 `200 OK` (자기 현재 닉네임 그대로 보내도 200)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "새닉네임",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 닉네임이 비었거나 규칙 위반, JSON 형식이 잘못됨 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 다른 회원이 이미 쓰는 닉네임 (동시에 같은 닉네임으로 바꾸려는 경우도 포함) |

### 13. 비밀번호 변경 `PUT /users/me/password`

요청 본문

```json
{ "currentPassword": "oldPassw0rd", "newPassword": "newPassw0rd" }
```

| 필드 | 규칙 |
|------|------|
| currentPassword | 비어 있으면 안 됨, 64자·UTF-8 72바이트 이하 (맞는지는 서버가 확인) |
| newPassword | 8~64자, 공백만은 불가, UTF-8 72바이트 이하 (가입과 같은 규칙) |

성공하면 비밀번호를 바꾸고 이 회원의 모든 리프레시 토큰을 지운다(모든 기기 로그아웃). 클라이언트는 새 비밀번호로 다시 로그인해야 한다.

성공 응답 `204 No Content` (본문 없음) + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

실패 (비밀번호·토큰은 그대로. 단 아래 500 예외 참고)

| 상태코드 | 언제 |
|----------|------|
| 400 | 값이 비었음, newPassword가 규칙 위반, JSON 형식이 잘못됨, 현재 비밀번호가 틀림, 새 비밀번호가 현재 비밀번호와 같음 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

주의: 현재 비밀번호가 틀려도 401이 아니라 400이다(401이면 프론트가 토큰 재발급을 시도하기 때문).
예외: 비밀번호를 바꾼 뒤 Redis(리프레시 토큰 삭제) 실패로 500이 나면 비밀번호는 이미 바뀌었을 수 있다. 새 비밀번호로 로그인해 볼 것.

### 14. 회원 탈퇴 `DELETE /users/me`

요청 본문 (DELETE지만 본문이 있다. `Content-Type: application/json`)

```json
{ "password": "myPassw0rd" }
```

| 필드 | 규칙 |
|------|------|
| password | 비어 있으면 안 됨, 64자·UTF-8 72바이트 이하 (맞는지는 서버가 확인) |

성공 응답 `204 No Content` (본문 없음) + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

검사 순서: CSRF(403) -> 로그인(401) -> 본문 형식(400) -> 회원이 DB에 있는지(없으면 401) -> 비밀번호 확인(틀리면 400) -> 삭제.

탈퇴하면
- 회원 정보가 지워지고, 이 회원의 모든 리프레시 토큰도 지워진다(모든 기기 로그아웃).
- 이 회원이 쓴 글은 **지워지지 않고** 작성자만 없어진다(`author`가 `null`). 작성자 없는 글은 수정은 아무도 못 하고(403), 삭제는 관리자만 할 수 있다.
- 이 회원이 쓴 댓글도 지워지지 않고 작성자만 없어진다(`author`가 `null`). 작성자 없는 댓글은 수정은 아무도 못 하고(403), 삭제는 관리자만 할 수 있다.
- 이 회원이 누른 공감은 삭제되어 해당 글의 `likeCount`가 줄어든다.
- 이 회원이 한 신고는 남고 신고자만 없어진다(`reporter_id`가 null).
- 이 회원이 쓴 비자 후기도 남고 작성자만 없어진다(`author`가 `null`, 학교는 그대로).
- 이 회원의 비자 일정은 함께 지워진다(`ON DELETE CASCADE`).
- 이 회원이 올린 물건 글(중고거래·나눔)도 함께 지워진다(`ON DELETE CASCADE`). 판매자가 탈퇴하면 중고 글과 그 글에 달린 신고도 함께 삭제된다.
- 학교 인증 정보(인증 학교·시각·메일 해시)도 함께 지워진다. 그래서 그 학교 메일은 새 계정이 다시 인증에 쓸 수 있다(현재 의도한 동작. 막을지는 S11 기획 때 다시 결정).
- 인증 코드·발송 제한 같은 Redis 인증 키(`email-verify*`로 시작하는 키들)는 탈퇴 때 따로 지우지 않고, 시간이 지나면(코드 10분, 재발송 쿨다운 60초, 횟수 24시간) 저절로 사라진다. 같은 메일 하루 5회 제한(`email-verify-target`)은 계정과 무관하게 그대로 남는다.
- 같은 아이디·닉네임으로 다시 가입할 수 있다(새 회원이며 옛 글과는 이어지지 않는다).
- 탈퇴 전에 받은 액세스 토큰으로 `GET /auth/me`, `POST /posts` 등을 부르면 401이다. 탈퇴 전 리프레시 토큰으로 재발급해도 401이다.
- 글·댓글·공감·비자 후기 작성·비자 일정 등록·물건 글 올리기 요청과 탈퇴가 거의 동시에 일어나 저장되지 못한 경우에도 401이다(500 아님).

실패 (회원·글은 그대로. 단 아래 500 예외 참고)

| 상태코드 | 언제 |
|----------|------|
| 400 | 비밀번호가 비었음·64자/UTF-8 72바이트 초과, JSON 형식이 잘못됨, 비밀번호가 틀림 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

주의: 비밀번호가 틀려도 401이 아니라 400이다(401이면 프론트가 토큰 재발급을 시도하기 때문).
예외: 회원을 지운 뒤 Redis(리프레시 토큰 삭제) 실패로 500이 나면 회원은 이미 삭제된 상태다. 남은 리프레시 토큰으로 재발급을 요청해도 회원이 DB에 없어 401이므로 다시 로그인되지는 않는다.

## 학교 메일 인증 (School verification)

### 15. 인증 코드 요청 `POST /users/me/school-verification/code`

학교 메일로 6자리 인증 코드를 보낸다(코드 확인은 16번). 로그인과 CSRF 헤더(`X-XSRF-TOKEN`)가 필요하다. 검사 순서: CSRF(403) → 로그인(401) → 본문 형식(400) → 회원이 DB에 있는지(없으면 401) → 지원 도메인(400) → 이미 인증됨(409) → 다른 회원이 쓴 메일(409) → 재발송·하루 횟수(429) → 발송. 429 검사 순서: 재발송 60초 → 회원 하루 10회 → 같은 계정·같은 메일 하루 2회 → 같은 메일 하루 5회(계정 여러 개 합산). 앞에서 걸리면 뒤 횟수는 세지 않는다.

요청 본문

```json
{ "email": "a@yonsei.ac.kr" }
```

| 필드 | 규칙 |
|------|------|
| email | 비어 있으면 안 됨, 이메일 형식, 254자 이하. 앞뒤 공백 제거·소문자로 바꿔 처리하고, 학교는 `@` 뒤 도메인이 `school_email_domains`와 정확히 일치할 때만 인정(서브도메인 불가) |

성공 응답 `202 Accepted` (본문 없음). 코드는 6자리 숫자(앞자리 0 가능), 10분 동안 유효하다. 새 코드를 받으면 이전 코드는 쓸 수 없다. 메일 원문은 DB에 저장하지 않는다.
개발·테스트 환경(`app.mail.mode=log`, 기본)에서는 실제 메일 대신 서버 로그에 받는 사람과 코드가 찍힌다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 메일이 비었음·형식 아님·254자 초과, JSON 형식이 잘못됨, 지원하지 않는 학교 메일 도메인 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 이미 학교 인증을 마친 회원, 다른 회원이 이미 인증에 사용한 메일(대소문자만 달라도 같은 메일) |
| 429 | 직전 요청 후 60초가 지나지 않음(기존 코드는 그대로 유효), 하루 10회 초과, 같은 계정이 같은 메일 주소로 하루 2번 초과, 같은 메일 주소로는 하루 5번까지(계정 여러 개여도 합산) |
| 500 | 메일 발송 실패(저장한 코드·제한을 되돌리므로 바로 다시 요청할 수 있다) 또는 Redis 장애(이때는 60초 뒤 다시 요청해야 할 수 있다) |

### 16. 인증 코드 확인 `POST /users/me/school-verification`

15번에서 받은 6자리 코드를 확인하고 학교 인증을 완료한다. 로그인과 CSRF 헤더(`X-XSRF-TOKEN`)가 필요하다. 검사 순서: CSRF(403) → 로그인(401) → 본문 형식(400) → 회원이 DB에 있는지(없으면 401) → 이미 인증됨(409) → 코드 확인(틀림 400 / 코드 없음 410) → 저장(다른 회원이 쓴 메일 409).

요청 본문

```json
{ "code": "123456" }
```

| 필드 | 규칙 |
|------|------|
| code | 비어 있으면 안 됨, 정확히 숫자 6자리. 앞뒤 공백은 제거하고 검사 |

성공 응답 `200 OK` (인증 학교가 채워진 회원 정보. 이후 `GET /auth/me`에도 반영된다. 새 토큰은 필요 없다)

```json
{ "id": 1, "username": "alice", "nickname": "앨리스", "role": "USER", "verifiedSchool": { "id": 3, "name": "연세대학교" } }
```

코드는 일치하면 바로 지워지므로 한 번만 쓸 수 있다. 틀리면 시도 횟수가 1 늘고, 5번째로 틀리면 코드가 폐기되어 다시 받아야 한다. 재발송 쿨다운·하루 횟수는 확인으로 바뀌지 않는다. 성공 뒤 같은 코드를 다시 보내면 "이미 인증"이 먼저 검사되어 410이 아니라 409다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 코드가 비었음·숫자 6자리 아님, JSON 형식이 잘못됨 / 코드가 틀림(`인증 코드가 올바르지 않습니다.`, 시도 횟수 +1, 같은 코드로 다시 입력 가능) |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 이미 학교 인증을 마친 회원(같은 코드로 동시에 확인하면 진 요청은 보통 410, 드물게 409), 다른 회원이 이미 인증에 사용한 메일, 코드를 받은 뒤 학교가 삭제됨. 주의: 코드는 이미 소모된 뒤라 409 후에는 코드를 다시 받아야 한다 |
| 410 | 코드가 더 이상 없음 → 코드를 다시 받아야 함: 받은 적 없음·10분 만료(`인증 코드가 없거나 만료되었습니다.`), 5번째로 틀려 폐기됨(`틀린 횟수를 넘어 코드가 폐기되었습니다. 다시 받아 주세요.`), 같은 코드로 동시 확인해 이미 쓰인 경우 |
| 500 | Redis 장애 |

## 비자 후기 (Visa review)

비자 후기 표(`visa_reviews`)는 S11-a에서 만들었다. 현재 API는 선택지(17), 작성(18), 단건 조회(19), 목록(20), 수정(21), 삭제(22), 통계(23)이다. (내 비자 일정 24~26은 아래 별도 절) (작성·수정 요청 본문은 같은 필드를 쓴다.)

### 17. 비자 후기 선택지 `GET /visa-review-options`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). DB를 조회하지 않고 고정값을 돌려준다. 각 목록의 순서는 서버 enum 선언 순서다.

성공 응답 `200 OK`

```json
{
  "visaTypes": [
    { "code": "D_2", "name": "D-2 유학" },
    { "code": "D_4", "name": "D-4 어학연수" },
    { "code": "D_10", "name": "D-10 구직" },
    { "code": "E_7", "name": "E-7 특정활동(취업)" },
    { "code": "OTHER", "name": "기타" }
  ],
  "applicationTypes": [
    { "code": "NEW", "name": "신규 발급" },
    { "code": "REGISTRATION", "name": "외국인등록" },
    { "code": "EXTENSION", "name": "체류기간 연장" },
    { "code": "CHANGE", "name": "체류자격 변경" },
    { "code": "OTHER", "name": "기타" }
  ],
  "results": [
    { "code": "APPROVED", "name": "승인" },
    { "code": "DENIED", "name": "불허" }
  ]
}
```

`code`는 이후 후기 작성 요청에 보낼 값이고, `name`은 화면에 보여 줄 한글 이름이다.

### 18. 비자 후기 작성 `POST /visa-reviews`

로그인 필요, **학교 인증을 마친 회원만** 쓸 수 있다(관리자도 예외 없음). 후기의 학교는 본문으로 받지 않고 **작성자가 인증한 학교가 자동으로 복사**된다(`schoolId`·`authorId`·`author` 같은 모르는 필드를 보내도 무시한다). 그래서 글쓰기와 달리 "다른 학교 403"은 없다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| visaType | O | `GET /visa-review-options`의 `visaTypes` code 중 하나. 그 밖의 문자열·숫자(예: `0`)면 400 |
| applicationType | O | `applicationTypes` code 중 하나 |
| receivedDate | O | 접수일. `"2026-09-01"` 형식(`yyyy-MM-dd`), 형식이 틀리면 400 |
| resultDate | O | 결과 받은 날. 같은 형식 |
| result | O | `APPROVED`(승인), `DENIED`(불허) 중 하나 |
| content | | 후기 본문. 없거나 `null`이면 빈 문자열로 저장. 최대 2000자, NUL 문자 불가 |

날짜 규칙: 접수일 ≤ 결과일 ≤ 오늘(한국 시간 기준). 결과일이 접수일보다 앞서거나, 두 날짜 중 하나라도 오늘 이후면 400이다. 이에 더해 (1) 접수일은 한국 시간 오늘 기준 최근 5년 이내여야 한다(오늘 − 5년 당일은 통과, 하루라도 더 이전이면 400. 아주 옛날·음수 연도 날짜도 400). (2) 처리 일수(`resultDate - receivedDate`)는 365일 이하여야 한다(365일은 통과, 366일부터 400). 수정(`PUT`)에도 같은 규칙이 적용된다.

요청 예시

```json
{
  "visaType": "D_2",
  "applicationType": "EXTENSION",
  "receivedDate": "2026-09-01",
  "resultDate": "2026-09-20",
  "result": "APPROVED",
  "content": "서류는 3개월치 통장 사본을 냈어요."
}
```

성공 응답 `201 Created` (헤더 `Location: /visa-reviews/1`). 본문은 19번 단건 조회와 같다.

```json
{
  "id": 1,
  "author": { "id": 1, "nickname": "길동이" },
  "school": { "id": 1, "name": "경희대학교" },
  "visaType": { "code": "D_2", "name": "D-2 유학" },
  "applicationType": { "code": "EXTENSION", "name": "체류기간 연장" },
  "receivedDate": "2026-09-01",
  "resultDate": "2026-09-20",
  "result": { "code": "APPROVED", "name": "승인" },
  "processingDays": 19,
  "content": "서류는 3개월치 통장 사본을 냈어요.",
  "createdAt": "2026-11-01T01:30:00.123456Z"
}
```

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 회원이 DB에 있는지(없으면 401) → 학교 미인증 403 → 날짜 규칙 400 → 저장. (글쓰기와 같이 "누가 쓸 수 있나"를 먼저 보고 입력 내용은 그 뒤에 본다.)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 필수 필드 없음, 없는 코드·숫자로 보낸 enum, 날짜 형식 오류, 본문 2000자 초과, NUL 문자 포함, JSON 형식 오류, 결과일이 접수일보다 앞섬, 접수일·결과일이 오늘 이후, 접수일이 최근 5년보다 이전, 처리 기간이 365일 초과 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 저장 직전에 탈퇴해 저장되지 못함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함 |

### 19. 비자 후기 단건 조회 `GET /visa-reviews/{id}`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`).

요청 예시: `GET /visa-reviews/1`

성공 응답 `200 OK`: 18번의 응답 예시와 같은 모양.

| 필드 | 설명 |
|------|------|
| author | `{id, nickname}`. 작성자가 탈퇴했으면 `null` |
| school | `{id, name}`. 작성 시점에 인증한 학교(작성자가 탈퇴해도 그대로) |
| visaType, applicationType, result | `{code, name}` (code는 API 값, name은 화면용 한글 이름) |
| receivedDate, resultDate | `yyyy-MM-dd` |
| processingDays | 접수일부터 결과일까지의 일수(`resultDate - receivedDate`). 저장하지 않고 계산한다 |
| content | 본문. 안 썼으면 `""` |
| createdAt | 작성 시각 (UTC) |

실패

| 상태코드 | 언제 |
|----------|------|
| 404 | 없는 id |
| 400 | id가 숫자가 아님 (예: `/visa-reviews/abc`) (단, `/visa-reviews/stats`는 23번 통계 API) |

### 20. 비자 후기 목록 `GET /visa-reviews`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). 최신순(id 내림차순), 페이징 없음. 후기가 없으면 빈 배열 `[]`. 본문(`content`)까지 포함해 19번 단건과 같은 모양의 배열을 돌려준다.

쿼리 파라미터 (모두 선택, 넘긴 것만 AND 조건)

| 이름 | 설명 |
|------|------|
| `schoolId` | 그 학교의 후기만 |
| `visaType` | 비자 종류 code (`GET /visa-review-options`의 `visaTypes`) |
| `applicationType` | 신청 종류 code (`applicationTypes`) |

- 파라미터 없이 부르면 전체. 값이 비어 있으면(`?visaType=`) 조건을 안 건 것과 같다.
- 존재하는 학교인데 후기가 없으면 `200`과 `[]`.
- 예: `GET /visa-reviews?schoolId=1&visaType=D_2&applicationType=EXTENSION`

성공 응답 `200 OK`: 19번 응답 객체의 배열.

실패

| 상태코드 | 언제 |
|----------|------|
| 404 | 없는 학교 id (예: `?schoolId=999`) |
| 400 | `schoolId`가 숫자가 아님, 모르는 `visaType`·`applicationType` 코드 |

### 21. 비자 후기 수정 `PUT /visa-reviews/{id}`

로그인 필요, **본인이 쓴 후기만** 가능(관리자도 남의 후기는 수정할 수 없다). 학교 인증은 필요 없다. 요청 본문은 18번 작성과 같은 필드·규칙이며 모두 새 값으로 바꾼다(일부만 바꾸는 PATCH는 없음). 학교·작성자·`createdAt`은 바뀌지 않는다(`schoolId` 등 모르는 필드는 무시).

요청 예시: `PUT /visa-reviews/1` (본문은 18번과 같은 모양)

성공 응답 `200 OK`: 수정된 후기. 19번 응답과 같은 모양.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 날짜 규칙 400 → 없는 id 404 → 본인 아님 403 (글 수정과 같이 입력 오류가 먼저, 남의 후기여도 본문이 잘못되면 403이 아니라 400).

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 18번과 같은 본문 오류(필수 누락, 없는 코드, 날짜 형식·규칙 위반(접수일이 최근 5년보다 이전, 처리 기간이 365일 초과 포함), 2000자 초과, NUL 문자), id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 후기가 아님 (작성자가 탈퇴한 후기 포함, 관리자도 불가) |
| 404 | 없는 id |

### 22. 비자 후기 삭제 `DELETE /visa-reviews/{id}`

로그인 필요, 본인 또는 관리자만 가능. DB에서 후기를 완전히 지운다(복구 불가). 학교 인증은 필요 없다.

요청 예시: `DELETE /visa-reviews/1`

| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 후기가 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |

### 23. 비자 후기 통계 `GET /visa-reviews/stats`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). **학교 × 비자 종류 × 신청 종류** 조합마다 후기 건수와 평균 처리 일수(`resultDate - receivedDate`)를 돌려준다. 승인/불허로 나누지 않으며, **평균에는 불허 건도 포함**한다. 후기가 없는 조합은 행이 없고, 후기가 하나도 없으면 빈 배열 `[]`.

- 예: `GET /visa-reviews/stats?schoolId=1&visaType=D_2`
- 정렬: 학교 이름 가나다 → 학교 id → 비자 종류 선언 순 → 신청 종류 선언 순 (선택지 목록 17번의 순서와 같다).

```json
    "school": { "id": 1, "name": "경희대학교" },

    "applicationType": { "code": "NEW", "name": "신규 발급" },

```

| 필드 | 설명 |
|------|------|
| school | `{id, name}` |
| visaType, applicationType | `{code, name}` |
| count | 그 조합의 후기 수 (1 이상) |
| avgDays | 평균 처리 일수. 소수 1자리 반올림 |

실패

| 상태코드 | 언제 |
|----------|------|
| 404 | 없는 학교 id (예: `?schoolId=999`) |

## 내 비자 일정 (Visa plan)

회원마다 체류 만료일 하나만 적어 두는 기능(표 `visa_plans`, S12-a). 세 API 모두 **로그인 필요**(`/users/me/**`)이고 `/visa-reviews` 아래가 아니다. 응답에는 만료일과 함께 남은 일수·띠 단계·할 일 목록이 서버 계산으로 붙는다(S12-b).

### 24. 내 비자 일정 조회 `GET /users/me/visa-plan`

로그인 필요. 학교 인증은 필요 없다. **일정이 없어도 404가 아니라 `200`** 이고 `expiryDate`가 `null`이다(화면이 매번 불러도 되게).

성공 응답 `200 OK` (오늘 2026-11-10 서울 기준 예시)

```json
{
  "expiryDate": "2026-12-31",
  "daysLeft": 51,
  "stage": "PREPARE",
  "todos": [
    { "code": "PREPARE", "title": "체류 기간 연장·자격 변경 준비 — 필요한 서류와 신청 시기를 하이코리아에서 확인하세요", "dueDate": "2026-09-02", "daysLeft": -69 },
    { "code": "CHECK", "title": "신청 확인 — 연장이나 자격 변경을 할 계획이라면 하이코리아에서 방법을 확인하세요", "dueDate": "2026-12-01", "daysLeft": 21 },
    { "code": "URGENT", "title": "만료 임박 — 체류 상태를 하이코리아나 관할 출입국·외국인청에서 확인하세요", "dueDate": "2026-12-24", "daysLeft": 44 }
  ]
}
```

일정이 없을 때: `{ "expiryDate": null, "daysLeft": null, "stage": null, "todos": [] }`

| 필드 | 설명 |
|------|------|
| expiryDate | 저장된 체류 만료일. 일정이 없으면 null |
| daysLeft | 만료일 − **서울 오늘**(일 수). 오늘이 만료일이면 0, 지났으면 음수. 일정이 없으면 null |
| stage | 띠 단계 문자열. `daysLeft ≥ 121` → null, `31~120` → `PREPARE`, `8~30` → `CHECK`, `0~7` → `URGENT`, `< 0` → `EXPIRED`. 일정이 없으면 null |
| todos | 할 일 체크리스트(일정이 없으면 빈 배열). 시점 3개 고정(만료 120·30·7일 전), `dueDate` 오름차순. 이미 지난 할 일도 빼지 않고 `daysLeft`를 음수로 둔다 |
| todos[].code | 시점 코드 `PREPARE`·`CHECK`·`URGENT` (이름은 식별자라 기준 숫자를 바꿔도 그대로) |
| todos[].title | 할 일 문구(확인을 안내하는 말투, 개인 사정에 대한 지시·판단 없음) |
| todos[].dueDate | 만료일 − N일. 그 확인을 시작할 시점이지 마감이 아니다 |
| todos[].daysLeft | dueDate − 서울 오늘 (지났으면 음수) |

`daysLeft`·`stage`·`todos`는 DB에 저장하지 않고 요청 때마다 서울 오늘 기준으로 계산한다. 시점 숫자(120·30·7)와 문구는 서버의 `VisaMilestone` enum 한 곳에서만 바꾼다.

화면 표시: 화면은 `daysLeft`로 D-n / D-Day / D+n을 보여 주고, `stage`는 띠(색·강조) 판단용으로만 쓴다. 화면은 `todo.code === stage`인 할 일 줄을 "지금 확인할 때"로 강조한다.

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효한데 회원이 DB에 없음) |

### 25. 내 비자 일정 등록·덮어쓰기 `PUT /users/me/visa-plan`

로그인 필요, **학교 인증을 마친 회원만** 가능(인증 여부는 매번 DB로 확인). 일정이 없으면 만들고 있으면 새 값으로 덮어쓴다(회원당 1개). 같은 회원의 PUT이 동시에 와도 행은 1개이고 나중 값이 남는다.

요청 본문

```json
{ "expiryDate": "2026-12-31" }
```

| 필드 | 규칙 |
|------|------|
| expiryDate | 필수. `YYYY-MM-DD` 형식. **서울 기준 오늘 이상, 오늘+5년 이하**(오늘과 오늘+5년 정확히는 허용) |

날짜는 `YYYY-MM-DD` 문자열로 보낸다. 다만 배열(`[2026,12,31]`)이나 숫자(1970-01-01부터의 일수, 예: `20818` = 2026-12-31)로 보내도 날짜로 받아질 수 있다(알려진 한계, 나중에 후기 날짜와 함께 막을 예정). 숫자도 같은 범위 검사를 받으므로 `0`(1970-01-01)은 오늘 이전이라 400이다.

성공 응답 `200 OK`: 24번과 같은 모양(`expiryDate`·`daysLeft`·`stage`·`todos`). 저장한 만료일과 서울 오늘로 바로 계산한다.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400(빈 값·형식) → 학교 미인증 403 → 날짜 범위 400

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `expiryDate`가 없거나 null, 날짜 형식이 아님, 서울 오늘보다 이전, 서울 오늘+5년보다 이후 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음. 저장 직전 탈퇴가 커밋된 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 학교 인증을 안 한 회원 |

### 26. 내 비자 일정 삭제 `DELETE /users/me/visa-plan`

로그인 필요. 학교 인증은 필요 없다. 일정을 DB에서 지운다.

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

## 중고거래·나눔 (Market item)

물건 글 표(`market_items`)는 S13-a에서 만들었다. API는 올리기(27)·한 건 보기(28)·목록(29)·수정(30)·삭제(31)·상태 바꾸기(32)·사진 올리기(33)·사진 보기(34)·사진 지우기(35)다. 페이징은 아직 없다(제목 검색은 29번 `q`).

### 27. 물건 글 올리기 `POST /market-items`

로그인 필요, **학교 인증을 마친 회원만** 올릴 수 있다(관리자도 예외 없음). 글의 학교는 본문으로 받지 않고 **판매자가 인증한 학교가 자동으로 복사**되고, 상태는 항상 `ON_SALE`로 시작한다(`schoolId`·`status`·`sellerId` 같은 모르는 필드를 보내도 무시한다).

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 비어 있거나 공백뿐이면 400, 최대 100자, NUL 문자 불가 |
| content | O | 비어 있거나 공백뿐이면 400, 최대 2000자, NUL 문자 불가 |
| tradeType | O | `SALE`(판매), `FREE`(나눔) 중 하나. 그 밖의 문자열·숫자면 400 |
| price | 판매만 O | `SALE`: 1~10,000,000(원) 정수. 없거나 0 이하이거나 상한을 넘으면 400. `FREE`: 없거나 `null`이거나 0이면 0으로 저장, 1 이상(음수 포함)이면 400 |

요청 예시

```json
{ "title": "전공 서적 팝니다", "content": "거의 새 책이에요.", "tradeType": "SALE", "price": 15000 }
```

성공 응답 `201 Created` (헤더 `Location: /market-items/1`). 본문은 28번 단건 조회와 같다(방금 올렸으니 `photos`는 `[]`).

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 회원이 DB에 있는지(없으면 401) → 학교 미인증 403 → 가격 규칙 400 → 저장. (비자 후기와 같이 "누가 올릴 수 있나"를 먼저 보고 가격 규칙은 그 뒤에 본다.)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 제목·본문이 비었거나 길이 초과, NUL 포함, `tradeType` 없음·없는 값, JSON 형식 오류, 가격 규칙 위반(판매인데 가격 없음·0 이하·상한 초과, 나눔인데 가격 1 이상) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 저장 직전에 탈퇴해 저장되지 못함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함 |

### 28. 물건 글 한 건 보기 `GET /market-items/{id}`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`).

성공 응답 `200 OK`

```json
{
  "id": 1,
  "title": "전공 서적 팝니다",
  "content": "거의 새 책이에요.",
  "tradeType": { "code": "SALE", "name": "판매" },
  "price": 15000,
  "status": { "code": "ON_SALE", "name": "판매중" },
  "school": { "id": 1, "name": "경희대학교" },
  "seller": { "id": 1, "nickname": "길동이" },

    { "id": 7, "width": 1365, "height": 2048, "thumbWidth": 213, "thumbHeight": 320, "contentType": "image/jpeg" }
  ]

```

| 필드 | 설명 |
|------|------|
| tradeType | `{code, name}`: `SALE`(판매) / `FREE`(나눔) |
| price | 원 단위 정수. 나눔은 `0` |
| status | `{code, name}`: `ON_SALE`(판매중) / `RESERVED`(예약중) / `DONE`(거래완료). 올릴 때는 `ON_SALE`, 바꾸는 방법은 32번(수정 API 30번으로는 안 바뀐다). `DONE`이 되면 내용 수정 불가 |
| school | `{id, name}`. 올린 시점에 판매자가 인증한 학교 |
| seller | `{id, nickname}`. 판매자가 탈퇴하면 글도 지워지므로 항상 값이 있다 |
| createdAt | 올린 시각 (UTC) |
| photos | 올린 사진 목록(올린 순 = id 오름차순). 사진이 없으면 `[]`. 각 항목은 `{id, width, height, thumbWidth, thumbHeight, contentType}`이고 창고 이름(key)은 내보내지 않는다. 사진 올리기는 33번, 사진 파일 보기는 34번, 지우기는 35번 |

실패

| 상태코드 | 언제 |
|----------|------|
| 404 | 없는 id |
| 400 | id가 숫자가 아님 (예: `/market-items/abc`) |

회원 탈퇴(14번) 때 그 회원이 올린 물건 글은 DB가 함께 지운다(`ON DELETE CASCADE`). 판매자가 탈퇴하면 중고 글과 그 글에 달린 신고도 함께 삭제된다.

### 29. 물건 글 목록 `GET /market-items`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). 최신순(id 내림차순), 페이징 없음. 글이 없으면 빈 배열 `[]`. 본문(`content`)까지 포함해 28번 단건과 같은 모양의 배열을 돌려준다. 단, **목록 항목에는 `photos` 필드가 없다**(글마다 사진을 따로 읽는 비용을 피하려고. 대표 사진은 S13-g5에서 정한다).

쿼리 파라미터 (모두 선택, 넘긴 것만 AND 조건)

| 이름 | 설명 |
|------|------|
| `schoolId` | 그 학교의 글만 |
| `tradeType` | `SALE`(판매) / `FREE`(나눔) |
| `status` | `ON_SALE` / `RESERVED` / `DONE` |
| `q` | 제목 검색어. 제목만 보며(본문 제외), 대소문자를 가리지 않는 부분 일치. `%`·`_`·`\`는 와일드카드가 아니라 글자 그대로 찾는다. 앞뒤 공백은 무시하고, 비었거나 공백뿐이면 조건을 안 건 것과 같다. 앞뒤 공백을 뺀 길이가 50자(글자 기준)를 넘거나 NUL 문자가 있으면 400 |

- 파라미터 없이 부르면 전체. 값이 비어 있으면(`?status=`) 조건을 안 건 것과 같다.

- 예: `GET /market-items?schoolId=1&tradeType=SALE&status=ON_SALE`, `GET /market-items?q=자전거`

실패

| 상태코드 | 언제 |
|----------|------|
| 404 | 없는 학교 id (예: `?schoolId=999`) |
| 400 | `schoolId`가 숫자가 아님, 모르는 `tradeType`·`status` 값, 공백을 뺀 `q`가 50자 초과 또는 `q`에 NUL 문자 포함 (`q`의 400이 학교 404보다 먼저) |

### 30. 물건 글 수정 `PUT /market-items/{id}`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 수정할 수 없다). 학교 인증은 필요 없다. 요청 본문은 27번 올리기와 같은 필드·규칙(`title`, `content`, `tradeType`, `price`)이며 모두 새 값으로 바꾼다(일부만 바꾸는 PATCH는 없음). 상태·학교·판매자·`createdAt`은 바뀌지 않는다(`status`·`schoolId` 등 모르는 필드는 무시). **거래완료(`DONE`)된 글은 수정할 수 없다(409).** 상태는 32번으로만 바꾼다.

요청 예시: `PUT /market-items/1`

```json
{ "title": "전공 서적 팝니다 (가격 내림)", "content": "거의 새 책이에요.", "tradeType": "SALE", "price": 12000 }
```

성공 응답 `200 OK`: 수정된 글. 28번 응답과 같은 모양.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 가격 규칙 400 → 없는 id 404 → 본인 아님 403 → 거래완료 글 409 (비자 후기 수정과 같이 입력 오류가 먼저, 남의 글이어도 본문이 잘못되면 403이 아니라 400).

동시 요청: 수정은 "상태가 `DONE`이 아닐 때만" 바꾸는 조건부 UPDATE 한 문장이다. 수정하는 사이에 다른 요청이 `DONE`으로 바꿔 커밋하면 내용은 바뀌지 않고 409, 글이 지워졌으면 404다. 수정이 상태를 옛 값으로 되돌리는 일은 없다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 27번과 같은 본문 오류(필수 누락, 없는 `tradeType`, 길이 초과, NUL 문자, 가격 규칙 위반), id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 id, 또는 수정하는 사이에 글이 지워진 경우 |
| 409 | 거래완료(`DONE`)된 글 (수정하는 사이에 `DONE`이 된 경우 포함) |

### 31. 물건 글 삭제 `DELETE /market-items/{id}`

로그인 필요, 판매자 본인 또는 관리자만 가능. DB에서 글을 완전히 지운다(복구 불가). 이 글에 달린 신고도 함께 삭제된다. 학교 인증은 필요 없다.

요청 예시: `DELETE /market-items/1`

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 남의 글을 관리자 토큰으로 지우려는데 그 회원이 DB에 없는 경우도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |
| 404 | 없는 id (이미 삭제된 id 포함) |

### 32. 물건 글 상태 바꾸기 `PUT /market-items/{id}/status`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 바꿀 수 없다). 학교 인증은 필요 없다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| status | O | `ON_SALE` / `RESERVED` / `DONE` 중 하나. 없거나 `null`이거나 모르는 값이면 400 |

요청 예시: `PUT /market-items/1/status`

```json
{ "status": "RESERVED" }
```

성공 응답 `200 OK`: 상태가 바뀐 글. 28번 응답과 같은 모양(`photos` 포함).

허용하는 전환

| 지금 | 바꿀 수 있는 상태 |
|------|------------------|
| `ON_SALE` (판매중) | `RESERVED`, `DONE` |
| `RESERVED` (예약중) | `ON_SALE`, `DONE` |
| `DONE` (거래완료) | 없음 (한 번 완료되면 되돌릴 수 없다) |

위 표에 없는 전환과 **지금과 같은 상태로 바꾸기**는 409다.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 없는 id 404 → 본인 아님 403 → 전환 불가 409 (비자 후기와 같은 흐름).

동시 요청: "지금 상태가 읽은 값일 때만 바꾸는" 조건부 UPDATE 한 문장이다. 같은 글에 요청이 동시에 두 번 와도 하나만 200이고 나머지는 409, 그 사이 글이 지워졌으면 404다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 본문이 비었거나 JSON 형식 오류, `status`가 없음·`null`·모르는 값, id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 id, 또는 바꾸는 사이에 글이 지워진 경우 |
| 409 | 허용하지 않는 전환 (`DONE`에서 나가기, 지금과 같은 상태로 바꾸기), 또는 동시에 다른 요청이 먼저 상태를 바꾼 경우 |

### 33. 물건 글 사진 올리기 `POST /market-items/{id}/photos`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 403). 학교 인증은 필요 없다. 거래완료(`DONE`) 글에는 올릴 수 없다. 수정(30번)과 같은 규칙이다. 한 요청에 사진 1장, 글당 최대 10장.

요청: `multipart/form-data`, 파트 이름 `file` 한 개.

```
POST /market-items/1/photos
Content-Type: multipart/form-data; boundary=...
(파트 file: 사진 파일)
```

- JPEG·PNG만 받는다. 형식은 파일 이름·`Content-Type`이 아니라 파일 맨 앞 바이트(매직 바이트)로 판별한다. HEIC·WebP·GIF·가짜 파일은 400.
- 파일 하나 최대 10MB(요청 전체 11MB). 넘으면 413 (서버 설정 `spring.servlet.multipart.max-file-size`·`max-request-size`). 401·413처럼 본문을 읽지 않고 응답할 때도 연결이 끊기지 않도록 남은 본문 버리기 한도(`server.tomcat.max-swallow-size`)를 11MB로 맞췄다.
- 서버가 사진을 다시 만들어 저장한다: 긴 변 2048px로 줄이고, EXIF 회전을 반영하고, GPS 같은 메타데이터는 지운다. 320px 썸네일도 함께 저장한다. 형식은 유지(JPEG는 JPEG, PNG는 PNG).
- 픽셀 상한: 긴 변 10,000px 초과 또는 총 4천만 픽셀 초과는 400.

성공 응답 `201 Created` (헤더 `Location: /market-items/1/photos/7` — 사진 한 장 보기 주소이며 34번 GET으로 열린다)

```json
{ "id": 7, "width": 1365, "height": 2048, "thumbWidth": 213, "thumbHeight": 320, "contentType": "image/jpeg" }
```

| 필드 | 설명 |
|------|------|
| id | 사진 id |
| width·height | 저장된 본 사진 크기(px, 줄이고 회전한 뒤 값) |
| thumbWidth·thumbHeight | 썸네일 크기(px, 긴 변 최대 320) |
| contentType | `image/jpeg` 또는 `image/png` |

검사 순서: CSRF 403 → 로그인 401 → 파일 없음·빈 파일 400 → 없는 글 404 → 본인 아님 403 → 거래완료 409 → 이미 10장 409 → 사진 검사 400(형식·깨짐·크기) → (저장 직전 글을 잠그고 다시 확인) 글이 사라짐 404, 거래완료 409, 이미 10장 409.
앞쪽 10장 검사는 무거운 처리를 헛하지 않으려는 미리보기이고, 잠금 안의 검사가 최종이다.
이미지 처리는 서버 전체에서 동시에 2장까지만 한다. 자리가 날 때까지 최대 5초 기다리고, 그래도 안 나면 503. 파일 내용은 자리를 얻은 뒤에 읽는다.
저장 과정(파일 저장 → DB 기록) 중 하나라도 실패하면 방금 저장한 파일 2개는 지운다. 같은 글에 동시에 올려도 글 행을 잠그고 사진 수를 세므로 10장을 넘지 않는다(9장일 때 동시 2장이면 하나만 성공, 나머지 409).
글을 지우거나 판매자가 탈퇴하면 사진 행도 DB가 함께 지운다(`ON DELETE CASCADE`). 글 삭제·탈퇴 때의 창고 파일 정리는 S13-g4에서 한다. 사진 한 장만 지우기는 35번.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `file` 파트가 없음, 빈 파일, JPEG·PNG가 아님(가짜 파일 포함), 깨진 파일, 픽셀 수 초과, id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 id, 또는 처리하는 사이에 글이 지워진 경우 |
| 409 | 거래완료 글, 또는 이미 사진이 10장 |
| 413 | 파일이 10MB 초과, 또는 요청 전체가 11MB 초과 |
| 415 | `multipart/form-data`가 아닌 요청 |
| 500 | 서버가 받아 둔 업로드 임시 파일을 읽지 못함, 또는 창고 저장 실패(저장한 파일은 치운다) |
| 503 | 이미지 처리 자리가 5초 안에 나지 않음(잠시 뒤 다시 시도) |

### 34. 물건 글 사진 보기 `GET /market-items/{id}/photos/{photoId}`

로그인 없이 볼 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). 이 한 주소의 GET만 공개이고, 올리기(POST)·지우기(DELETE)는 로그인이 필요하다. `/market-items/{id}/photos` 자체의 GET은 없다(사진 목록은 28번 단건 응답의 `photos`).

요청 예시

```
GET /market-items/1/photos/7              (본 사진)
GET /market-items/1/photos/7?size=thumb   (썸네일)
```

| 쿼리 | 설명 |
|------|------|
| size | 없음 = 본 사진, `thumb` = 썸네일(긴 변 최대 320px). 그 밖의 값(빈 값 `size=`·`THUMB` 포함)은 400 |

성공 응답 `200 OK`, 본문은 사진 파일 바이트(JSON 아님)

| 응답 헤더 | 값 |
|-----------|-----|
| Content-Type | 사진을 올릴 때 DB에 적어 둔 `image/jpeg` 또는 `image/png` (파일 내용에서 추측하지 않음) |
| Content-Length | 본문 바이트 수 |
| Cache-Control | `public, max-age=31536000, immutable` — 사진 id의 그림은 한 번 올리면 바뀌지 않아서 1년 저장해도 된다 |
| X-Content-Type-Options | `nosniff` |

검사 순서: `size` 값 400 → 사진 번호와 글 번호가 둘 다 맞는 사진이 없음 404 → 장부(DB)에는 있는데 창고에 파일이 없음 404.
다른 글의 사진 번호로 요청하면 404다(그 사진이 보이지 않는다). 존재하지 않는 글과 존재하지 않는 사진은 구분하지 않고 같은 404다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `size`가 비었거나 `thumb`가 아님, 글 id·사진 id가 숫자가 아님 |
| 404 | 없는 글·없는 사진·다른 글의 사진, 또는 창고에 파일이 없음 |
| 500 | 창고에서 파일을 읽다 오류(디스크·S3 오류 등) |

### 35. 물건 글 사진 지우기 `DELETE /market-items/{id}/photos/{photoId}`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 403). 학교 인증은 필요 없다. 거래완료(`DONE`) 글의 사진은 지울 수 없다. 33번(올리기)과 같은 규칙이다.

요청 예시: `DELETE /market-items/1/photos/7`

성공 응답 `204 No Content` (본문 없음)

검사 순서: CSRF 403 → 로그인 401 → 없는 글 404 → 본인 아님 403 → 거래완료 409 → 이 글의 사진이 아님(없는 사진·다른 글의 사진·이미 지운 사진) 404 → 장부(DB) 행 삭제.
글 행을 잠그고(`FOR UPDATE`) 확인하므로 같은 글의 거래완료 전환·사진 올리기와 줄을 서서 처리된다.
DB 삭제가 커밋된 **뒤에** 창고 파일 2개(본 사진·썸네일)를 지운다. 파일 지우기가 실패해도 이미 장부에서 지웠으므로 응답은 그대로 204이고 실패는 서버 로그에만 남는다(남은 파일은 S13-g4의 청소가 맡는다).
지운 뒤 34번 보기는 404, 28번 단건의 `photos`에서도 빠진다(나머지 사진의 순서는 그대로).

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 글 id·사진 id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 글, 이 글의 사진이 아님(없는 사진·다른 글의 사진·이미 지운 사진) |
| 409 | 거래완료 글 |
