# API 명세

게시판 API 목록. 새 API를 만들거나 바꾸면 이 문서에 이어서 적는다.
에러 응답 본문은 Spring 기본 형식을 쓰고, 상태코드가 중요하다.
브라우저(프론트엔드) 허용 주소는 환경변수 `CORS_ALLOWED_ORIGINS`로 설정한다(기본값 `http://localhost:5173`, 쉼표로 여러 개).
허용되지 않은 주소에서 브라우저로 요청하면 403이 반환된다 (curl 등 브라우저가 아닌 요청은 CORS 대상이 아님).

배포 환경(EC2)에서는 nginx를 거치므로 API가 `/api` 아래에 있다 (예: `/api/posts`, `/api/posts/1`). nginx가 `/api`를 떼고 백엔드에 전달하므로 이 문서의 URL 자체는 그대로다.
헬스체크는 `/actuator/health` 그대로 쓴다 (`/api` 없음). 로컬 브라우저도 Flutter 개발 서버 프록시(`flutter_app/web_dev_config.yaml`)로 `/api`를 쓴다(`refresh_token` 쿠키 Path=`/api/auth`가 붙으려면 필요). curl 등은 `http://localhost:8080`에 직접 요청해도 된다.
글 작성 응답의 `Location` 헤더는 백엔드 기준(`/posts/{id}`)이며 nginx가 바꾸지 않는다. 배포 환경에서 API로 따라가려면 앞에 `/api`를 붙인다 (현재 프론트는 `Location`을 사용하지 않음).

## CSRF 보호 (모든 POST/PUT/DELETE 공통)

S4-a부터 Spring Security가 켜져 있어서, **POST/PUT/DELETE는 `X-XSRF-TOKEN` 헤더가 없으면 `403`** 이다 (GET은 필요 없음).
1. 앱 시작 시 `GET /csrf`를 한 번 호출하면 `XSRF-TOKEN` 쿠키가 설정된다.
2. 이후 POST/PUT/DELETE마다 그 쿠키 값을 `X-XSRF-TOKEN` 헤더에 실어 보낸다 (axios는 같은 주소 요청에서 자동으로 해 준다). 안드로이드 앱은 브라우저가 없어서 쿠키 보관함(cookie_jar)이 쿠키 저장·전송을 대신하고, 앱 코드가 보관한 `XSRF-TOKEN` 쿠키 값을 같은 헤더에 옮겨 싣는다.

서버는 세션(`JSESSIONID`)을 만들지 않는다. 로그인이 필요한 경로는 인증 없이 부르면 `401`이다 (허용 목록 밖의 없는 경로도 404가 아니라 401).
글 API는 **목록·단건 조회(GET)만 로그인 없이** 쓸 수 있다. 작성·수정·삭제(POST/PUT/DELETE)는 로그인(`access_token` 쿠키)이 필요하고, 토큰이 없거나 만료·변조되면 `401`이다.
조회(GET)는 만료되거나 변조된 `access_token` 쿠키가 붙어 와도 정상(200)이다.
수정은 **본인이 쓴 글만** 가능하다. 남의 글, 그리고 작성자가 없는 글(S4-d 이전에 쓴 글)은 관리자도 `403`이다.
삭제는 **본인 또는 관리자**가 할 수 있다(관리자는 작성자가 없는 글도 지울 수 있다). 남의 글을 일반 회원이 지우면 `403`이다.
관리자 확인: 토큰의 `role`이 `ADMIN`이면 서버가 DB에서 회원을 다시 읽는다(회원이 없으면 `401`, DB의 role이 `USER`면 `403`). 토큰은 최대 15분 묵을 수 있어서다. 관리자 지정은 API가 없고 DB에서 직접 한다(`UPDATE users SET role = 'ADMIN' WHERE username = '...'`). 가입으로는 만들 수 없다.
쓰기 요청은 아래 순서로 검사하고 먼저 걸리는 오류를 돌려준다: CSRF 403 → 로그인 안 됨 401 → 본문 검증 400 → 없는 글 404 → 본인 글 아님 403.
단, 관리자 토큰의 회원 재확인(401·403)은 글·댓글이 있는지 확인(404)한 다음에 한다.

### 학교 인증 규칙 (S10-d, 글쓰기·댓글·공감·신고 공통)
학교 인증을 안 한 회원은 **읽기만** 가능하다. 아래 "만들기"(글쓰기·댓글·공감·신고, 그리고 비자 후기 작성·비자 일정 등록 `PUT /users/me/visa-plan`·물건 글 올리기 `POST /market-items`·판매자에게 쪽지 보내기 `POST /market-items/{id}/conversations`·대화에 답장 `POST /conversations/{id}/messages`)는 학교 인증(`verifiedSchool`)을 마친 회원이, **인증한 학교의 글에만** 할 수 있다(관리자도 예외 없음).
- 글쓰기 `POST /posts`: 본문의 `schoolId`가 인증한 학교와 같아야 한다.
- 댓글 작성, 공감 누르기, 글·댓글 신고: 대상 글(댓글이면 그 댓글의 글)의 학교가 인증한 학교와 같아야 한다. 학교가 없는 옛 글에는 아무도 할 수 없다(읽기만). 중고 글 신고도 중고 글의 학교가 인증한 학교와 같아야 한다.
- 대화 신고 `POST /conversations/{id}/reports`(42)도 답장과 같다: 미인증 `403`만 있고 "다른 학교 403"은 없다(참가자가 아니거나 없는 방은 `404`).
- 대화 답장 `POST /conversations/{id}/messages`: 학교 인증이 필요한 "만들기"지만, 미인증 `403`만 있고 "다른 학교 403"은 없다(이미 있는 대화에 이어 쓰는 것이라 참가자인지만 본다. 참가자가 아니거나 없는 방은 `404`).
- 비자 후기 작성 `POST /visa-reviews`: 인증한 학교가 후기의 학교로 자동 복사된다. 학교를 본문으로 받지 않아 "다른 학교 403"은 없고 미인증만 403이다. (검사 순서: CSRF 403 → 로그인 401 → 본문 400 → 회원 없음 401 → 미인증 403 → 날짜 400)
- 실패는 모두 `403`이다(`401`은 프론트가 토큰 재발급을 돌리므로 쓰지 않는다). 미인증과 다른 학교(학교 없는 글 포함) 모두 403이며 응답 본문으로는 구분할 수 없다. 화면은 `/auth/me` 등 회원 응답의 `verifiedSchool`과 글의 학교를 비교해 먼저 막는다. CSRF 실패도 403이다.
- 인증 여부는 토큰이 아니라 매번 DB로 확인한다(인증 직후 토큰 재발급 없이 바로 반영).
- 검사 순서: CSRF 403 → 로그인 401 → 본문 400 → 회원이 DB에 있는지(없으면 401) → 미인증 403 → (글쓰기: 없는 학교 400) / (그 외: 없는 글·댓글 404) → 다른 학교 403 → (그 뒤의 자기 것 400·중복 409).
- 인증과 무관한 것: 글·댓글·비자 후기·물건 글 수정·삭제(본인·관리자 규칙 그대로), 비자 일정 조회·삭제, 공감 취소, 모든 GET, 관리자 신고 API, 회원 API, 허가서 인증 신청 API(44~46), 관리자 허가서 심사 API(47~50).
- 사이트는 외국인 유학생 인증으로 바뀌었다(S20, 2026-11-17 운영 배포). 표준입학허가서 인증(44~46번)을 관리자가 승인(49번)하거나 서버가 자동 승인(44번, S20-d2)하면 같은 `verifiedSchool` 칸(과 `verifiedAt`)에 학교가 들어가므로 위 규칙은 그대로 적용된다. 승인 전 회원은 기존처럼 403이다. 허가서 승인은 `school_email_hash` 칸(예전 메일 인증 S10 회원의 칸, S20-f에서 메일 인증을 없앴다)을 건드리지 않는다(NULL 그대로). 학교 메일 인증 API(15·16번)는 S20-f에서 삭제됐다.

## 게시글 (Post)

| 기능 | 메서드 | URL | 성공 | 실패 |
|------|--------|-----|------|------|
| 작성 | POST | `/posts` | 201 | 400, 401, 403 |
| 단건 조회 | GET | `/posts/{id}` | 200 | 404, 400 |
| 목록 조회 | GET | `/posts` | 200 | 400, 404 |
| 수정 | PUT | `/posts/{id}` | 200 | 400, 401, 403, 404 |
| 삭제 | DELETE | `/posts/{id}` | 204 | 400, 401, 403, 404 |

### 응답 필드

| 필드 | 타입 | 설명 |
|------|------|------|
| id | 숫자 | 게시글 번호 |
| title | 문자열 | 제목 |
| content | 문자열 | 본문 |
| createdAt | 문자열 | 작성 시각 (예: `2026-11-01T01:30:00.123456Z`) |
| author | 객체 또는 null | 글쓴이 `{ "id": 숫자, "nickname": 문자열 }`. 로그인 아이디(username)는 숨긴다. 작성자가 없는 글(S4-d 이전에 쓴 글)은 `null` |
| school | 객체 또는 null | 학교 `{ "id": 숫자, "name": 문자열 }`. 학교가 없는 글(S7-a 이전에 쓴 글)은 `null` |
| category | 객체 | 말머리 `{ "code": 문자열, "name": 문자열 }` (예: `{ "code": "CHAT", "name": "잡담" }`). S7-a 이전에 쓴 글은 `CHAT` |
| commentCount | 숫자 | 댓글 수. 조회할 때 센다 (S8-b). 없으면 0 |
| likeCount | 숫자 | 공감 수. 조회할 때 센다 (S8-b). 없으면 0 |

말머리 코드는 `CHAT`(잡담), `QUESTION`(질문), `CAMPUS_LIFE`(학교생활) 세 가지다.

`commentCount`·`likeCount`는 표에 칸을 두지 않고 조회할 때 센다. 단건 조회는 쿼리 3번(글·댓글 수·공감 수), 목록은 글 수와 상관없이 3번 고정(글 1 + 댓글 수 group by 1 + 공감 수 group by 1). 작성(POST) 응답은 항상 `0`·`0`, 수정(PUT) 응답은 현재 값이다. 내가 공감했는지는 여기 담지 않고 로그인 전용 `GET /posts/{id}/likes/me`로 따로 확인한다.

시간대: UTC(Z). 소수점 자릿수는 가변(최대 6자리). 화면에 보여줄 때 한국 시간으로 변환한다.

### 1. 게시글 작성 `POST /posts`

로그인 필요. 글쓴이는 로그인한 사용자로 정해지며, 요청 본문에 `author`·`authorId` 같은 값을 보내도 무시한다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 공백만 있으면 안 됨, 최대 100자, NUL 문자 불가 |
| content | O | 공백만 있으면 안 됨, 길이 제한 없음, NUL 문자 불가 |
| schoolId | O | `GET /schools`에 있는 학교 id. 없는 id면 400 |
| category | O | `CHAT`, `QUESTION`, `CAMPUS_LIFE` 중 하나. 그 밖의 문자열이면 400 |

요청 예시

```json
{
  "title": "첫 글",
  "content": "안녕하세요",
  "schoolId": 1,
  "category": "CHAT"
}
```

성공 응답 `201 Created` (헤더 `Location: /posts/1`)

```json
{
  "id": 1,
  "title": "첫 글",
  "content": "안녕하세요",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  },
  "school": {
    "id": 1,
    "name": "경희대학교"
  },
  "category": {
    "code": "CHAT",
    "name": "잡담"
  },
  "commentCount": 0,
  "likeCount": 0
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | title/content가 비었거나 공백만 있음, title이 100자 초과, NUL 문자 포함, schoolId·category가 없음, 없는 학교 id, 없는 말머리 코드, JSON 형식이 잘못됨, category를 숫자로 보냄(예: `0`도 400) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효하지만 그 사용자가 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, `schoolId`가 인증한 학교와 다름 (위 "학교 인증 규칙") |

### 3. 게시글 목록 조회 `GET /posts`

최신순(id 내림차순)으로 돌려준다. 페이징 없음. 글이 없으면 빈 배열 `[]`. 로그인 없이 호출 가능. (아래 예시의 두 번째 글처럼 작성자·학교가 없는 옛 글은 `author`·`school`이 `null`이고 `category`는 `CHAT`)

쿼리 파라미터 (둘 다 선택, 같이 주면 두 조건을 모두 만족하는 글만)

| 이름 | 설명 |
|------|------|
| `schoolId` | 그 학교 글만. 학교 없는 옛 글은 포함되지 않는다 |
| `category` | 그 말머리 글만 (`CHAT`, `QUESTION`, `CAMPUS_LIFE`) |

- 파라미터 없이 부르면 학교 없는 옛 글까지 전체를 돌려준다.
- 값이 비어 있으면(`?schoolId=&category=`) 조건을 안 건 것과 같다.
- 존재하는 학교인데 글이 없으면 `200`과 `[]`.
- 예: `GET /posts?schoolId=1`, `GET /posts?category=QUESTION`, `GET /posts?schoolId=1&category=QUESTION`

| 상태코드 | 언제 |

### 4. 게시글 수정 `PUT /posts/{id}`

로그인 필요, 본인이 쓴 글만 가능. 제목·본문·말머리를 모두 새 값으로 바꾼다 (일부만 바꾸는 PATCH는 없음). `createdAt`은 바뀌지 않는다.
**학교는 바꿀 수 없다.** 요청 본문에 `schoolId`를 보내도 무시한다(에러 아님).

요청 본문 (title·content는 작성과 같은 규칙, 셋 다 필수)

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 공백만 있으면 안 됨, 최대 100자, NUL 문자 불가 |
| content | O | 공백만 있으면 안 됨, 길이 제한 없음, NUL 문자 불가 |
| category | O | `CHAT`, `QUESTION`, `CAMPUS_LIFE` 중 하나. 그 밖의 문자열이면 400 |

요청 예시: `PUT /posts/1`

```json
{
  "title": "수정한 제목",
  "content": "수정한 내용",
  "category": "QUESTION"
}
```

성공 응답 `200 OK`

```json
{
  "id": 1,
  "title": "수정한 제목",
  "content": "수정한 내용",
  "createdAt": "2026-11-01T01:30:00.123456Z",
  "author": {
    "id": 1,
    "nickname": "길동이"
  },
  "school": {
    "id": 1,
    "name": "경희대학교"
  },
  "category": {
    "code": "QUESTION",
    "name": "질문"
  },
  "commentCount": 0,
  "likeCount": 0
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | title/content가 비었거나 공백만 있음, title이 100자 초과, NUL 문자 포함, category가 없거나 없는 말머리 코드, JSON 형식이 잘못됨, category를 숫자로 보내도 400, id가 숫자가 아님 (남의 글이어도 본문이 잘못되면 403이 아니라 400) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id·숫자 아닌 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (작성자가 없는 글 포함, 관리자도 수정할 수 없음) |
| 404 | 없는 id (예: `/posts/999`) |

검사 순서: 400(본문) → 404 → 403. 즉 본문이 올바르고 글이 있어야 본인 글인지 확인한다.

### 5. 게시글 삭제 `DELETE /posts/{id}`

로그인 필요, 본인 또는 관리자만 가능. DB에서 글을 완전히 지운다 (복구 불가). 그 글의 댓글·공감·신고(글과 댓글에 달린 신고 모두)도 함께 삭제된다.

요청 예시: `DELETE /posts/1`

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 (예: `/posts/abc`) |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id·숫자 아닌 id도 401. 남의 글을 관리자 토큰으로 지우려는데 그 회원이 DB에 없는 경우도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |
| 404 | 없는 id (이미 삭제된 id 포함). 본인과 관리자가 동시에 지우면 늦은 쪽이 404 |

## 학교·말머리 (School, Category)

글을 쓸 때 고를 선택지 목록. 둘 다 로그인 없이 호출 가능하고, 만료되거나 변조된 `access_token` 쿠키가 붙어 와도 200이다.

### 5-1. 학교 목록 `GET /schools`

학교를 이름순으로 돌려준다. 캠퍼스 구분은 없다. 학교는 DB 마이그레이션으로 넣어 두며(경희대·고려대·성균관대·연세대·한양대) 추가·수정 API는 없다.

성공 응답 `200 OK`

```json
[
  { "id": 1, "name": "경희대학교" },
  { "id": 3, "name": "성균관대학교" }
]
```

각 항목은 `id`, `name`만 갖는다(이름순). 예전에 있던 `emailDomains`(학교 메일 도메인)는 S20-f에서 메일 인증과 함께 없어졌다. 글 응답의 `school`도 같은 모양이다.

### 5-2. 말머리 목록 `GET /categories`

성공 응답 `200 OK`

```json
[
  { "code": "CHAT", "name": "잡담" },
  { "code": "QUESTION", "name": "질문" },
  { "code": "CAMPUS_LIFE", "name": "학교생활" }
]
```

`code`를 글 작성·수정 요청의 `category`에 보낸다.

## 댓글 (Comment)

글에 다는 평댓글(대댓글 없음). 목록 조회(GET)만 로그인 없이 쓸 수 있고(만료·변조된 `access_token` 쿠키가 붙어 와도 200), 작성·수정·삭제는 로그인과 CSRF 헤더가 필요하다.
쓰기 검사 순서는 글과 같다: CSRF 403 → 로그인 401 → 본문 400 → 없는 글·댓글 404 → 본인 댓글 아님 403. 작성(POST)만 그 사이에 학교 인증 403(미인증 → 없는 글 404 → 다른 학교 글 403)이 들어간다("학교 인증 규칙" 참고).
단, 토큰은 유효하지만 회원이 DB에 없고 본문도 잘못된 경우에는 400이 먼저 나온다.

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 목록 | GET | `/posts/{postId}/comments` | 공개 | 200 | 400, 404 |
| 작성 | POST | `/posts/{postId}/comments` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404 |
| 수정 | PUT | `/comments/{id}` | 본인 | 200 | 400, 401, 403, 404 |
| 삭제 | DELETE | `/comments/{id}` | 본인·관리자 | 204 | 400, 401, 403, 404 |

### 응답 필드 (CommentResponse)

| 필드 | 타입 | 설명 |
|------|------|------|
| id | 숫자 | 댓글 번호 |
| postId | 숫자 | 댓글이 달린 글 번호 |
| content | 문자열 | 내용 |
| createdAt | 문자열 | 작성 시각 (글과 같은 UTC 형식) |
| author | 객체 또는 null | 댓글쓴이 `{ "id": 숫자, "nickname": 문자열 }`. 작성자가 탈퇴했으면 `null` |

### 5-3. 댓글 목록 `GET /posts/{postId}/comments`

id 오름차순(오래된 댓글이 먼저). 페이징 없음. 댓글이 없으면 `[]`.

```json
[
  {
    "id": 1,
    "postId": 3,
    "content": "첫 댓글",
    "createdAt": "2026-11-07T01:30:00.123456Z",
    "author": { "id": 1, "nickname": "길동이" }
  }
]
```

실패: 400(postId가 숫자가 아님), 404(없는 글)

### 5-4. 댓글 작성 `POST /posts/{postId}/comments`

작성자는 로그인한 사용자로 정해진다(본문에 `author`를 보내도 무시).

요청 본문: `{ "content": "첫 댓글" }`

| 필드 | 필수 | 규칙 |
|------|------|------|
| content | O | 공백만 있으면 안 됨, 1~1000자, NUL 문자 불가 |

성공 응답 `201 Created` (헤더 `Location: /comments/1`) + 위 CommentResponse 한 건

| 상태코드 | 언제 |
|----------|------|
| 400 | content가 비었거나 공백만 있음, 1000자 초과, NUL 문자 포함, JSON 형식이 잘못됨, postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 작성 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 글이 인증한 학교의 글이 아님(학교 없는 글 포함) |
| 404 | 없는 글 (작성 도중 글이 삭제된 경우 포함) |

### 5-5. 댓글 수정 `PUT /comments/{id}`

내용만 새 값으로 바꾼다(작성 시각·작성자는 그대로). 본문 규칙은 작성과 같다. 성공 시 `200 OK` + CommentResponse.

| 상태코드 | 언제 |
|----------|------|
| 400 | content 규칙 위반, JSON 형식이 잘못됨, id가 숫자가 아님 (남의 댓글이어도 본문이 잘못되면 403이 아니라 400) |
| 401 | 로그인 안 됨 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 댓글이 아님 (작성자가 없는 댓글 포함) |
| 404 | 없는 댓글 |

### 5-6. 댓글 삭제 `DELETE /comments/{id}`

본인 또는 관리자만 가능(관리자는 작성자 없는 댓글도 가능). DB에서 댓글을 완전히 지운다. 이 댓글에 달린 신고도 함께 삭제된다. 성공 시 `204 No Content`.

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 |
| 401 | 로그인 안 됨 (남의 댓글을 관리자 토큰으로 지우려는데 그 회원이 DB에 없는 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 댓글이 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |
| 404 | 없는 댓글 (이미 삭제된 id 포함). 본인과 관리자가 동시에 지우면 늦은 쪽이 404 |

## 공감 (Like)

글에만 누를 수 있다(댓글 공감 없음). 한 회원이 한 글에 한 번만, 취소할 수 있다. 개수는 글 응답의 `likeCount`로 공개되고(비로그인도 봄), 아래 3개는 모두 로그인이 필요하다(공개 경로 아님).
쓰기 검사 순서: CSRF 403 -> 로그인 401 -> (누르기만) 미인증 403 -> 없는 글 404 -> (누르기만) 다른 학교 글 403 -> 상태 충돌 409. 학교 인증은 "학교 인증 규칙" 참고.
공감은 본문이 없어서 @Valid 검사가 없다. 토큰은 유효하지만 회원이 DB에 없으면 바로 401이고, 경로의 postId가 숫자가 아니면 그 전에 400이 먼저 나온다.

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 공감 | POST | `/posts/{postId}/likes` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 공감 취소 | DELETE | `/posts/{postId}/likes` | 로그인 | 200 | 400, 401, 403, 404 |
| 내가 공감했는지 | GET | `/posts/{postId}/likes/me` | 로그인 | 200 | 400, 401, 404 |

### 5-7. 공감 `POST /posts/{postId}/likes`

요청 본문 없음. 성공 응답 `201 Created`: 처리 후 개수를 다시 센 값.

```json
{ "likeCount": 1, "liked": true }
```

| 상태코드 | 언제 |
|----------|------|
| 400 | postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 누르는 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 글이 인증한 학교의 글이 아님(학교 없는 글 포함) |
| 404 | 없는 글 (누르는 도중 글이 삭제된 경우 포함) |
| 409 | 이미 공감한 글. 같은 회원이 동시에 여러 번 눌러도 한 번만 성공하고 나머지는 409 |

### 5-8. 공감 취소 `DELETE /posts/{postId}/likes`

성공 응답 `200 OK`: 처리 후 개수.

```json
{ "likeCount": 0, "liked": false }
```

| 상태코드 | 언제 |
|----------|------|
| 400 | postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 404 | 없는 글, 또는 내가 공감하지 않은 글 |

### 5-9. 내가 공감했는지 `GET /posts/{postId}/likes/me`

성공 응답 `200 OK`

```json
{ "liked": true }
```

| 상태코드 | 언제 |
|----------|------|
| 400 | postId가 숫자가 아님 |
| 401 | 로그인 안 됨 (공개 경로가 아니므로 쿠키가 없거나 만료·변조면 401, 토큰은 유효하지만 회원이 DB에 없는 경우도 401) |
| 404 | 없는 글 |


탈퇴하면 그 회원의 공감은 DB가 함께 지운다(`likeCount`가 1 줄어든다). 글을 지우면 그 글의 공감도 함께 지워진다.

## 신고 (Report)

회원이 글·댓글·중고 글·쪽지 대화방을 신고한다. 신고 사유 목록(GET)만 로그인 없이 쓸 수 있고(만료·변조된 `access_token` 쿠키가 붙어 와도 200), 신고하기는 로그인과 CSRF 헤더가 필요하다.
관리자의 신고 목록·기각은 아래 "관리자(Admin)" 절. 일반 회원이 신고를 조회·취소하는 API는 없다.
검사 순서: CSRF 403 -> 로그인 401 -> 본문 400 -> 회원이 DB에 있는지(없으면 401) -> 미인증 403 -> 없는 대상 404 -> 다른 학교 글 403 -> 자기 글·댓글·중고 글 400 -> 중복 409. ("학교 인증 규칙" 참고)

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 사유 목록 | GET | `/report-reasons` | 공개 | 200 | - |
| 글 신고 | POST | `/posts/{postId}/reports` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 댓글 신고 | POST | `/comments/{id}/reports` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 중고 글 신고 | POST | `/market-items/{id}/reports` | 학교 인증(같은 학교 글) | 201 | 400, 401, 403, 404, 409 |
| 대화 신고 | POST | `/conversations/{id}/reports` | 학교 인증(대화 참가자만, 같은 학교 검사 없음) | 201 | 400, 401, 403, 404, 409 |

### 5-10. 신고 사유 목록 `GET /report-reasons`

성공 응답 `200 OK`

```json
[
  { "code": "SPAM", "name": "광고·스팸" },
  { "code": "ABUSE", "name": "욕설·비방" },
  { "code": "SEXUAL", "name": "음란·선정적" },
  { "code": "PRIVACY", "name": "개인정보 노출" },
  { "code": "OTHER", "name": "기타" }
]
```

`code`를 신고 요청의 `reason`에 보낸다.

### 5-11. 글 신고 `POST /posts/{postId}/reports`, 5-12. 댓글 신고 `POST /comments/{id}/reports`, 중고 글 신고 `POST /market-items/{id}/reports`

신고자는 로그인한 사용자로 정해진다(본문에 보내도 무시). 한 회원은 같은 글(댓글·중고 글)을 한 번만 신고할 수 있다. 자기 글·자기 댓글·자기 중고 글은 신고할 수 없다(중고 글이면 400 "자기 중고 글은 신고할 수 없습니다."). 중고 글 신고(S13-e)도 글 신고와 같은 규칙·검사 순서·응답이고, 응답의 `target`만 `{ "type": "MARKET_ITEM", "id": 5, "postId": null }`이다.

요청 본문: `{ "reason": "SPAM", "detail": "광고예요" }`

| 필드 | 필수 | 규칙 |
|------|------|------|
| reason | O | 사유 목록의 `code` 중 하나 |
| detail | X | 최대 300자, NUL 문자 불가. `OTHER`여도 선택. 없거나 빈 문자열·공백뿐이면 `null`로 저장 |

성공 응답 `201 Created`. 신고 한 건을 따로 조회하는 API가 없어서 `Location` 헤더는 없다.

```json
{
  "id": 1,
  "target": { "type": "POST", "id": 3, "postId": 3 },
  "reason": { "code": "SPAM", "name": "광고·스팸" },
  "detail": "광고예요",
  "status": "PENDING",
  "createdAt": "2026-11-08T03:00:00.123456Z"
}
```

- `target.type`은 `POST`·`COMMENT`·`MARKET_ITEM`·`CONVERSATION`, `target.id`는 신고된 글(댓글·중고 글·대화방)의 id, `target.postId`는 그 글의 id(글 신고면 `id`와 같다, 중고 글·대화방 신고면 `null`). 대화 신고(`POST /conversations/{id}/reports`)는 쪽지 절 42번.
- `status`는 새 신고면 항상 `PENDING`(처리 대기). 기각되면 `DISMISSED`.

| 상태코드 | 언제 |
|----------|------|
| 400 | reason이 없거나 사유 목록에 없음, detail 300자 초과, detail에 NUL 문자 포함, JSON 형식이 잘못됨, reason을 숫자로 보냄(예: `0`도 400), id가 숫자가 아님, 자기 글·자기 댓글·자기 중고 글을 신고함 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 신고 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 대상 글(댓글이면 그 댓글의 글)이 인증한 학교의 글이 아님(학교 없는 글 포함) |
| 404 | 없는 글·댓글·중고 글 (신고 도중 삭제된 경우 포함) |
| 409 | 이미 신고한 대상. 같은 회원이 동시에 여러 번 보내도 한 번만 성공하고 나머지는 409 |

신고는 대상이 지워지면 함께 지워진다(글을 지우면 그 글의 댓글과, 글·댓글에 달린 신고도 모두 삭제. 중고 글을 지우면 그 글의 신고도 삭제). 신고자가 탈퇴해도 신고는 남고 신고자만 없어진다.

## 관리자 (Admin)

신고 목록 보기와 기각은 관리자만 쓸 수 있다. 신고된 글·댓글·중고 글을 지우는 건 새 API 없이 기존 `DELETE /posts/{id}`, `DELETE /comments/{id}`, `DELETE /market-items/{id}`를 관리자 계정으로 부른다. 화면은 S9-d. **대화 신고(`CONVERSATION`)에는 삭제 처리가 없다**: 목록에서 보고, 신고된 대화를 읽고(5-15), 기각만 할 수 있다.

### 접근 규칙 (`/admin/**` 공통)

| 상황 | 결과 |
|------|------|
| 로그인 안 됨 (쿠키 없음, 토큰 만료·변조) | 401 |
| 토큰의 `role`이 `ADMIN`이 아님 (`USER`, `role` 클레임이 없는 옛 토큰, 모르는 값 포함) | 403 |
| 토큰은 `ADMIN`인데 회원이 DB에 없음 (탈퇴) | 401 |
| 토큰은 `ADMIN`인데 DB의 role은 `USER` (강등됨) | 403 |

- 토큰의 `role`은 최대 15분(액세스 토큰 수명) 묵을 수 있다. 관리자로 지정한 뒤에는 **다시 로그인하거나 토큰이 재발급(`POST /auth/refresh`)돼야** 새 role이 토큰에 반영된다. 반대로 강등·탈퇴는 서버가 매번 DB로 다시 확인하므로 바로 막힌다.
- 관리자 지정은 API가 없고 DB에서 직접 한다 (위 "CSRF 보호" 절 아래 설명 참고).
- 검사 순서: CSRF 403(PUT) → 로그인 401 → 토큰 role 403 → 파라미터 400 → DB 재확인 401/403 → 없는 신고 404 → 이미 기각 409. GET은 CSRF 헤더가 필요 없고, PUT은 `X-XSRF-TOKEN` 헤더가 필요하다.

| 기능 | 메서드 | URL | 권한 | 성공 | 실패 |
|------|--------|-----|------|------|------|
| 신고 목록 | GET | `/admin/reports` | 관리자 | 200 | 400, 401, 403 |
| 신고 기각 | PUT | `/admin/reports/{id}/dismiss` | 관리자 | 200 | 400, 401, 403, 404, 409 |
| 신고된 대화 읽기 | GET | `/admin/reports/{id}/conversation` | 관리자 | 200 | 400, 401, 403, 404 |
| 허가서 신청 목록 | GET | `/admin/permit-requests` | 관리자 | 200 | 400, 401, 403 |
| 허가서 사진 보기 | GET | `/admin/permit-requests/{id}/photo` | 관리자 | 200 | 401, 403, 404, 500 |
| 허가서 승인 | PUT | `/admin/permit-requests/{id}/approve` | 관리자 | 200 | 400, 401, 403, 404, 409 |
| 허가서 반려 | PUT | `/admin/permit-requests/{id}/reject` | 관리자 | 200 | 400, 401, 403, 404, 409 |
| 허가서 인증 취소 | PUT | `/admin/permit-requests/{id}/revoke` | 관리자 | 200 | 400, 401, 403, 404, 409 |

허가서 심사 API 5개(47~51번)는 아래 "관리자 허가서 심사" 절에 있다.

### 5-15. 신고된 대화 읽기 `GET /admin/reports/{id}/conversation`

`{id}`는 **신고 id**(대화방 id가 아니다). 대화 신고(`target.type`이 `CONVERSATION`)의 방과 최근 쪽지 200통을 돌려준다(S14-f2, S14-g). 접근 규칙은 위 "접근 규칙 (`/admin/**` 공통)"과 같고, GET이라 CSRF 헤더는 필요 없다.

성공 응답 `200 OK`

```json
{
  "reportId": 4,
  "conversationId": 12,
  "itemTitle": "중고 자전거 팝니다",
  "buyer": { "id": 2, "nickname": "신고자" },
  "seller": { "id": 8, "nickname": "판매자" },
  "messages": [
    { "id": 30, "sender": { "id": 2, "nickname": "신고자" }, "content": "아직 있나요?", "createdAt": "2026-11-13T03:00:00.123456Z" },
    { "id": 31, "sender": null, "content": "탈퇴한 사람이 보낸 쪽지", "createdAt": "2026-11-13T03:05:00.000000Z" }
  ],
  "hasMore": false
}
```

- **관리자는 신고된 대화를 이 통로로만 읽는다.** 일반 대화 보기 `GET /conversations/{id}`(38)는 관리자도 참가자가 아니면 **여전히 404**다(S14 결정 ⑥, 바뀌지 않았다).
- **신고 시각으로 자르지 않는다:** 신고 뒤에 오간 쪽지, 신고하지 않은 상대가 보낸 쪽지도 나온다(S14-f 사용자 결정). 다만 `messages`는 **최근 200통만**, **쪽지 id 오름차순**이다(S14-g). 방에 쪽지가 200통을 넘으면 가장 오래된 것들이 빠지고 `hasMore`가 `true`다(200통 이하면 전부 주고 `false`). 이전 쪽지를 불러오는 페이지 나누기는 아직 없다.
- **읽음 처리가 안 된다.** 관리자가 읽어도 쪽지의 읽은 시각(`read_at`)과 참가자의 안 읽은 쪽지 수는 바뀌지 않는다. 응답에는 읽음 여부도, `mine`(내가 보낸 것)도 없다.
- `buyer`·`seller`·`sender`는 `{id, nickname}`이고, 탈퇴했으면 `null`이다. 글이 지워졌거나 상대가 탈퇴했어도 200이고, `itemTitle`은 방을 만들 때 복사해 둔 제목이다.
- **기각된 신고(`DISMISSED`)도 계속 읽을 수 있다**(409 없음). 기각해도 방과 쪽지는 그대로 남는다.
- 글·댓글·중고 글 신고의 id는 404다(대화 신고만 열린다).
- 서버는 쪽지가 몇 통이든 SQL을 같은 횟수로 실행한다(보낸 사람을 쪽지와 함께 읽는다, N+1 없음). 읽기만 하므로 행 잠금을 잡지 않는다.

검사 순서: 로그인 401 → 토큰 role 403 → 신고 id 400 → DB 재확인 401/403 → 없는 신고 404 → 대화 신고가 아님 404.

| 상태코드 | 언제 |
|----------|------|
| 400 | 신고 id가 숫자가 아님 (`abc`, `1.5`, Long 범위 초과) |
| 401 | 로그인 안 됨, 토큰은 `ADMIN`인데 회원이 DB에서 탈퇴(삭제)됨 |
| 403 | 일반 회원(토큰 role이 `ADMIN`이 아님), 토큰은 `ADMIN`인데 DB에서 `USER`로 강등된 관리자 |
| 404 | **두 가지 모두 404**: ① 없는 신고(0·음수 id 포함), ② 있지만 대화 신고가 아닌 신고(글·댓글·중고 글 신고의 id) |

## CSRF 토큰 (Csrf)

### 6. CSRF 쿠키 발급 `GET /csrf`

`XSRF-TOKEN` 쿠키를 설정한다. 로그인 없이 호출 가능.

성공 응답 `200 OK` (헤더 `Set-Cookie: XSRF-TOKEN=...; Path=/`)

```json
{
  "headerName": "X-XSRF-TOKEN"
}
```

`headerName`은 토큰을 실어 보낼 헤더 이름이다. 헤더에는 **쿠키에 설정된 값 그대로**를 쓴다.

## 회원 (Auth)

회원 응답(가입·로그인·`/auth/me`·재발급·닉네임 변경 공통)의 `verifiedSchool`은 학교 인증을 마친 학교 `{ "id": 숫자, "name": 문자열 }`, 미인증이면 `null`이다(인증은 허가서 인증 44번 참고). 아래 예시는 모두 미인증 회원이다.

### 7. 회원가입 `POST /auth/signup`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다. 가입만 하고 로그인은 되지 않는다(로그인은 `POST /auth/login`).
비밀번호는 `{bcrypt}` 접두어가 붙은 해시로만 저장되며 응답에 포함되지 않는다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| username | O | 영문 소문자·숫자·밑줄(`_`)만, 4~20자 (대문자·공백·한글 불가) |
| nickname | O | 한글(가-힣)·영문 대소문자·숫자·밑줄(`_`)만, 2~20자 (공백 불가, 대소문자 구분: `Kim`과 `kim`은 다른 닉네임) |
| password | O | 8~64자, 공백만 있으면 안 됨, UTF-8로 72바이트 이하 (한글은 글자당 3바이트라 24자까지) |

요청 예시

```json
{
  "username": "user01",
  "nickname": "길동이",
  "password": "password123"
}
```

성공 응답 `201 Created`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | username/nickname/password가 비었거나 규칙 위반, JSON 형식이 잘못됨 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 이미 있는 username 또는 nickname (둘을 구분해 알려 주지 않음. 동시에 같은 아이디·닉네임으로 가입해도 한 명만 성공) |

### 8. 로그인 `POST /auth/login`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다.
성공하면 액세스 토큰(JWT, HS256)을 `access_token` 쿠키로 내려준다. 쿠키: `HttpOnly; Path=/; SameSite=Lax; Max-Age=900` (HTTPS 환경에서는 `Secure`도 붙음). 세션(JSESSIONID)은 만들지 않는다.
리프레시 토큰도 `refresh_token` 쿠키로 함께 내려준다. 값은 랜덤 문자열(서버 Redis에는 해시만 저장), 쿠키: `HttpOnly; Path=/api/auth; SameSite=Lax; Max-Age=604800`(7일, HTTPS 환경에서는 `Secure`도 붙음). 경로는 브라우저 기준이며 설정 `app.cookie.refresh-path`로 바꾼다. 여러 기기에서 동시에 로그인할 수 있다(로그인마다 별도 토큰). 앱은 쿠키 보관함(cookie_jar)이 브라우저 대신 같은 일(저장, Path에 맞춰 보내기)을 한다. 앱이 `/api` 없이 백엔드에 직통(`http://localhost:8080`)으로 붙는 로컬 시험에서는 앱이 보내는 경로가 `/auth/...`라서 쿠키 Path가 맞지 않으므로, bootRun 때 `APP_COOKIE_REFRESH_PATH=/auth` 환경변수가 필요하다.
토큰 클레임: `sub`=사용자 id, `username`, `role`(`USER`|`ADMIN`), `iat`, `exp`(발급 15분 후). `role`이 없는 옛 토큰은 `USER`로 취급한다.
만료되거나 변조된 `access_token` 쿠키가 붙어 와도 이 API는 정상 동작한다.

요청 본문: `{ "username": "user01", "password": "password123" }` (둘 다 필수, 빈 값 불가. 형식 검사는 가입에서만 한다)

성공 응답 `200 OK` + `Set-Cookie: access_token=...` + `Set-Cookie: refresh_token=...`
(응답의 `role`은 `"USER"` 또는 `"ADMIN"`)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | username/password가 비었거나 JSON 형식이 잘못됨 |
| 401 | 아이디 또는 비밀번호가 틀림 (없는 아이디와 틀린 비밀번호 모두 같은 401 응답이라 본문으로 구분할 수 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 9. 로그아웃 `POST /auth/logout`

CSRF 헤더 필요. `refresh_token` 쿠키가 있으면 서버(Redis)의 리프레시 토큰을 삭제하고, `access_token`·`refresh_token` 쿠키를 둘 다 지운다(`Max-Age=0`). 로그인하지 않았거나 토큰이 만료돼도 항상 성공한다.

성공 응답 `204 No Content` + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

실패

| 상태코드 | 언제 |
|----------|------|
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

### 10. 내 정보 `GET /auth/me`

`access_token` 쿠키가 필요하다 (Authorization 헤더는 사용하지 않음). 토큰에는 닉네임이 없어서 매번 DB에서 회원을 읽어 응답한다.

성공 응답 `200 OK`

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 쿠키가 없음, 토큰이 만료됨, 서명이 변조됨, 토큰은 유효하지만 회원이 DB에 없음 (리다이렉트(302)는 하지 않음) |

### 11. 토큰 재발급 `POST /auth/refresh`

로그인 없이 호출 가능하지만 CSRF 헤더(`X-XSRF-TOKEN`)는 필요하다. 요청 본문은 없다.
`refresh_token` 쿠키(브라우저가 Path=`/api/auth` 요청에 자동으로 붙임)로 새 액세스 토큰과 새 리프레시 토큰을 받는다.
리프레시 토큰은 한 번만 쓸 수 있다(회전): 쓰면 옛 토큰은 바로 지워지고, 같은 토큰을 다시 쓰면 401이다.
만료되거나 변조된 `access_token` 쿠키가 붙어 와도 이 API는 정상 동작한다.
주의: 실패(401) 응답이 두 쿠키를 지우므로, 클라이언트는 재발급 요청을 동시에 하나만 보내야 한다(여러 요청이 동시에 401을 받아도 재발급은 한 번만, S4-e 화면에서 처리).

성공 응답 `200 OK` + `Set-Cookie: access_token=...` + `Set-Cookie: refresh_token=...` (쿠키 속성은 로그인과 같음)

```json
{
  "id": 1,
  "username": "user01",
  "nickname": "길동이",
  "role": "USER",
  "verifiedSchool": null
}
```

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 쿠키가 없음, 모르는 토큰, 이미 사용한 토큰, 만료됨, 사용자가 삭제됨 (이유는 구분해서 알려주지 않음). 응답에 두 쿠키 삭제 `Set-Cookie`(`Max-Age=0`)가 붙음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

## 내 정보 변경 (Users)

이 절의 API(12~14번)는 모두 로그인(`access_token` 쿠키)과 CSRF 헤더(`X-XSRF-TOKEN`)가 필요하다. 검사 순서: CSRF(403) → 로그인(401) → 본문 형식(400) → 그 밖의 검사.
단, 토큰은 유효하지만 회원이 DB에 없고 본문도 잘못된 경우에는 400이 먼저 나온다.

실패

|----------|------|

### 13. 비밀번호 변경 `PUT /users/me/password`

요청 본문

```json
{ "currentPassword": "oldPassw0rd", "newPassword": "newPassw0rd" }
```

| 필드 | 규칙 |
|------|------|
| currentPassword | 비어 있으면 안 됨, 64자·UTF-8 72바이트 이하 (맞는지는 서버가 확인) |
| newPassword | 8~64자, 공백만은 불가, UTF-8 72바이트 이하 (가입과 같은 규칙) |

성공하면 비밀번호를 바꾸고 이 회원의 모든 리프레시 토큰을 지운다(모든 기기 로그아웃). 클라이언트는 새 비밀번호로 다시 로그인해야 한다. 이 회원의 기기 토큰(푸시 알림용, 52번)도 전부 지운다(비밀번호 UPDATE와 같은 트랜잭션).

성공 응답 `204 No Content` (본문 없음) + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

실패 (비밀번호·토큰은 그대로. 단 아래 500 예외 참고)

| 상태코드 | 언제 |
|----------|------|
| 400 | 값이 비었음, newPassword가 규칙 위반, JSON 형식이 잘못됨, 현재 비밀번호가 틀림, 새 비밀번호가 현재 비밀번호와 같음 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

주의: 현재 비밀번호가 틀려도 401이 아니라 400이다(401이면 프론트가 토큰 재발급을 시도하기 때문).
예외: 비밀번호를 바꾼 뒤 Redis(리프레시 토큰 삭제) 실패로 500이 나면 비밀번호는 이미 바뀌었을 수 있다. 새 비밀번호로 로그인해 볼 것.

### 14. 회원 탈퇴 `DELETE /users/me`

요청 본문 (DELETE지만 본문이 있다. `Content-Type: application/json`)

```json
{ "password": "myPassw0rd" }
```

| 필드 | 규칙 |
|------|------|
| password | 비어 있으면 안 됨, 64자·UTF-8 72바이트 이하 (맞는지는 서버가 확인) |

성공 응답 `204 No Content` (본문 없음) + `Set-Cookie: access_token=; Max-Age=0; ...` + `Set-Cookie: refresh_token=; Max-Age=0; Path=/api/auth; ...`

검사 순서: CSRF(403) -> 로그인(401) -> 본문 형식(400) -> 회원이 DB에 있는지(없으면 401) -> 비밀번호 확인(틀리면 400) -> 삭제.

탈퇴하면
- 회원 정보가 지워지고, 이 회원의 모든 리프레시 토큰도 지워진다(모든 기기 로그아웃).
- 이 회원이 쓴 글은 **지워지지 않고** 작성자만 없어진다(`author`가 `null`). 작성자 없는 글은 수정은 아무도 못 하고(403), 삭제는 관리자만 할 수 있다.
- 이 회원이 쓴 댓글도 지워지지 않고 작성자만 없어진다(`author`가 `null`). 작성자 없는 댓글은 수정은 아무도 못 하고(403), 삭제는 관리자만 할 수 있다.
- 이 회원이 누른 공감은 삭제되어 해당 글의 `likeCount`가 줄어든다.
- 이 회원이 한 신고(대화 신고 포함)는 남고 신고자만 없어진다(`reporter_id`가 null).
- 이 회원이 쓴 비자 후기도 남고 작성자만 없어진다(`author`가 `null`, 학교는 그대로).
- 이 회원의 비자 일정은 함께 지워진다(`ON DELETE CASCADE`).
- 이 회원이 올린 물건 글(중고거래·나눔)도 함께 지워진다(`ON DELETE CASCADE`). 판매자가 탈퇴하면 중고 글과 그 글에 달린 신고도 함께 삭제된다. 그 글들의 사진 파일도 정리된다(커밋 뒤 삭제, 실패분은 주기 청소가 처리하며 응답은 그대로 `204`).
- 이 회원의 허가서 인증 신청(44번)도 함께 지워진다(`ON DELETE CASCADE`). 대기 중이던 허가서 사진 파일도 정리된다(커밋 뒤 삭제, 실패분은 주기 청소가 처리하며 응답은 그대로 `204`).
- 학교 인증 정보(인증 학교·시각, 예전 메일 인증 회원이면 메일 해시)도 함께 지워진다. 허가서 번호 해시는 신청 행과 함께 지워진다.
- 같은 아이디·닉네임으로 다시 가입할 수 있다(새 회원이며 옛 글과는 이어지지 않는다).
- 탈퇴 전에 받은 액세스 토큰으로 `GET /auth/me`, `POST /posts` 등을 부르면 401이다. 탈퇴 전 리프레시 토큰으로 재발급해도 401이다.
- 글·댓글·공감·비자 후기 작성·비자 일정 등록·물건 글 올리기 요청과 탈퇴가 거의 동시에 일어나 저장되지 못한 경우에도 401이다(500 아님).

실패 (회원·글은 그대로. 단 아래 500 예외 참고)

| 상태코드 | 언제 |
|----------|------|
| 400 | 비밀번호가 비었음·64자/UTF-8 72바이트 초과, JSON 형식이 잘못됨, 비밀번호가 틀림 |
| 401 | 쿠키가 없음, 토큰 만료·변조, 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

주의: 비밀번호가 틀려도 401이 아니라 400이다(401이면 프론트가 토큰 재발급을 시도하기 때문).
예외: 회원을 지운 뒤 Redis(리프레시 토큰 삭제) 실패로 500이 나면 회원은 이미 삭제된 상태다. 남은 리프레시 토큰으로 재발급을 요청해도 회원이 DB에 없어 401이므로 다시 로그인되지는 않는다.

## 허가서 인증 신청 (Permit verification)

표준입학허가서(외국인 유학생 입학 허가서) 인증 "신청" API (S20-a). 세 API 모두 로그인이 필요하고 POST·DELETE는 CSRF 헤더(`X-XSRF-TOKEN`)도 필요하다. 신청은 먼저 대기(`PENDING`)로 만들어지고, 같은 요청 안에서 곧바로 서버가 사진 글자를 읽어 판정한다(S20-d2). 4가지(허가서 제목·외국 국적·학교 별칭 일치·번호 읽힘+미사용)가 모두 맞으면 **자동 승인**(`APPROVED`)하고, 그 밖은 `PENDING` 그대로 관리자 심사(47~50번, S20-b)를 기다린다. **자동 반려는 없다.** 글자를 읽는 판독기는 서버 설정 `PERMIT_OCR_MODE`로 고른다(S20-e2): `off`(기본)는 항상 못 읽음이라 모든 신청이 `PENDING`(`machine_result` `UNREADABLE`)이고, `vision`은 구글 Cloud Vision으로 읽는다(`VISION_API_KEY` 필수, 비면 서버가 시작 때 실패). `vision`이면 이 POST가 판독이 끝날 때까지 **최대 약 10초**(`VISION_TIMEOUT`, 기본 10s) 걸릴 수 있다. 판독기 실패(구글 오류·한도 초과·시간 초과·글자 없음·너무 큰 사진·동시 판독 자리 없음)는 에러 응답이 아니라 `UNREADABLE`로 대기시킨 `201`이다. 대기가 14일을 넘기면 서버가 자동으로 반려(`EXPIRED`)하고 사진을 지운다(S20-c, 서버가 켜져 있으면 1시간 안에, 꺼져 있던 동안 밀린 것은 켜진 뒤 몇 분 안에).
승인되면 `users.verified_school_id`(학교 인증 칸)에 학교가 들어가고, 글쓰기 등 "학교 인증 규칙"의 검사는 그 칸을 그대로 쓴다. 예전 메일 인증 회원(S20-f 전에 학교 메일로 인증한 회원, `verifiedSchool`이 있는 회원)은 신청 없이도 `APPROVED`로 본다.
사진 보관: 허가서 사진은 **심사 결과가 나올 때까지만** 서버 비공개 저장소(운영 S3 비공개 버킷, 로컬은 폴더)에 보관한다. 허가서 전용 접두사(`permits/`)에 JPEG/PNG로 다시 저장하고(긴 변 2048px로 줄이고 EXIF·GPS 메타데이터 제거), 사진을 돌려주는 API는 관리자 전용 48번뿐이다(회원 본인용은 없다). 철회·회원 탈퇴 때 사진도 지우고, 대기 상태로 14일이 넘은 신청은 서버가 켜져 있으면 1시간 안에, 서버가 꺼져 있던 동안 밀린 것은 켜진 뒤 몇 분 안에 자동 반려와 함께 사진이 지워진다. 운영 S3에는 `permits/` 14일 자동 삭제(수명 주기) 규칙이 안전망으로 걸린다. 서버 로그에는 파일 이름·사진 key·내용을 남기지 않고 회원 id와 결과 종류만 남긴다.

### 44. 허가서 인증 신청 `POST /users/me/permit-verification`

요청: `multipart/form-data`

| 파트 | 규칙 |
|------|------|
| file | 허가서 사진 한 장. JPEG·PNG만(형식은 파일 이름·`Content-Type`이 아니라 맨 앞 바이트로 판별). 없거나 비어 있으면 400 |
| consent | `true`여야 함(사진 수집·이용 동의). 없거나 `true`가 아니면 400, 불린 형식이 아닌 값도 400 |

```
POST /users/me/permit-verification
Content-Type: multipart/form-data; boundary=...
(파트 file: 사진 파일)
(파트 consent: true)
```

- 파일 하나 최대 10MB(요청 전체 11MB). 넘으면 413. 사진 올리기(33번)와 같은 전역 멀티파트 설정(`spring.servlet.multipart.max-file-size`·`max-request-size`)이라 서버 쪽은 이 API만 따로 걸지 않았다. nginx는 이 주소(`/api/users/me/permit-verification`)에만 `client_max_body_size 11m`·`proxy_read_timeout 150s` 예외 블록이 있다(없으면 1MB 넘는 사진이 413).
- 서버가 사진을 다시 만들어 저장한다(33번과 같은 처리기 사용). 허가서는 본 사진 한 장만 보관하고 썸네일은 만들지 않는다. 픽셀 상한(긴 변 10,000px 초과 또는 총 4천만 픽셀 초과)은 400.
- 회원당 대기(`PENDING`) 신청은 동시에 1건만 가능하다(DB 부분 UNIQUE `uk_permit_requests_user_pending`로 보장: 같은 회원이 동시에 두 번 보내도 하나만 성공하고 나머지는 409).
- 하루 3회까지: Redis 카운터로 서울 날짜(`Asia/Seoul`) 기준 하루에 센다(자정에 0으로 돌아감). 철회하고 다시 내도 횟수는 줄지 않는다. 이미 승인됐거나 이미 대기 중이라 409로 거절된 요청은 세지 않고, 사진이 깨져 400이 난 시도는 센다(남용 방지). 서버 탓 실패(처리 자리 없음 503, 정리 작업과 겹친 503, 창고 저장 실패 500, 동시 신청에서 져서 난 409 등)는 센 횟수를 되돌려 세지 않는다.
- Vision 하루 전체 상한(`VISION_GLOBAL_PER_DAY`, 기본 30, 서울 날짜, 0이면 끔)을 넘으면 판독 없이 관리자 대기(`machineResult=UNREADABLE`)로 둔다. 응답은 그대로 201 `PENDING`. Redis 오류 때도 구글을 부르지 않고 같은 처리(보통 Redis 장애는 앞의 회원당 하루 횟수 확인에서 500이 난다. 그 확인을 통과한 직후 끊긴 경우만 해당). `PERMIT_OCR_MODE=off`면 세지 않는다.
- 상한은 판독 시도 기준으로 센다(사진이 너무 커서 구글을 안 부르는 경우도 1건).
- 이미지 처리는 이 기능 전용으로 서버 전체에서 동시에 1장까지만 한다. 자리가 날 때까지 최대 5초 기다리고, 그래도 안 나면 503.

성공 응답 `201 Created`. 신청이 접수되면 항상 201이고, 자동 승인 여부는 `status`로 구분한다. 응답에는 기계 판정 결과(`machineResult`)를 넣지 않는다(관리자 목록 47번에만 나온다).

```json
{ "status": "PENDING", "requestedAt": "2026-11-16T05:12:34.123456Z" }
```

자동 승인된 경우:

```json
{ "status": "APPROVED", "requestedAt": "2026-11-16T05:12:34.123456Z", "decidedAt": "2026-11-16T05:12:35.012345Z" }
```

검사 순서: CSRF 403 → 로그인 401 → 동의·파일 400(없음·빈 파일) → 회원이 DB에 있는지(없으면 401) → 이미 승인(학교 인증 있음) 409 → 이미 대기 중 409 → 하루 3회 429 → 사진 검사 400(형식·깨짐·크기) → 처리 자리 없음 503 → (저장 직전 회원 행을 잠그고 다시 확인) 회원 없음 401, 이미 승인 409, 동시에 먼저 신청됨 409 → (신청 행 저장이 커밋된 뒤) 판정 단계.

판정 단계(S20-d2): 신청 행 저장이 끝난 뒤 DB 트랜잭션 밖에서 판독기가 사진 글자를 읽고(이미지 처리 자리는 이미 돌려준 뒤) 판정 규칙이 `machine_result`를 정한다. 코드는 `UNREADABLE`(못 읽음), `NO_TITLE`, `NATIONALITY_UNCLEAR`, `SCHOOL_NOT_MATCHED`, `NUMBER_NOT_FOUND`, `NUMBER_DUPLICATE`, `ALL_PASSED`(뜻은 47번 표).
- `ALL_PASSED`이고 같은 번호가 아직 승인되지 않았고 관리자가 취소(`REVOKED`, 51번)한 적도 없으면 **자동 승인**: 관리자 승인과 같은 잠금 순서(회원 행 → 신청 행 → `PENDING` 재확인)로 신청 행을 `APPROVED`(`auto_decided` true, 결정한 관리자 없음, 학교 = 기계가 찾은 학교, 번호 해시 저장)로 바꾸고 `users.verified_school_id`를 채우고 사진을 지운다. 응답은 `201` + `APPROVED`.
- 그 밖(판독기가 빈 값·예외, 규칙 불통과, 같은 번호가 이미 승인됐거나 취소된 적이 있음(S21-b, 취소된 번호는 관리자가 직접 확인하도록 대기로 둔다. 관리자의 직접 승인(49번)은 막지 않는다) 또는 승인 순간 같은 번호의 다른 신청이 먼저 승인돼 짐(둘 다 `NUMBER_DUPLICATE`))은 **`PENDING` 그대로** 두고 `machine_result`와 `detected_school_id`만 적는다(번호 해시는 적지 않는다). 응답은 지금까지처럼 `201` + `PENDING`, 사진은 남고 하루 횟수는 그대로 1회다. 자동 반려는 없다.
- 판정 도중 회원이 철회·탈퇴했으면 조용히 끝나고(응답은 `201` + 신청 시점의 `PENDING`, 신청 행·사진은 철회가 지운 상태 그대로) 판독 도중 다른 방법으로 학교 인증이 채워졌으면 자동 승인하지 않고 `PENDING`으로 둔다(`machine_result`는 `ALL_PASSED`로 적힌다 — 관리자는 반려로 정리). 판독 도중 관리자가 먼저 승인·반려했으면 그 결정을 그대로 두고 아무것도 적지 않는다. 자동 심사 자체가 실패하면(판정 규칙 오류·DB 순간 장애) `machine_result`는 `null`인 `PENDING`으로 남는다.
- 판정 단계의 예외(`RuntimeException`)는 5xx로 바꾸지 않는다(이미 저장된 `PENDING` 신청이 응답이다). 메모리 부족 같은 서버 `Error`는 500이지만 신청은 `PENDING`으로 남는다.
- 서버 로그에는 "허가서 자동 승인: userId, requestId, result"처럼 회원 id·신청 id·결과 코드만 남기고, 읽은 글자·허가서 번호·해시·사진 key·`permits/`는 남기지 않는다. 판독기 오류도 예외 클래스 이름만 남기고, `vision` 판독기 로그에는 상태 숫자·`error.code` 숫자만 남긴다(API 키·사진·읽은 글자는 남기지 않는다).
- `vision` 모드는 구글을 동시에 2건까지만 부른다(넘으면 기다리지 않고 바로 `UNREADABLE`). 서버가 다시 만든 사진(base64로 바꾸기 전)이 7MB보다 크면 구글을 부르지 않고 `UNREADABLE`이다.

저장 전에 새 파일 이름을 서버의 "지울 파일 대기 표"에 먼저 적고 신청 행을 넣을 때 같이 뗀다(33번과 같은 방식: 뗄 때 청소부가 이미 집었으면 503). 사진 저장 뒤 DB 기록이 실패하면 저장한 사진을 지우고, 중간에 서버가 죽어 고아 파일이 생겨도 주기 청소가 지운다.

| 상태코드 | 언제 |
|----------|------|
| 400 | `consent`가 없음·`true`가 아님, `file` 파트가 없음·빈 파일, JPEG·PNG가 아님(가짜 파일 포함), 깨진 파일, 픽셀 수 초과 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조), 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 409 | 이미 승인된 회원(학교 인증이 있음. 예전 메일 인증 회원(S20-f 전) 포함), 이미 대기 중인 신청이 있음(동시 요청 포함) |
| 413 | 파일이 10MB 초과, 또는 요청 전체가 11MB 초과 |
| 415 | `multipart/form-data`가 아닌 요청(사진 올리기 33번과 같다. JPEG·PNG가 아닌 파일은 415가 아니라 400) |
| 429 | 오늘(서울 날짜) 이미 3번 신청함 |
| 500 | 서버가 받아 둔 업로드 임시 파일을 읽지 못함, 창고 저장 실패(저장한 파일은 치운다), 또는 Redis 장애(하루 횟수 확인 실패) |
| 503 | 이미지 처리 자리가 5초 안에 나지 않음, 또는 올리는 사이 정리 작업과 겹침(잠시 뒤 다시 시도) |

### 45. 내 허가서 인증 상태 `GET /users/me/permit-verification`

성공 응답 `200 OK`. 값이 없는 칸은 JSON에서 빠진다.

```json
{ "status": "PENDING", "requestedAt": "2026-11-16T05:12:34.123456Z" }
```

| 필드 | 설명 |
|------|------|
| status | `NONE`(신청한 적 없음) / `PENDING`(대기) / `REJECTED`(거절) / `APPROVED`(승인) / `REVOKED`(승인됐다가 관리자가 취소함, 51번. 다시 신청할 수 있다) |
| rejectReason | `REJECTED`·`REVOKED`일 때만(`REVOKED`는 취소 사유, `EXPIRED` 제외). 거절 이유 코드: `BLURRY`, `NOT_PERMIT`, `NOT_MASKED`, `UNSUPPORTED_SCHOOL`, `DUPLICATE`, `EXPIRED`(14일 넘게 대기해 서버가 자동 반려함. 다시 신청할 수 있다), `OTHER` |
| requestedAt | 신청 시각(UTC). 신청이 없으면 없음 |
| decidedAt | 결정 시각(UTC). 결정 전이거나 신청이 없으면 없음 |

자동 승인(44번)된 회원도 관리자가 승인한 회원과 똑같이 `APPROVED`로 나간다(구분하는 칸은 없고, 기계 판정 결과 `machineResult`도 이 응답에는 없다).

판단 순서: 회원의 학교 인증(`verified_school_id`)이 있으면 신청 행이 없어도 `APPROVED`(예전 메일 인증 회원(S20-f 전)은 `{ "status": "APPROVED" }`만 나간다. 신청 행 중 승인된 것이 있으면 그 신청·결정 시각이 같이 나간다). 없으면 가장 최근 신청 행의 상태, 신청이 없으면 `NONE`.

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조), 토큰은 유효하지만 회원이 DB에 없음 |

### 46. 허가서 신청 철회·인증 해제 `DELETE /users/me/permit-verification`

성공 응답 `204 No Content` (본문 없음). 한 트랜잭션에서 이 회원의 신청 행을 지우고(관리자가 취소한 `REVOKED` 행은 지우지 않고 남긴다. 취소 기록과 번호 해시를 본인이 없애 같은 번호로 다시 자동 승인받지 못하게 하려는 것), 학교 인증(`verified_school_id`·`verified_at`·`school_email_hash`)이 있으면 비운다(`NULL`). 사진 파일은 커밋 뒤에 지우고, 지우기가 실패해도 응답은 그대로 `204`이며 주기 청소가 처리한다.
- 대기(`PENDING`) 신청: 사진과 신청 행을 지운다(철회).
- 승인된 회원(`APPROVED`): 신청 행들을 지우고 학교 인증을 비운다. **이후 글쓰기 등 "학교 인증 규칙"의 만들기 요청은 `403`이다.** 신청 행 없이 학교 인증만 있는 예전 메일 인증 회원(S20-f 전)도 같은 처리다(인증을 해제하므로 되돌리려면 다시 인증해야 한다).
- 거절(`REJECTED`)된 신청만 있어도 그 행들을 지우고 `204`다.
- 취소(`REVOKED`)된 행만 있고 학교 인증도 없으면 지울 것이 없어 `404`. 취소된 뒤 다시 신청한 대기 신청이 있으면 그 대기 행만 지워지고 `REVOKED` 행은 남는다.
- 신청(지울 행)도 학교 인증도 없으면 `404`.
- 철회해도 하루 3회 신청 횟수(44번)는 줄지 않는다.
- **알려진 한계(S20-d2)**: 본인 철회가 승인된(`APPROVED`) 신청 행(허가서 번호 해시)은 지우므로 "승인 → 본인 철회 → 다른 계정으로 같은 허가서 신청"은 다시 자동 승인될 수 있다. 관리자가 취소(51번)한 번호는 S21-b에서 막혔다(`REVOKED` 행이 남아 자동 승인 대신 관리자 대기).

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조), 토큰은 유효하지만 회원이 DB에 없음 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 404 | 지울 신청(취소된 REVOKED 행 제외)도 학교 인증도 없음 |

## 관리자 허가서 심사 (Admin permit review)

관리자가 허가서 인증 신청(44번)을 보고 승인·반려·인증 취소 API 5개 (S20-b, 인증 취소는 S21-a). 접근 규칙(401·403·DB 재확인)은 관리자 절의 "접근 규칙 (`/admin/**` 공통)"과 같고, PUT은 `X-XSRF-TOKEN` 헤더가 필요하다. 신청 직후 기계 판정·자동 승인(S20-d2)은 44번에 있고, 자동 승인·판정 결과는 아래 47번 목록에 나온다. 글자 판독기는 `PERMIT_OCR_MODE`(`off`|`vision`)로 고른다(44번).
자동 만료(S20-c): 대기(`PENDING`)가 14일(`app.permit.pending-ttl`)을 넘긴 신청은 서버가 자동으로(서버가 켜져 있으면 1시간 주기, 꺼져 있던 동안 밀린 것은 켜진 뒤 3분쯤 지나 첫 실행 때. `app.permit.expiry-interval`·`app.permit.expiry-initial-delay`) `REJECTED`(`rejectReason` `EXPIRED`, `decidedAt` 채움)로 바꾸고 사진을 지운다. 사람이 아닌 시스템 결정이라 결정한 관리자 정보는 없다. 이 반려 건도 아래 47번 목록의 `REJECTED`에 나온다.
서버 로그에는 "허가서 승인/반려/인증 취소: adminId, requestId"만 남기고 허가서 번호·해시·사진 key·사진 내용은 남기지 않는다.

### 47. 허가서 신청 목록 `GET /admin/permit-requests?status=PENDING`

`status`는 `PENDING`(기본)·`APPROVED`·`REJECTED`·`REVOKED`(S21-a, 취소된 건). 모르는 값은 400. 정렬: `PENDING`은 오래된 순(id 오름차순 = 대기 처리 순서), 나머지는 최신순(id 내림차순, 방금 처리한 것이 먼저). 페이징 없이 최대 200건만 돌려준다(관리자 신고 목록처럼 상한만 둠). 성공 `200 OK`:

```json
[
  { "id": 7, "userId": 3, "nickname": "minsu", "status": "PENDING",
    "createdAt": "2026-11-16T05:12:34.123456Z", "decidedAt": null,
    "schoolId": null, "schoolName": null, "rejectReason": null,
    "detectedSchoolId": null, "detectedSchoolName": null,
    "machineResult": "UNREADABLE", "autoDecided": false, "hasPhoto": true }
]
```

| 필드 | 설명 |
|------|------|
| schoolId·schoolName | 승인된 학교(승인·취소(`APPROVED`·`REVOKED`) 때만) |
| rejectReason | 반려 이유 코드(반려·취소(`REJECTED`·`REVOKED`) 때만. 취소는 취소 사유) |
| detectedSchoolId·detectedSchoolName | 기계가 글자에서 찾은 학교(별칭 표와 일치한 경우. 다른 항목이 떨어져도 채워진다. 못 찾았거나 판정 전이면 `null`) |
| machineResult | 기계 판정 결과 코드(판정 전 옛 행이거나 자동 심사가 실패한 건이면 `null`): `UNREADABLE`(글자를 못 읽음: 판독기 빈 값·오류), `NO_TITLE`(허가서 제목 없음), `NATIONALITY_UNCLEAR`(국적이 한국 계열이거나 외국 나라 이름 목록에 없음·칸 없음), `SCHOOL_NOT_MATCHED`(학교명이 별칭 표와 일치하지 않음), `NUMBER_NOT_FOUND`(번호 칸 없음·4자 미만), `NUMBER_DUPLICATE`(같은 번호가 이미 승인됐거나 관리자가 취소한 적이 있음, S21-b), `ALL_PASSED`(4가지 모두 통과. 보통 자동 승인된 건이고, `status`가 `PENDING`이면 판독 도중 회원이 다른 방법으로 이미 인증돼 자동 승인하지 않은 건 — 반려로 정리) |
| autoDecided | 서버(기계)가 자동 승인했으면 `true`. 이 건은 결정한 관리자 정보가 없고(사람이 아닌 시스템 결정, 만료 반려와 같다) 사진은 이미 지워져 `hasPhoto`가 `false`다. 위조는 못 막는다(글자 규칙만 보므로 알려진 한계) |
| hasPhoto | 신청 행에 `photo_key`가 있는가(대기 중이면 보통 `true`, 처리가 끝나면 `false`). 창고에 파일이 실제로 있는지는 보지 않으므로 파일이 없으면 48번은 `404` |

사진 key·허가서 번호 해시·content type은 응답에 넣지 않는다. 값이 없는 칸도 `null`로 나간다. 신청자가 탈퇴하면 신청 행도 같이 지워지므로 목록에 닉네임 없는 항목은 없다.

### 48. 허가서 사진 보기 `GET /admin/permit-requests/{id}/photo`

성공 `200 OK`, 본문은 사진 바이트(`Content-Type`은 DB 값을 그대로가 아니라 `image/jpeg`·`image/png` 고정 값 중 하나). 개인정보라 응답 헤더에 `Cache-Control: no-store`와 `X-Content-Type-Options: nosniff`를 붙인다. 없는 신청 `404`, 사진이 없는 신청(처리가 끝나 지워짐·삭제됨) `404`. 저장된 종류가 `image/jpeg`·`image/png`가 아니면 `404`.
검사 순서: 로그인 401 → 토큰 role 403 → DB 재확인 401/403 → 없는 신청 404 → 사진 없음 404 → 저장된 종류가 image/jpeg·image/png가 아니면 404 → 창고 열기(없으면 404, 실패하면 500).

### 49. 허가서 승인 `PUT /admin/permit-requests/{id}/approve`

```json
{ "schoolId": 1, "permitNumber": "AB-12 34 56" }
```

| 필드 | 규칙 |
|------|------|
| schoolId | 필수. 관리자가 사진을 보고 확인한 학교 |
| permitNumber | 필수, 공백만이면 안 됨, 최대 50자. 허가서의 **표준입학허가서 번호(문서 번호)** 하나다(기계 자동 승인이 읽는 번호와 같은 번호라 같은 허가서면 기계가 승인한 번호와 겹쳐 409). 서버가 유니코드 NFKC로 정규화(전각 → 일반 문자)한 뒤 글자·숫자만 남기고(공백·하이픈·`/`·`.`·`_` 등 제거) 대문자로 바꾸고, **HMAC-SHA256(비밀 값 `PERMIT_HASH_SECRET`)** 해시(hex)만 저장한다(원문은 저장하지 않음). 정리하고 나서 빈 문자열이면 400. "제…호"·"No." 같은 접두·접미어는 지우지 않으므로 **관리자는 번호의 영숫자 부분만 입력**한다 |

성공 `200 OK` + 처리된 항목(47번과 같은 모양, `status` `APPROVED`, `schoolId`·`schoolName`·`decidedAt` 채워짐, `hasPhoto` `false`). 한 트랜잭션에서 신청 행(승인·학교·번호 해시·결정 시각·결정 관리자·사진 칸 비움)과 회원(`verified_school_id`·`verified_at`)을 함께 바꾸고, 사진 파일은 커밋 뒤에 지운다(실패해도 응답은 그대로, 주기 청소가 처리). 회원의 `school_email_hash`는 건드리지 않는다.

검사 순서: CSRF 403 → 로그인 401 → 토큰 role 403 → 본문 400 → DB 재확인 401/403 → 번호에 쓸 글자 없음 400 → 없는 신청 404 → 본인 신청 403(관리자는 자기 신청을 심사할 수 없다) → 없는 학교 404(기존 관례: 없는 학교는 404) → (신청자 회원 행 잠금 → 신청 행 잠금 → 다시 확인) 신청자 탈퇴 404, 이미 처리됨(`PENDING` 아님) 409, 이미 인증된 회원 409, 같은 허가서 번호가 이미 승인됨 409(미리 확인) → (저장 때) 동시 승인 경쟁에서 진 쪽은 부분 UNIQUE 위반으로 409. 처리 중 이 관리자 계정이 탈퇴하면 401.

| 상태코드 | 언제 |
|----------|------|
| 400 | `schoolId` 없음, `permitNumber` 없음·공백·50자 초과·정리하면 빈 문자열, 본문 형식 오류 |
| 401·403 | 관리자 절의 접근 규칙, 또는 `X-XSRF-TOKEN` 없음(403) |
| 403(본인 신청) | 관리자 본인의 신청 |
| 404 | 없는 신청, 없는 학교, 신청자가 탈퇴함 |
| 409 | 이미 처리된 신청, 이미 인증된 회원(대기 중 다른 방법으로 인증됨 — 반려로 정리할 수 있다), 같은 허가서 번호가 이미 승인됨(부분 UNIQUE `uk_permit_requests_permit_hash`) |

관리자 둘이 같은 신청을 동시에 승인·반려하면 하나만 `200`, 나머지는 `409`. 같은 번호를 두 신청에 동시에 승인해도 하나만 `200`이다.

### 50. 허가서 반려 `PUT /admin/permit-requests/{id}/reject`

```json
{ "reason": "BLURRY" }
```

`reason`은 필수이고 `BLURRY`, `NOT_PERMIT`, `NOT_MASKED`, `UNSUPPORTED_SCHOOL`, `DUPLICATE`, `EXPIRED`, `OTHER` 중 하나(그 밖의 값은 400). 성공 `200 OK` + 처리된 항목(`status` `REJECTED`, `rejectReason`·`decidedAt` 채워짐, `hasPhoto` `false`). 사진 칸을 비우고 파일은 커밋 뒤에 지운다. 회원은 다시 신청할 수 있다(대기 신청 1건 제한만 있어 반려된 줄은 영향 없음). 이미 인증된 회원의 대기 신청도 반려로 정리할 수 있다.
검사 순서: CSRF 403 → 로그인 401 → 토큰 role 403 → 본문 400 → DB 재확인 401/403 → 없는 신청 404 → 본인 신청 403 → (신청자 회원 행 잠금 → 신청 행 잠금 → 다시 확인) 신청자 탈퇴 404, 이미 처리됨 409.

| 상태코드 | 언제 |
|----------|------|
| 400 | `reason` 없음·목록 밖 값, 본문 형식 오류 |
| 401·403 | 관리자 절의 접근 규칙, 또는 `X-XSRF-TOKEN` 없음(403) |
| 403(본인 신청) | 관리자 본인의 신청 |
| 404 | 없는 신청, 신청자가 탈퇴함 |
| 409 | 이미 처리된 신청 |

**잠금 순서**: 승인·반려는 신청자 회원 행(`FOR UPDATE`) → 신청 행(`FOR UPDATE`) → 상태 재확인 순서로 잡는다. 철회(46번)·탈퇴(14번)가 회원 행을 먼저 잠그므로 같은 순서를 지켜 교착(40P01)을 막는다. 인증 취소(51번)도 같은 순서다.

### 51. 허가서 인증 취소 `PUT /admin/permit-requests/{id}/revoke`

승인된(`APPROVED`) 신청을 관리자가 되돌린다(S21-a). 자동 승인된 위조 허가서 등을 SQL 없이 정리하는 용도다.

```json
{ "reason": "NOT_PERMIT" }
```

`reason`은 필수이고 반려(50번)와 같은 코드 중 `BLURRY`, `NOT_PERMIT`, `NOT_MASKED`, `UNSUPPORTED_SCHOOL`, `DUPLICATE`, `OTHER` 중 하나다. `EXPIRED`(대기 만료 전용)와 목록 밖의 값은 400. 성공 `200 OK` + 처리된 항목(`status` `REVOKED`, `rejectReason` 채워짐, `decidedAt`·결정한 관리자는 취소한 시각·관리자로 덮어씀, `schoolName`은 원래 승인된 학교, `hasPhoto` `false`). 한 트랜잭션에서 신청을 `REVOKED`로 바꾸고 그 회원의 학교 인증(`verified_school_id`·`verified_at`·`school_email_hash`)을 비운다. **이후 글쓰기 등 "학교 인증 규칙"의 만들기 요청은 `403`이다.** 사유는 기존 `reject_reason` 칸에 저장하고 새 칸은 없다.
신청 줄이 없는 인증 회원(예전 메일 인증·SQL로 인증한 계정)은 이 API로 취소할 수 없다(SQL 또는 본인의 인증 해제 46번).
취소된 회원은 다시 신청(44번)할 수 있다(대기 신청 1건 제한만 있다). 취소된 줄은 목록 47번에서 `status=REVOKED`로 볼 수 있다. 취소된 번호의 허가서는 다시 신청해도 4관문을 통과했을 때 자동 승인되지 않고 `NUMBER_DUPLICATE`로 관리자 대기(`PENDING`)가 된다(S21-b, 44번). 관리자가 직접 승인(49번)하는 것은 막지 않는다(잘못 취소했을 때 구제). 회원 본인 철회(46번)는 취소된 줄을 지우지 않는다. 알려진 한계: 회원 탈퇴는 취소 기록도 함께 지운다.
검사 순서: CSRF 403 → 로그인 401 → 토큰 role 403 → 본문 400 → DB 재확인 401/403 → `EXPIRED` 400 → 없는 신청 404 → 본인 신청 403 → (신청자 회원 행 잠금 → 신청 행 잠금 → 다시 확인) 신청자 탈퇴 404, `APPROVED` 아님 409.

| 상태코드 | 언제 |
|----------|------|
| 400 | `reason` 없음·목록 밖 값·`EXPIRED`, 본문 형식 오류 |
| 401·403 | 관리자 절의 접근 규칙, 또는 `X-XSRF-TOKEN` 없음(403) |
| 403(본인 신청) | 관리자 본인의 신청 |
| 404 | 없는 신청, 신청자가 탈퇴함 |
| 409 | 승인(`APPROVED`) 상태가 아님(대기·반려·이미 취소됨). 메시지: "승인된 신청만 취소할 수 있습니다." |

회원 본인 철회(46번)와 동시에 와도 한쪽이 기다렸다 순서대로 처리되고(철회가 먼저면 신청 행이 지워져 `404`), 교착(500)은 없다. 서버 로그에는 "허가서 인증 취소: adminId, requestId"만 남긴다.

## 비자 후기 (Visa review)

비자 후기 표(`visa_reviews`)는 S11-a에서 만들었다. 현재 API는 선택지(17), 작성(18), 단건 조회(19), 목록(20), 수정(21), 삭제(22), 통계(23)이다. (내 비자 일정 24~26은 아래 별도 절) (작성·수정 요청 본문은 같은 필드를 쓴다.)

### 17. 비자 후기 선택지 `GET /visa-review-options`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). DB를 조회하지 않고 고정값을 돌려준다. 각 목록의 순서는 서버 enum 선언 순서다.

성공 응답 `200 OK`

```json
{
  "visaTypes": [
    { "code": "D_2", "name": "D-2 유학" },
    { "code": "D_4", "name": "D-4 어학연수" },
    { "code": "D_10", "name": "D-10 구직" },
    { "code": "E_7", "name": "E-7 특정활동(취업)" },
    { "code": "OTHER", "name": "기타" }
  ],
  "applicationTypes": [
    { "code": "NEW", "name": "신규 발급" },
    { "code": "REGISTRATION", "name": "외국인등록" },
    { "code": "EXTENSION", "name": "체류기간 연장" },
    { "code": "CHANGE", "name": "체류자격 변경" },
    { "code": "OTHER", "name": "기타" }
  ],
  "results": [
    { "code": "APPROVED", "name": "승인" },
    { "code": "DENIED", "name": "불허" }
  ]
}
```

`code`는 이후 후기 작성 요청에 보낼 값이고, `name`은 화면에 보여 줄 한글 이름이다.

### 18. 비자 후기 작성 `POST /visa-reviews`

로그인 필요, **학교 인증을 마친 회원만** 쓸 수 있다(관리자도 예외 없음). 후기의 학교는 본문으로 받지 않고 **작성자가 인증한 학교가 자동으로 복사**된다(`schoolId`·`authorId`·`author` 같은 모르는 필드를 보내도 무시한다). 그래서 글쓰기와 달리 "다른 학교 403"은 없다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| visaType | O | `GET /visa-review-options`의 `visaTypes` code 중 하나. 그 밖의 문자열·숫자(예: `0`)면 400 |
| applicationType | O | `applicationTypes` code 중 하나 |
| receivedDate | O | 접수일. `"2026-09-01"` 형식(`yyyy-MM-dd`), 형식이 틀리면 400 |
| resultDate | O | 결과 받은 날. 같은 형식 |
| result | O | `APPROVED`(승인), `DENIED`(불허) 중 하나 |
| content | | 후기 본문. 없거나 `null`이면 빈 문자열로 저장. 최대 2000자, NUL 문자 불가 |

날짜 규칙: 접수일 ≤ 결과일 ≤ 오늘(한국 시간 기준). 결과일이 접수일보다 앞서거나, 두 날짜 중 하나라도 오늘 이후면 400이다. 이에 더해 (1) 접수일은 한국 시간 오늘 기준 최근 5년 이내여야 한다(오늘 − 5년 당일은 통과, 하루라도 더 이전이면 400. 아주 옛날·음수 연도 날짜도 400). (2) 처리 일수(`resultDate - receivedDate`)는 365일 이하여야 한다(365일은 통과, 366일부터 400). 수정(`PUT`)에도 같은 규칙이 적용된다.

요청 예시

```json
{
  "visaType": "D_2",
  "applicationType": "EXTENSION",
  "receivedDate": "2026-09-01",
  "resultDate": "2026-09-20",
  "result": "APPROVED",
  "content": "서류는 3개월치 통장 사본을 냈어요."
}
```

성공 응답 `201 Created` (헤더 `Location: /visa-reviews/1`). 본문은 19번 단건 조회와 같다.

```json
{
  "id": 1,
  "author": { "id": 1, "nickname": "길동이" },
  "school": { "id": 1, "name": "경희대학교" },
  "visaType": { "code": "D_2", "name": "D-2 유학" },
  "applicationType": { "code": "EXTENSION", "name": "체류기간 연장" },
  "receivedDate": "2026-09-01",
  "resultDate": "2026-09-20",
  "result": { "code": "APPROVED", "name": "승인" },
  "processingDays": 19,
  "content": "서류는 3개월치 통장 사본을 냈어요.",
  "createdAt": "2026-11-01T01:30:00.123456Z"
}
```

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 회원이 DB에 있는지(없으면 401) → 학교 미인증 403 → 날짜 규칙 400 → 저장. (글쓰기와 같이 "누가 쓸 수 있나"를 먼저 보고 입력 내용은 그 뒤에 본다.)

실패

| 상태코드 | 언제 |
|----------|------|

## 내 비자 일정 (Visa plan)

회원마다 체류 만료일 하나만 적어 두는 기능(표 `visa_plans`, S12-a). 세 API 모두 **로그인 필요**(`/users/me/**`)이고 `/visa-reviews` 아래가 아니다. 응답에는 만료일과 함께 남은 일수·띠 단계·할 일 목록이 서버 계산으로 붙는다(S12-b).

### 24. 내 비자 일정 조회 `GET /users/me/visa-plan`

로그인 필요. 학교 인증은 필요 없다. **일정이 없어도 404가 아니라 `200`** 이고 `expiryDate`가 `null`이다(화면이 매번 불러도 되게).

성공 응답 `200 OK` (오늘 2026-11-10 서울 기준 예시)

```json
{
  "expiryDate": "2026-12-31",
  "daysLeft": 51,
  "stage": "PREPARE",
  "todos": [
    { "code": "PREPARE", "title": "체류 기간 연장·자격 변경 준비 — 필요한 서류와 신청 시기를 하이코리아에서 확인하세요", "dueDate": "2026-09-02", "daysLeft": -69 },
    { "code": "CHECK", "title": "신청 확인 — 연장이나 자격 변경을 할 계획이라면 하이코리아에서 방법을 확인하세요", "dueDate": "2026-12-01", "daysLeft": 21 },
    { "code": "URGENT", "title": "만료 임박 — 체류 상태를 하이코리아나 관할 출입국·외국인청에서 확인하세요", "dueDate": "2026-12-24", "daysLeft": 44 }
  ]
}
```

일정이 없을 때: `{ "expiryDate": null, "daysLeft": null, "stage": null, "todos": [] }`

| 필드 | 설명 |
|------|------|
| expiryDate | 저장된 체류 만료일. 일정이 없으면 null |
| daysLeft | 만료일 − **서울 오늘**(일 수). 오늘이 만료일이면 0, 지났으면 음수. 일정이 없으면 null |
| stage | 띠 단계 문자열. `daysLeft ≥ 121` → null, `31~120` → `PREPARE`, `8~30` → `CHECK`, `0~7` → `URGENT`, `< 0` → `EXPIRED`. 일정이 없으면 null |
| todos | 할 일 체크리스트(일정이 없으면 빈 배열). 시점 3개 고정(만료 120·30·7일 전), `dueDate` 오름차순. 이미 지난 할 일도 빼지 않고 `daysLeft`를 음수로 둔다 |
| todos[].code | 시점 코드 `PREPARE`·`CHECK`·`URGENT` (이름은 식별자라 기준 숫자를 바꿔도 그대로) |
| todos[].title | 할 일 문구(확인을 안내하는 말투, 개인 사정에 대한 지시·판단 없음) |
| todos[].dueDate | 만료일 − N일. 그 확인을 시작할 시점이지 마감이 아니다 |
| todos[].daysLeft | dueDate − 서울 오늘 (지났으면 음수) |

`daysLeft`·`stage`·`todos`는 DB에 저장하지 않고 요청 때마다 서울 오늘 기준으로 계산한다. 시점 숫자(120·30·7)와 문구는 서버의 `VisaMilestone` enum 한 곳에서만 바꾼다.

화면 표시: 화면은 `daysLeft`로 D-n / D-Day / D+n을 보여 주고, `stage`는 띠(색·강조) 판단용으로만 쓴다. 화면은 `todo.code === stage`인 할 일 줄을 "지금 확인할 때"로 강조한다.

실패

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 토큰은 유효한데 회원이 DB에 없음) |

### 25. 내 비자 일정 등록·덮어쓰기 `PUT /users/me/visa-plan`

로그인 필요, **학교 인증을 마친 회원만** 가능(인증 여부는 매번 DB로 확인). 일정이 없으면 만들고 있으면 새 값으로 덮어쓴다(회원당 1개). 같은 회원의 PUT이 동시에 와도 행은 1개이고 나중 값이 남는다.

요청 본문


| 필드 | 규칙 |

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400(빈 값·형식) → 학교 미인증 403 → 날짜 범위 400

실패

| 상태코드 | 언제 |
|----------|------|

## 중고거래·나눔 (Market item)

물건 글 표(`market_items`)는 S13-a에서 만들었다. API는 올리기(27)·한 건 보기(28)·목록(29)·수정(30)·삭제(31)·상태 바꾸기(32)·사진 올리기(33)·사진 보기(34)·사진 지우기(35)다. 페이징은 아직 없다(제목 검색은 29번 `q`).

### 27. 물건 글 올리기 `POST /market-items`

로그인 필요, **학교 인증을 마친 회원만** 올릴 수 있다(관리자도 예외 없음). 글의 학교는 본문으로 받지 않고 **판매자가 인증한 학교가 자동으로 복사**되고, 상태는 항상 `ON_SALE`로 시작한다(`schoolId`·`status`·`sellerId` 같은 모르는 필드를 보내도 무시한다).

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| title | O | 비어 있거나 공백뿐이면 400, 최대 100자, NUL 문자 불가 |
| content | O | 비어 있거나 공백뿐이면 400, 최대 2000자, NUL 문자 불가 |
| tradeType | O | `SALE`(판매), `FREE`(나눔) 중 하나. 그 밖의 문자열·숫자면 400 |
| price | 판매만 O | `SALE`: 1~10,000,000(원) 정수. 없거나 0 이하이거나 상한을 넘으면 400. `FREE`: 없거나 `null`이거나 0이면 0으로 저장, 1 이상(음수 포함)이면 400 |

요청 예시

```json
{ "title": "전공 서적 팝니다", "content": "거의 새 책이에요.", "tradeType": "SALE", "price": 15000 }
```

성공 응답 `201 Created` (헤더 `Location: /market-items/1`). 본문은 28번 단건 조회와 같다(방금 올렸으니 `photos`는 `[]`).

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 회원이 DB에 있는지(없으면 401) → 학교 미인증 403 → 가격 규칙 400 → 저장. (비자 후기와 같이 "누가 올릴 수 있나"를 먼저 보고 가격 규칙은 그 뒤에 본다.)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 제목·본문이 비었거나 길이 초과, NUL 포함, `tradeType` 없음·없는 값, JSON 형식 오류, 가격 규칙 위반(판매인데 가격 없음·0 이하·상한 초과, 나눔인데 가격 1 이상) |

### 29. 물건 글 목록 `GET /market-items`

로그인 없이 쓸 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). 최신순(id 내림차순), 페이징 없음. 글이 없으면 빈 배열 `[]`. 본문(`content`)까지 포함해 28번 단건과 거의 같은 모양의 배열을 돌려준다. 단, **목록 항목에는 `photos` 대신 `coverPhoto`가 있다**(그 글에서 id가 가장 작은 = 처음 올린 사진 한 장. 사진이 없으면 `null`이고 키는 항상 있다). 글마다 사진을 따로 읽는 비용을 피하려고, 대표 사진은 글 1000개당 쿼리 1번(보통 1번)으로 모아 온다.

| 이름 | 설명 |

| `schoolId` | 그 학교의 글만 |
| `tradeType` | `SALE`(판매) / `FREE`(나눔) |
| `status` | `ON_SALE` / `RESERVED` / `DONE` |

### 30. 물건 글 수정 `PUT /market-items/{id}`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 수정할 수 없다). 학교 인증은 필요 없다. 요청 본문은 27번 올리기와 같은 필드·규칙(`title`, `content`, `tradeType`, `price`)이며 모두 새 값으로 바꾼다(일부만 바꾸는 PATCH는 없음). 상태·학교·판매자·`createdAt`은 바뀌지 않는다(`status`·`schoolId` 등 모르는 필드는 무시). **거래완료(`DONE`)된 글은 수정할 수 없다(409).** 상태는 32번으로만 바꾼다.

요청 예시: `PUT /market-items/1`

```json
{ "title": "전공 서적 팝니다 (가격 내림)", "content": "거의 새 책이에요.", "tradeType": "SALE", "price": 12000 }
```

성공 응답 `200 OK`: 수정된 글. 28번 응답과 같은 모양.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 가격 규칙 400 → 없는 id 404 → 본인 아님 403 → 거래완료 글 409 (비자 후기 수정과 같이 입력 오류가 먼저, 남의 글이어도 본문이 잘못되면 403이 아니라 400).

동시 요청: 수정은 "상태가 `DONE`이 아닐 때만" 바꾸는 조건부 UPDATE 한 문장이다. 수정하는 사이에 다른 요청이 `DONE`으로 바꿔 커밋하면 내용은 바뀌지 않고 409, 글이 지워졌으면 404다. 수정이 상태를 옛 값으로 되돌리는 일은 없다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 27번과 같은 본문 오류(필수 누락, 없는 `tradeType`, 길이 초과, NUL 문자, 가격 규칙 위반), id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 id, 또는 수정하는 사이에 글이 지워진 경우 |
| 409 | 거래완료(`DONE`)된 글 (수정하는 사이에 `DONE`이 된 경우 포함) |

### 31. 물건 글 삭제 `DELETE /market-items/{id}`

로그인 필요, 판매자 본인 또는 관리자만 가능. DB에서 글을 완전히 지운다(복구 불가). 이 글에 달린 신고도 함께 삭제된다. 학교 인증은 필요 없다.
글에 붙은 사진도 함께 지워진다: 사진 행은 DB가 지우고, 창고 파일(본 사진·썸네일)은 커밋 뒤에 서버가 지운다. 파일 지우기가 실패해도 응답은 그대로 `204`이고, 못 지운 파일은 서버의 주기 청소(10분마다)가 마저 지운다.

요청 예시: `DELETE /market-items/1`

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 남의 글을 관리자 토큰으로 지우려는데 그 회원이 DB에 없는 경우도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아니고 관리자도 아님 (토큰은 ADMIN인데 DB의 role이 USER인 경우 포함) |
| 404 | 없는 id (이미 삭제된 id 포함) |

### 32. 물건 글 상태 바꾸기 `PUT /market-items/{id}/status`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 바꿀 수 없다). 학교 인증은 필요 없다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| status | O | `ON_SALE` / `RESERVED` / `DONE` 중 하나. 없거나 `null`이거나 모르는 값이면 400 |

요청 예시: `PUT /market-items/1/status`

```json
{ "status": "RESERVED" }
```

성공 응답 `200 OK`: 상태가 바뀐 글. 28번 응답과 같은 모양(`photos` 포함).

허용하는 전환

| 지금 | 바꿀 수 있는 상태 |
|------|------------------|
| `ON_SALE` (판매중) | `RESERVED`, `DONE` |
| `RESERVED` (예약중) | `ON_SALE`, `DONE` |
| `DONE` (거래완료) | 없음 (한 번 완료되면 되돌릴 수 없다) |

위 표에 없는 전환과 **지금과 같은 상태로 바꾸기**는 409다.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 없는 id 404 → 본인 아님 403 → 전환 불가 409 (비자 후기와 같은 흐름).

동시 요청: "지금 상태가 읽은 값일 때만 바꾸는" 조건부 UPDATE 한 문장이다. 같은 글에 요청이 동시에 두 번 와도 하나만 200이고 나머지는 409, 그 사이 글이 지워졌으면 404다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 본문이 비었거나 JSON 형식 오류, `status`가 없음·`null`·모르는 값, id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 비로그인이면 없는 id도 401 |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 id, 또는 바꾸는 사이에 글이 지워진 경우 |
| 409 | 허용하지 않는 전환 (`DONE`에서 나가기, 지금과 같은 상태로 바꾸기), 또는 동시에 다른 요청이 먼저 상태를 바꾼 경우 |

### 33. 물건 글 사진 올리기 `POST /market-items/{id}/photos`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 403). 학교 인증은 필요 없다. 거래완료(`DONE`) 글에는 올릴 수 없다. 수정(30번)과 같은 규칙이다. 한 요청에 사진 1장, 글당 최대 10장.

요청: `multipart/form-data`, 파트 이름 `file` 한 개.

```
POST /market-items/1/photos
Content-Type: multipart/form-data; boundary=...
(파트 file: 사진 파일)
```

- JPEG·PNG만 받는다. 형식은 파일 이름·`Content-Type`이 아니라 파일 맨 앞 바이트(매직 바이트)로 판별한다. HEIC·WebP·GIF·가짜 파일은 400.
- 파일 하나 최대 10MB(요청 전체 11MB). 넘으면 413 (서버 설정 `spring.servlet.multipart.max-file-size`·`max-request-size`). 401·413처럼 본문을 읽지 않고 응답할 때도 연결이 끊기지 않도록 남은 본문 버리기 한도(`server.tomcat.max-swallow-size`)를 11MB로 맞췄다.
- 서버가 사진을 다시 만들어 저장한다: 긴 변 2048px로 줄이고, EXIF 회전을 반영하고, GPS 같은 메타데이터는 지운다. 320px 썸네일도 함께 저장한다. 형식은 유지(JPEG는 JPEG, PNG는 PNG).
- 픽셀 상한: 긴 변 10,000px 초과 또는 총 4천만 픽셀 초과는 400.

성공 응답 `201 Created` (헤더 `Location: /market-items/1/photos/7` — 사진 한 장 보기 주소이며 34번 GET으로 열린다)

```json
{ "id": 7, "width": 1365, "height": 2048, "thumbWidth": 213, "thumbHeight": 320, "contentType": "image/jpeg" }
```

| 필드 | 설명 |
|------|------|
| id | 사진 id |
| width·height | 저장된 본 사진 크기(px, 줄이고 회전한 뒤 값) |
| thumbWidth·thumbHeight | 썸네일 크기(px, 긴 변 최대 320) |
| contentType | `image/jpeg` 또는 `image/png` |

검사 순서: CSRF 403 → 로그인 401 → 파일 없음·빈 파일 400 → 없는 글 404 → 본인 아님 403 → 거래완료 409 → 이미 10장 409 → 사진 검사 400(형식·깨짐·크기) → (저장 직전 글을 잠그고 다시 확인) 글이 사라짐 404, 거래완료 409, 이미 10장 409, 지울 파일 쪽지를 청소부가 이미 집었으면 503.
앞쪽 10장 검사는 무거운 처리를 헛하지 않으려는 미리보기이고, 잠금 안의 검사가 최종이다.
이미지 처리는 서버 전체에서 동시에 2장까지만 한다. 자리가 날 때까지 최대 5초 기다리고, 그래도 안 나면 503. 파일 내용은 자리를 얻은 뒤에 읽는다.
저장 과정(파일 저장 → DB 기록) 중 하나라도 실패하면 방금 저장한 파일 2개는 지운다. 같은 글에 동시에 올려도 글 행을 잠그고 사진 수를 세므로 10장을 넘지 않는다(9장일 때 동시 2장이면 하나만 성공, 나머지 409).
저장 전에 새 파일 이름 2개를 서버의 "지울 파일 대기 표"에 먼저 적고, 사진 행을 넣을 때 같이 뗀다(잠금 뒤 쪽지를 떼는데, 청소부가 이미 집었으면 503). 중간에 서버가 죽어 고아 파일이 생겨도 주기 청소가 지운다.
글을 지우거나 판매자가 탈퇴하면 사진 행도 DB가 함께 지운다(`ON DELETE CASCADE`). 그때의 창고 파일 정리는 31번·14번 설명을 본다. 사진 한 장만 지우기는 35번.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `file` 파트가 없음, 빈 파일, JPEG·PNG가 아님(가짜 파일 포함), 깨진 파일, 픽셀 수 초과, id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조). 회원이 DB에 있는지는 확인하지 않는다(탈퇴·삭제된 회원의 유령 토큰도 최대 15분은 통과하며, 공개 글만 읽고 횟수 제한은 그대로 적용된다) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 id, 또는 처리하는 사이에 글이 지워진 경우 |
| 409 | 거래완료 글, 또는 이미 사진이 10장 |
| 413 | 파일이 10MB 초과, 또는 요청 전체가 11MB 초과 |
| 415 | `multipart/form-data`가 아닌 요청 |
| 500 | 서버가 받아 둔 업로드 임시 파일을 읽지 못함, 또는 창고 저장 실패(저장한 파일은 치운다) |
| 503 | 이미지 처리 자리가 5초 안에 나지 않음, 또는 올리는 사이 정리 작업과 겹침(잠시 뒤 다시 시도) |

### 34. 물건 글 사진 보기 `GET /market-items/{id}/photos/{photoId}`

로그인 없이 볼 수 있다(만료·변조된 `access_token` 쿠키가 붙어 와도 `200`). 이 한 주소의 GET만 공개이고, 올리기(POST)·지우기(DELETE)는 로그인이 필요하다. `/market-items/{id}/photos` 자체의 GET은 없다(사진 목록은 28번 단건 응답의 `photos`).

요청 예시

```
GET /market-items/1/photos/7              (본 사진)
GET /market-items/1/photos/7?size=thumb   (썸네일)
```

| 쿼리 | 설명 |
|------|------|
| size | 없음 = 본 사진, `thumb` = 썸네일(긴 변 최대 320px). 그 밖의 값(빈 값 `size=`·`THUMB` 포함)은 400 |

성공 응답 `200 OK`, 본문은 사진 파일 바이트(JSON 아님). Range 요청은 지원하지 않고 항상 200 전체 본문을 준다.

| 응답 헤더 | 값 |
|-----------|-----|
| Content-Type | 사진을 올릴 때 DB에 적어 둔 `image/jpeg` 또는 `image/png` (파일 내용에서 추측하지 않음) |
| Content-Length | 본문 바이트 수 |
| Cache-Control | `public, max-age=31536000, immutable` — 사진 id의 그림은 한 번 올리면 바뀌지 않아서 1년 저장해도 된다 |
| X-Content-Type-Options | `nosniff` |

검사 순서: `size` 값 400 → 사진 번호와 글 번호가 둘 다 맞는 사진이 없음 404 → 장부(DB)에는 있는데 창고에 파일이 없음 404.
다른 글의 사진 번호로 요청하면 404다(그 사진이 보이지 않는다). 존재하지 않는 글과 존재하지 않는 사진은 구분하지 않고 같은 404다.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `size`가 비었거나 `thumb`가 아님, 글 id·사진 id가 숫자가 아님 |
| 404 | 없는 글·없는 사진·다른 글의 사진, 또는 창고에 파일이 없음 |
| 500 | 창고에서 파일을 여는 중 오류(디스크·S3 오류 등) |

500은 파일을 여는 중 오류만 해당한다. 전송 중 읽기 오류는 헤더가 이미 나간 뒤라 연결이 끊긴다(본문이 Content-Length보다 짧음).

### 35. 물건 글 사진 지우기 `DELETE /market-items/{id}/photos/{photoId}`

로그인 필요, **판매자 본인의 글만** 가능(관리자도 남의 글은 403). 학교 인증은 필요 없다. 거래완료(`DONE`) 글의 사진은 지울 수 없다. 33번(올리기)과 같은 규칙이다.

요청 예시: `DELETE /market-items/1/photos/7`

성공 응답 `204 No Content` (본문 없음)

검사 순서: CSRF 403 → 로그인 401 → 없는 글 404 → 본인 아님 403 → 거래완료 409 → 이 글의 사진이 아님(없는 사진·다른 글의 사진·이미 지운 사진) 404 → 장부(DB) 행 삭제.
글 행을 잠그고(`FOR UPDATE`) 확인하므로 같은 글의 거래완료 전환·사진 올리기와 줄을 서서 처리된다.
DB 삭제가 커밋된 **뒤에** 창고 파일 2개(본 사진·썸네일)를 지운다. 파일 지우기가 실패해도 이미 장부에서 지웠으므로 응답은 그대로 204이다. 지울 파일 이름은 DB 삭제와 같은 트랜잭션에서 "지울 파일 대기 표"에 적어 두므로, 실패분은 서버의 주기 청소(10분마다)가 마저 지운다.
지운 뒤 34번 보기는 404, 28번 단건의 `photos`에서도 빠진다(나머지 사진의 순서는 그대로).

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | 글 id·사진 id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 또는 본인 글이 아님 (관리자도 불가) |
| 404 | 없는 글, 이 글의 사진이 아님(없는 사진·다른 글의 사진·이미 지운 사진) |
| 409 | 거래완료 글 |

## 쪽지 (Message)

쪽지는 "대화방" 방식이다(S14). **중고 글 + 구매자 한 쌍에 대화방 1개**이고, 같은 글에 다시 보내면 기존 방에 쪽지가 붙는다. 실시간이 아니다. 표는 `conversations`·`messages`(V12). 지금(S14-f1)은 첫 쪽지 보내기(36), 내 대화 목록(37), 대화 보기(38), 이어서 보내기(39), 읽음 처리(40), 안 읽은 수(41), 대화 신고(42, 표 `reports`에 V13)가 있다.

### 36. 중고 글 판매자에게 쪽지 보내기 `POST /market-items/{id}/conversations`

로그인 필요, **학교 인증을 마친 회원이 인증한 학교의 글에만** 보낼 수 있다(관리자도 예외 없음). 보내는 사람(구매자)은 로그인 정보로 정해지고 받는 사람은 글의 판매자다. 자기 글에는 보낼 수 없다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| content | O | 1~1000자. 비어 있거나 공백뿐이면 400, NUL 문자 불가 |

요청 예시: `POST /market-items/1/conversations`

```json
{ "content": "안녕하세요, 아직 있나요?" }
```

성공 응답 `201 Created`. **새 방이든 기존 방이든 항상 201**이다. 응답 본문에 `conversationId`가 있어서 `Location` 헤더는 없다(방은 `GET /conversations/{id}`로 본다).

```json
{
  "conversationId": 3,
  "message": { "id": 10, "content": "안녕하세요, 아직 있나요?", "createdAt": "2026-11-12T03:00:00.123456Z", "mine": true }
}
```

- 이 글 + 이 구매자의 방이 있으면 그 방에 쪽지를 붙이고(같은 `conversationId`), 없으면 방을 만든다. 방을 만들 때 글 제목을 복사해 둔다(글이 지워져도 대화에 제목이 남는다).
- 쪽지를 붙일 때마다 방의 마지막 쪽지 시각(`last_message_at`)이 갱신된다.
- `mine`은 내가 보낸 쪽지인가(여기서는 항상 `true`).
- **거래완료(`DONE`) 글에는 새 대화를 시작할 수 없다(409).** 단, 이미 방이 있으면 거래완료 글이어도 쪽지를 계속 보낼 수 있다(201).
- 같은 사람이 같은 글에 동시에 여러 번 보내도 방은 1개만 생기고 쪽지는 보낸 만큼 저장된다(모두 201). DB의 UNIQUE(`uk_conversations_item_buyer`)와 `ON CONFLICT DO NOTHING`으로 지킨다.
- 글이 지워지면 방은 남고 글 칸만 비워진다. 회원이 탈퇴해도 방·쪽지는 남고 그 회원 칸만 비워진다(DB의 `ON DELETE SET NULL`).

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 회원이 DB에 있는지(없으면 401) → 학교 미인증 403 → 없는 글 404 → 다른 학교 글 403 → 자기 글 400 → (방이 없을 때만) 거래완료 409 → 저장.

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `content`가 없거나 비었거나 공백뿐, 1001자 이상, NUL 포함, JSON 형식 오류, 글 id가 숫자가 아님, 자기 글에 보냄 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 저장 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함, 글이 인증한 학교의 글이 아님 |
| 404 | 없는 글 (보내는 도중 글이 지워진 경우 포함) |
| 409 | 거래완료 글에 새 대화를 시작함 (이미 방이 있으면 해당 없음) |

### 37. 내 대화 목록 `GET /conversations`

로그인 필요. **학교 인증은 필요 없다**(읽기는 대화 참가자이면 된다). 내가 구매자 또는 판매자인 방만, **마지막 쪽지가 최근인 순**(같으면 방 id 내림차순)으로 준다. 방이 없으면 `[]`. 페이지 나누기는 없다.

성공 응답 `200 OK`

```json
[
  {
    "id": 3,
    "item": { "id": 1, "title": "자전거 팝니다", "deleted": false },
    "partner": { "id": 7, "nickname": "판매자닉" },
    "lastMessage": { "content": "아직 있어요", "createdAt": "2026-11-12T03:00:00.123456Z", "mine": false },
    "unreadCount": 1
  }
]
```

- `unreadCount`는 **그 방에서 내가 아직 안 읽은 쪽지 수**다(상대가 보냈고 읽음 처리가 안 된 것, 상대가 탈퇴해 보낸 사람이 비어 있는 쪽지 포함). 없으면 `0`. 내가 보낸 쪽지는 세지 않는다. 정확한 정의는 41.

- `item.title`은 **방을 만들 때 복사해 둔 제목**이다(글을 고쳐도 대화의 제목은 그대로). 글이 지워진 방은 `item.id`가 `null`, `deleted`가 `true`, `title`은 복사해 둔 제목이다.
- `partner`는 대화 상대(나 말고 한 명). **상대가 탈퇴했으면 `null`**이다.
- `lastMessage.mine`은 마지막 쪽지를 내가 보냈는가. 보낸 사람이 탈퇴해 비어 있으면 `false`.
- 방이 1개든 20개든 SQL 수는 같다(상대 닉네임·마지막 쪽지·방별 안 읽은 수를 한꺼번에 읽는다).

검사 순서: 로그인 401 → 회원이 DB에 있는지(없으면 401).

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음) |

### 38. 대화 보기 `GET /conversations/{id}`

로그인 필요. 학교 인증은 필요 없다. **대화 참가자(구매자·판매자)만** 볼 수 있다. 없는 방이거나 내 방이 아니면(관리자 포함) 똑같이 404다(남의 대화가 있는지 알려 주지 않으려고).

성공 응답 `200 OK`

```json
{
  "id": 3,
  "item": { "id": 1, "title": "자전거 팝니다", "deleted": false },
  "partner": { "id": 7, "nickname": "판매자닉" },
  "messages": [
    { "id": 10, "content": "안녕하세요, 아직 있나요?", "createdAt": "2026-11-12T03:00:00.123456Z", "mine": true },
    { "id": 11, "content": "아직 있어요", "createdAt": "2026-11-12T03:05:00.000000Z", "mine": false }
  ],
  "hasMore": false
}
```

- `item`·`partner`는 목록(37)과 같은 모양이다. 상대가 탈퇴했어도 200이고 `partner`만 `null`이다.
- `messages`는 **최근 200통만**, **쪽지 id 오름차순**(오래된 것부터)이다. 시각(`createdAt`)이 아니라 id가 진짜 순서다(동시에 보낼 때 시각이 어긋날 수 있어서). 방에 쪽지가 200통을 넘으면 가장 오래된 것들이 빠지고 `hasMore`가 `true`다(200통 이하면 전부 주고 `false`). 이전 쪽지를 불러오는 페이지 나누기는 아직 없다.
- `mine`은 내가 보낸 쪽지인가(보낸 사람이 탈퇴해 비어 있으면 `false`).

검사 순서: 로그인 401 → 회원이 DB에 있는지(없으면 401) → 방이 없거나 참가자가 아님 404.

| 상태코드 | 언제 |
|----------|------|
| 400 | 방 id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음) |
| 404 | 없는 방, 내가 참가자가 아닌 방 (관리자도 404) |

### 39. 대화에 쪽지 보내기(답장) `POST /conversations/{id}/messages`

로그인 필요, **학교 인증을 마친 회원**만 보낼 수 있다(36과 같다). 대화 참가자만 보낼 수 있다. 보내는 사람은 로그인 정보로 정해진다.

요청 본문은 36과 같다.

| 필드 | 필수 | 규칙 |
|------|------|------|
| content | O | 1~1000자. 비어 있거나 공백뿐이면 400, NUL 문자 불가 |

요청 예시: `POST /conversations/3/messages`

```json
{ "content": "내일 3시에 만날까요?" }
```

성공 응답 `201 Created`

```json
{ "id": 12, "content": "내일 3시에 만날까요?", "createdAt": "2026-11-12T03:10:00.123456Z", "mine": true }
```

- 성공하면 방의 마지막 쪽지 시각이 갱신되어 **양쪽 대화 목록의 맨 위**로 올라간다.
- **글이 지워진 방, 거래완료 글의 방에도 보낼 수 있다(201).** 대화는 계속된다.
- **상대가 탈퇴했으면 409**다. 보내는 도중 상대 탈퇴가 먼저 커밋돼도 409이고 쪽지는 저장되지 않는다(쪽지를 넣기 전에 두 사람의 회원 행을 잠가, 탈퇴한 상대에게 쪽지가 들어가는 틈이 없다).

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → 회원이 DB에 있는지(없으면 401) → 학교 미인증 403 → 방이 없거나 참가자가 아님 404 → 상대가 이미 탈퇴함 409 → 저장.

| 상태코드 | 언제 |
|----------|------|
| 400 | `content`가 없거나 비었거나 공백뿐, 1001자 이상, NUL 포함, JSON 형식 오류, 방 id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 보내는 도중 내가 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함 |
| 404 | 없는 방, 내가 참가자가 아닌 방 (인증한 관리자도 404) |
| 409 | 상대가 탈퇴함 |

### 40. 읽음 처리 `PUT /conversations/{id}/read`

로그인 필요. **학교 인증은 필요 없다**(읽기 계열이라 GET과 같다). 대화 참가자만 쓸 수 있다. 화면이 대화(38)를 받은 뒤, **받은 쪽지 중 마지막 번호**를 보내서 "거기까지 봤다"고 알리는 용도다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| lastMessageId | O | 1 이상의 정수(쪽지 id). 없음·`null`·0 이하·숫자가 아닌 값이면 400. 소수(`1.5`, `1.0`, `1e2`)는 400, 숫자 모양 문자열 `"11"`은 받아진다(다른 요청과 같음) |

요청 예시: `PUT /conversations/3/read`

```json
{ "lastMessageId": 11 }
```

성공 응답 `204 No Content`(본문 없음)

- **본 쪽지까지만** 읽음 처리한다: 그 방에서 **쪽지 id가 `lastMessageId` 이하이고, 상대가 보낸**, 아직 안 읽은 쪽지에만 읽은 시각(`read_at`)을 찍는다. 화면을 연 뒤에 새로 도착한 쪽지(더 큰 id)는 안 읽음으로 남는다.
- **내가 보낸 쪽지는 절대 바뀌지 않는다.** 상대가 탈퇴해 보낸 사람이 비어 있는 쪽지는 "상대가 보낸 것"으로 보고 읽음 처리한다.
- 같은 요청을 **두 번 보내도 204**이고, 이미 찍힌 읽은 시각은 그대로다. 바뀐 쪽지가 0개여도 204다.
- `lastMessageId`가 그 방의 가장 큰 쪽지 id보다 커도 204다. 다른 방의 쪽지 번호를 넣어도 **이 방의 쪽지만** 읽음 처리된다(방 id가 조건에 항상 들어간다).
- 읽음 처리는 쪽지의 읽은 시각 칸만 바꾸는 UPDATE 한 문장이다. 먼저 상대 회원 행을 읽기 잠금(KEY SHARE)으로 잡은 뒤 실행하므로, 상대 탈퇴와 겹치면 한쪽이 잠깐 기다릴 뿐 교착(서버 오류)은 나지 않는다. 방 행은 잠그지 않는다.

검사 순서: CSRF 403 → 로그인 401 → 본문 400 → 회원이 DB에 있는지(없으면 401) → 방이 없거나 참가자가 아님 404 → 읽음 처리.

| 상태코드 | 언제 |
|----------|------|
| 400 | `lastMessageId`가 없거나 `null`이거나 0 이하이거나 숫자가 아님, JSON 형식 오류, 본문 없음, 방 id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
| 404 | 없는 방, 내가 참가자가 아닌 방 (관리자도 404) |

### 41. 안 읽은 쪽지 수 `GET /conversations/unread-count`

로그인 필요. 학교 인증은 필요 없다. 내가 참가자인 **모든 방**의 안 읽은 쪽지 수를 합쳐서 준다(상단바 "쪽지 (n)"용). 대화가 없으면 `0`.

성공 응답 `200 OK`

```json
{ "count": 3 }
```

- 세는 조건은 읽음 처리(40)와 똑같다: **상대가 보냈고(보낸 사람이 나와 다름, 탈퇴해 비어 있는 경우 포함) 읽은 시각이 비어 있는 쪽지**. 내가 보낸 쪽지는 세지 않는다.
- 주소가 `GET /conversations/{id}`(38)와 비슷하지만 `unread-count`는 글자 그대로의 주소라 먼저 잡힌다(숫자 id로 오해해 400이 나지 않는다).
- 이 숫자는 요청한 순간의 값이다. 화면 이동 때만 다시 센다(실시간 아님, S14 결정).

검사 순서: 로그인 401 → 회원이 DB에 있는지(없으면 401).

| 상태코드 | 언제 |
|----------|------|
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음) |

### 42. 대화 신고 `POST /conversations/{id}/reports`

로그인과 CSRF 헤더 필요. 대화방의 **참가자(구매자 또는 판매자)** 가 그 대화를 신고한다(S14-f). 표는 `reports`에 `conversation_id` 칸을 붙인 것(V13, 중고 글 신고 V10과 같은 방식). 사유 목록·본문·응답 모양은 글·댓글·중고 글 신고(5-11)와 같고, 사유 5개·detail 300자 규칙도 같다.

요청 본문: `{ "reason": "ABUSE", "detail": "욕을 해요" }` (`reason` 필수, `detail` 선택)

성공 응답 `201 Created` (`Location` 헤더 없음). 응답의 `target`만 다르다.

```json
{
  "id": 7,
  "target": { "type": "CONVERSATION", "id": 3, "postId": null },
  "reason": { "code": "ABUSE", "name": "욕설·비방" },
  "detail": "욕을 해요",
  "status": "PENDING",
  "createdAt": "2026-11-13T03:00:00.123456Z"
}
```

- `target.id`는 **대화방 id**, `target.postId`는 항상 `null`이다.
- 신고자는 로그인한 사용자로 정해진다. 구매자와 판매자가 각각 한 번씩 신고할 수 있고, **같은 회원이 같은 방을 또 신고하면 409**다. 동시에 두 번 보내도 한 번만 `201`이고 나머지는 `409`(DB의 `uk_reports_conversation_reporter`).
- **같은 학교 검사는 하지 않는다**(답장 39와 같다: 이미 시작된 대화라 참가자인지만 본다). 상대가 탈퇴한 방, 글이 지워진 방, 거래완료 글의 방도 신고할 수 있다(201).
- 참가자가 아닌 회원은 **관리자도 404**다(없는 방과 똑같이 보인다). 탈퇴로 비어 있는 방 칸은 "아무나"가 아니다.
- 신고해도 대화·쪽지는 바뀌지 않는다. 상대에게 알림도 가지 않는다.
- 신고자가 탈퇴해도 신고는 남고 신고자만 없어진다(`reporter_id`가 null). 대화방이 지워지는 일은 앱에 없지만, 지워지면 그 방의 신고도 DB가 함께 지운다(`ON DELETE CASCADE`).
- 신고 INSERT 전에 신고자 회원 행을 읽기 잠금(KEY SHARE)으로 먼저 잡는다(탈퇴가 "회원 행 먼저" 순서라 같은 순서를 지킨다). 신고 도중 신고자가 탈퇴하면 `401`이고 `500`은 없다. 상대 회원 행은 잡지 않는다(상대 탈퇴와 겹쳐도 교착 없이 `201`).
- 관리자가 보는 방법은 `GET /admin/reports`(5-13)의 `CONVERSATION` 항목. 기각은 `PUT /admin/reports/{id}/dismiss`(5-14)이고, 대화 신고에는 삭제 처리가 없다. 관리자가 신고된 방의 쪽지를 읽는 방법은 `GET /admin/reports/{신고 id}/conversation`(5-15)이다(신고 시각으로 자르지 않음, 최근 200통, 읽음 처리 안 됨).

검사 순서: CSRF 403 → 로그인 401 → 본문 400 → 회원이 DB에 있는지(없으면 401) → 미인증 403 → (신고자 회원 행 잠금, 그새 탈퇴면 401) → 방이 없거나 참가자가 아님 404 → 중복 409.

| 상태코드 | 언제 |
|----------|------|
| 400 | reason이 없거나 목록에 없음(숫자 `0`·`null` 포함), detail 300자 초과, detail에 NUL 문자 포함, JSON 형식이 잘못됨·본문 없음, 방 id가 숫자가 아님 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음, 신고 도중 탈퇴한 경우 포함) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림, 학교 인증을 안 함(참가자여도, 없는 방이어도 403이 먼저) |
| 404 | 없는 방, 내가 참가자가 아닌 방 (관리자도 404) |
| 409 | 이미 신고한 방. 같은 회원이 동시에 여러 번 보내도 한 번만 성공하고 나머지는 409 |

## 챗봇 (Chat)

### 43. 중고 글 챗봇 `POST /chat`

로그인과 CSRF 헤더 필요(학교 인증은 필요 없다). 질문을 보내면 ① AI가 질문에서 **검색 조건**(물건 단어·최대 가격)을 뽑고 ② 서버가 그 조건으로 **판매중·예약중 중고 글**을 찾고 ③ AI가 찾은 글을 보고 답한다. 응답은 AI의 답과 AI에게 준 글 목록(출처)이다(S17-c RAG 1편, S17-e4에서 2단계 흐름으로 바뀜). AI 호출은 한 질문에 많아야 2번이다. 대화 기억은 없다: 매 요청이 독립이고 서버는 아무것도 저장하지 않는다.

요청 본문

| 필드 | 필수 | 규칙 |
|------|------|------|
| question | O | 앞뒤 공백을 뺀 길이가 1~500자(코드포인트). 없음·`null`·비었거나 공백뿐이면 400, 500자 초과 400, NUL 문자 포함 400 |

요청 예시

```json
{ "question": "3만 원 이하 자전거 있어?" }
```

성공 응답 `200 OK`

```json
{
  "answer": "#12번 글에서 자전거를 3만 원에 팔고 있어요.",
  "sources": [
    {
      "type": "MARKET_ITEM",
      "id": 12,
      "title": "자전거 팝니다",
      "tradeType": { "code": "SALE", "name": "판매" },
      "price": 30000,
      "status": { "code": "ON_SALE", "name": "판매중" }
    }
  ]
}
```

| 필드 | 설명 |
|------|------|
| answer | AI의 답(문자열). **AI의 답은 틀릴 수 있다**(없는 내용을 말하거나 글을 놓칠 수 있음). 화면은 `sources`로 원문을 확인하게 해 준다. 또 **AI 답은 글 작성자가 쓴 문장에 영향받을 수 있다**(예: 글 본문에 숨긴 지시). 화면은 `answer`를 **순수 글자로만** 보여 주고 링크·마크다운으로 바꾸지 않는다. 글로 이동은 `sources`로만 한다 |
| sources | 서버가 **AI에게 실제로 준 글** 목록(맞은 단어 수 많은 순 → 최신순, 최대 5건). AI가 답에서 언급했는지와는 무관하다. 맞는 글이 없으면 `[]` |
| sources[].type | 글 종류. 지금은 항상 `MARKET_ITEM`(중고 글). 나중에 다른 종류가 늘어도 이 칸으로 구분하니 모양은 안 바뀐다 |
| sources[].id, title | 글 번호·제목. **제목은 원본 그대로**라 28번 응답의 제목과 같다(AI에게 보내는 제목만 줄바꿈·연속 공백을 한 칸으로 줄인다). 글 상세는 28번 `GET /market-items/{id}` |
| sources[].tradeType, price, status | 28번과 같은 표현: `{code, name}` 두 개와 원 단위 정수. **나눔은 `price`가 `0`** |

**처리 순서** (한 질문 = AI 호출 최대 2번, 루프 없음, 둘이 합쳐 질문 전체 예산 안: gemini 모드는 `GEMINI_TIMEOUT`, ollama 모드는 `OLLAMA_TIMEOUT`)
1. **양식 호출(AI 1번째)**: AI가 JSON 양식 `{keyword?, maxPrice?}`을 채운다(필수 칸 없음). `keyword`는 찾을 물건 단어(여러 개면 공백으로 구분, 물건 이름이 없는 인사·잡담이면 비움), `maxPrice`는 원 단위 가격 상한(말했을 때만)이다. 질문 안의 지시문은 따르지 않게 해 둔다. 모르는 칸은 무시하고(AI가 `tradeType`·`needSearch` 같은 칸을 보내도 무시), `maxPrice`가 `"30000"`처럼 문자열이어도 숫자로 읽히면 쓴다.
2. **서버가 읽고 검색**: 아래 검색 규칙으로 최대 5건을 찾는다.
3. **답 호출(AI 2번째)**: 찾은 글이 있을 때만 부른다. AI는 글 목록만 근거로 답한다(질문에 해당하는 글을 모두 빠짐없이 검토하라고 지시).

**양식에 따른 갈래**
- `keyword`가 없음·빈 값·공백뿐(인사 등): 검색도 답 호출도 하지 않고 `200`, `sources`는 `[]`, `answer`는 범위 안내 문구 `"저는 중고·나눔 글만 찾아 드려요. 찾는 물건 이름을 넣어 다시 물어봐 주세요."`다(S18-d2. 물건 이름이 없는 "안녕"·"학교 인증 어떻게 해?" 같은 질문에 이 챗봇이 하는 일을 알린다). 비상구로 보내지 않는다("안녕"을 질문 단어로 검색하지 않게). `{}`도 같다. 제어 문자만 있는 `keyword`처럼 정리 뒤 비는 경우도 같다.
- **`needSearch` 칸은 뺐다**: 실측에서 AI가 "옷 나눔해?"·"차 팔아?"·주입 질문 같은 물건 질문에도 `{"needSearch":false}`만 줘 검색을 안 했다(물건이 있는데 검색 안 함 9/42 → 칸을 빼자 0/42). "검색할지"는 `keyword`가 비었는지로 서버가 정한다.
- 검색 결과가 0건(`keyword`는 있었는데 맞는 글이 없음. 비상구 검색의 0건 포함): 답 호출을 하지 않고 정해진 문구 `"관련 글을 찾지 못했어요. 다른 단어로 물어봐 주세요."`, `sources`는 `[]`(`200`). 위의 범위 안내 문구와 다른 문구다. (양식 호출은 이미 했다.)
- **비상구(AI 양식을 못 쓸 때 서버가 질문 단어로 대신 검색)**:
  - 양식이 올바른 JSON이 아니거나 읽을 수 없음(JSON `null`·객체가 아닌 `[]`·`"문자열"`, `maxPrice`가 숫자가 아님 등): 가격 조건 없이 **질문의 단어**로 찾는다. (`{"keyword":"자전거"}`는 정상이고 `{}`는 위의 범위 안내 문구다.)
  - `keyword`를 정리한 뒤 **100자(코드포인트)를 넘으면**(AI가 같은 단어를 끝없이 반복하는 고장 대비) 쓸 키워드가 없는 것으로 보고 **질문의 단어**로 찾는다(AI가 준 `maxPrice` 조건은 유지, 아래 범위 규칙 적용).
  - 두 비상구 모두 응답 모양은 같다(`200`). 사용자에게 비상구를 탔다는 표시는 없다.
- `keyword` 정리: 쉼표(,)·슬래시(/)·중점(·)·제어 문자는 공백으로 바꾼 뒤 공백으로 쪼갠다(`"자전거, 헬멧"` → `자전거`, `헬멧`). 정리한 뒤 `keyword`가 완전히 비면(제어 문자만) 범위 안내 문구(`NO_KEYWORD`)이고, 글자는 남았는데 쓸 단어가 0개면(영문·숫자·기호 한 글자만 등) 검색 0건 문구(`NO_RESULT`, "관련 글을 찾지 못했어요…")다.
- **`maxPrice` 범위 규칙(비상구가 아니라 "그 칸만 버리고 정문 유지")**: 글 올릴 때의 판매 가격 범위인 **1 ~ 10,000,000**만 쓴다. 이 밖이면(0·`-0`·음수·`10000001` 이상·int를 넘는 아주 큰 수 `99999999999999`·`1e30`·`1e999999`·거의 0인 `1e-999999`) **그 칸만 버리고 가격 조건 없음**으로 본다. 양식 전체를 버리지 않으므로 AI가 준 `keyword`는 그대로 쓴다(정문). AI가 "팔아?"·"싸게"·"무료"에 0을 쓰는 버릇이 있고 0원 조건은 나눔만 남겨 판매 글이 사라지기 때문에 0 이하도 같은 규칙이다. 소수(`30000.7`)는 소수점 아래를 버려 `30000`으로 쓴다(`0.5`처럼 1 미만은 조건 없음). `null`은 가격 조건 없음이다. 숫자로 읽을 수 없는 글자(`"삼만"`)와, JSON 읽기 단계에서 막히는 극단 값(지수가 int를 넘는 `1e99999999999`, 1000자리를 넘는 숫자)만 JSON이 깨진 것과 같이 위 첫 번째 비상구로 간다(500이 아니다).
- **나눔 조건은 쓰지 않는다.** 실측에서 AI가 말하지 않은 나눔 조건을 붙여 판매 글이 사라졌고, "AI가 틀려도 글이 사라지지 않고 더 보이는 쪽"을 택해 양식에서 칸을 뺐다. 그래서 "무료 나눔 ○○"를 물어도 판매 글이 함께 나올 수 있다. 나눔인지는 AI의 답과 `sources[].tradeType`으로 구분한다.

**어떤 글을 찾나** (한국어 형태소 처리 없음, 단순 규칙)
- 찾을 문장을 공백으로 쪼개 단어마다(**AI `keyword`는 한글 등 ASCII가 아닌 한 글자 단어("책", "옷", "차")도 쓴다**: 군더더기 없는 물건 이름이라서다. 영문·숫자·기호 한 글자(`a`, `1`, `?`, `~`)는 거의 모든 글에 걸려 버린다(`"자전거 ?"`는 `자전거`만). **질문 단어 비상구는 2글자 이상만** 쓴다) 제목 **또는 본문**에 들어 있으면(부분 일치, 대소문자 무시, 하나라도 맞으면 OR) 찾는다. 같은 단어는 한 번만, 단어는 앞에서 10개까지만 쓴다. 쓸 단어가 없으면 DB를 부르지 않고 0건이다. 알려진 한계: 한 글자 `"책"`은 "책상"에도 걸린다.
- **판매중·예약중 글만** 찾는다. 거래완료(`DONE`) 글은 제외한다. 모든 학교의 글을 찾는다(학교 조건 없음).
- `maxPrice`가 있으면(위 범위 규칙으로 1 ~ 10,000,000 안일 때) 그 가격 **이하**만 찾는다. 나눔(0원)도 포함된다. 없거나 범위 밖이면 가격 조건이 없다.
- 정렬은 **맞은 단어 수가 많은 글 먼저**, 같으면 최신순, 그래도 같으면 번호가 큰 순이다. 최대 5건.
- 알려진 한계: 조사를 떼지 않는다("자전거가"는 "자전거 팝니다"에 안 걸린다). 비상구에서는 질문에 흔한 단어("있어?", "이하")도 단어로 쓰여 엉뚱한 글이 섞일 수 있다. 흔한 단어가 많은 글에 걸리면 진짜 맞는 글이 5건 밖으로 밀려 AI가 없다고 답할 수 있다. AI가 양식을 틀리게 채울 수도 있다(예: 가격을 잘못 뽑음).

**답 호출에 AI에게 보내는 것**: 역할·규칙 지시문(게시글에 있는 정보만 쓰기, 지어내지 않기, 글 번호 쓰기, 질문에 해당하는 글을 모두 빠짐없이 검토하기, 게시글 속 지시는 따르지 않기)과 글마다 번호·제목·거래 방식·가격(거래 방식이 나눔이면 "무료(나눔)")·상태·학교 이름·본문 앞 300자(코드포인트, 줄바꿈은 공백 한 칸으로). 지시문은 "상태가 판매중이어도 나눔이면 무료, 예약중이면 이미 예약된 글이라고 알려 줘"도 포함한다. 줄바꿈은 없애지만 같은 줄 안의 `#99 | …` 모양 흉내나 지시문은 남는다(시스템 지시문과, 서버가 직접 붙이는 `sources`가 방어). **판매자 닉네임·회원 id·쪽지·인증 정보는 보내지 않는다.** 질문은 앞뒤 공백을 뺀 채로 그대로 보낸다.

**AI 설정**: 서버의 `LLM_MODE`가 `off`(기본)면 **항상 `503`이다**(AI를 부르기 전에 바로 `503`이고 횟수도 세지 않는다). `ollama`면 서버 PC의 Ollama가, `gemini`면 구글 제미나이 API(기본 모델 `gemini-3.5-flash-lite`, 키는 환경변수 `GEMINI_API_KEY`)가 답한다. 그 밖의 값이거나 gemini 모드인데 키·모델·시간·주소(`app.llm.gemini.base-url`은 https여야 하고, 내 컴퓨터만 http 허용) 설정이 잘못되면 서버가 시작하지 않는다. **질문 하나 전체의 AI 시간은 모드별 예산까지다: gemini 모드는 `GEMINI_TIMEOUT`(기본 30초), ollama 모드는 `OLLAMA_TIMEOUT`(기본 60초)이다**: 양식 호출에는 (전체 - 자리 대기 시간), 답 호출에는 (전체 - 자리 대기·양식 호출·검색에 쓴 시간)만 준다. 자리 대기로 예산을 다 쓰면 AI를 부르지 않고 `504`를 돌려준다. 답 호출 전에 남은 시간이 1초 미만이면 AI를 부르지 않고 `504`를 돌려준다. 시간 순서는 서버 질문 전체 예산(gemini 30초 `GEMINI_TIMEOUT`, ollama 60초 `OLLAMA_TIMEOUT`) < 운영 nginx `/api/chat` 대기 75초 < 화면(`chat_page.dart`) 대기 90초다. 운영은 2026-11-15 S18 배포부터 gemini(무료 등급)로 켜져 있다(구글이 바쁘면 가끔 `503`이 나고, 다시 물으면 대개 된다).

**외부로 나가는 것(gemini 모드)**: 아래 내용이 **구글(Google) 서버로 전송된다**. 양식 호출은 지시문 + 질문, 답 호출은 지시문 + 글마다 번호·제목·거래 방식·가격·상태·학교 이름·본문 앞 300자 + 질문이다. 회원 정보 칸(닉네임·id)과 쪽지·인증 정보는 보내지 않지만, 글 본문이나 질문에 사람이 직접 쓴 연락처 등은 그대로 나간다. 쓰는 것은 무료 등급(AI Studio 키)이라 보낸 내용이 구글의 제품 개선에 쓰이거나 사람이 볼 수 있다. ollama·off 모드는 바깥으로 아무것도 나가지 않는다. 키는 요청 헤더로만 보내고 로그·예외·응답·actuator에 나오지 않는다. 단, 설정 값을 잘못된 칸(예: 키를 `GEMINI_TIMEOUT`에)에 넣으면 스프링 시작 오류 로그에 그 값이 찍힐 수 있다(deploy.md 참고).

**회원별 질문 횟수 제한(S17-f1)**: 회원 한 명이 **1분에 5번, 하루(서울 자정~자정)에 30번**까지 물을 수 있다. 넘으면 `429`다(관리자도 같다).
- **무엇을 세나**: 본문 검증(400)을 통과한 질문을 **AI를 부르기 전에 1번** 센다. 그래서 AI가 `503`·`504`로 실패한 질문, 검색 결과가 없거나(관련 글 없음 문구) 키워드가 비어(범위 안내 문구) 답 호출 없이 끝난 `200`도 1회로 친다(되돌리지 않음). **세지 않는 것**: `400`·`401`·`403`(그 전에 끝남), **`LLM_MODE=off`**(바로 `503`이라 횟수도 Redis 키도 안 생김), 그리고 `429`로 막힌 요청 자체(막힌 요청은 어느 카운터도 늘리지 않는다).
- **창 규칙(고정 창)**: 분 한도는 **시계의 분 단위**(예: 12:03:00~12:03:59)로 센다. 슬라이딩 창이 아니라서 분 경계에 걸치면 짧은 시간에 최대 10번(59초에 5번 + 다음 분 0초에 5번)까지 통과할 수 있다. 하루 한도는 **서울 자정 기준**이다. 분 한도에 걸려도 1분이 지나면 풀리고, 하루 한도에 걸리면 서울 다음 날 0시에 풀린다.
- **본문·헤더**: `429` 응답 본문에 안내 문구는 없다(503·504와 같음, 화면이 상태코드로 문구를 정한다). `Retry-After`·남은 횟수 헤더도 없다.
- **한도 값**: 서버 설정 `app.chat.rate-limit.per-minute`(5)·`per-day`(30). 리프레시 토큰·허가서 하루 3회 제한과 같은 Redis에 카운터를 둔다.
- **Redis 장애**: 횟수를 확인하지 못하면 `500`이다.

**동시 질문 상한(S17-f2)**: 서버 **전체**에서 AI를 쓰는 질문은 **동시에 2개**까지 진행한다(질문 하나가 양식 호출 → 검색 → 답 호출을 끝낼 때까지 자리 하나를 쥔다). 자리가 없으면 **최대 5초** 기다리고, 그래도 안 나면 `503`이다(AI를 부르지 않는다). `503`·`504`·고정 문구·예상 밖 오류 등 **어떻게 끝나든 자리는 돌아온다**. 자리를 기다린 시간도 **질문 전체 시간(모드별 `GEMINI_TIMEOUT` 30초·`OLLAMA_TIMEOUT` 60초)에 포함**된다: 양식 호출에는 (전체 예산 - 자리 대기 시간)만 준다. `app.chat.slot-wait`가 이 예산 이상이면 서버가 시작하지 않는다. 횟수 제한(429)을 먼저 검사하므로 자리가 없어 `503`이 나도 그 질문은 횟수 1회로 센다. `LLM_MODE=off`면 자리도 잡지 않고 바로 `503`이다. 서버 설정 `app.chat.max-concurrent`(2)·`app.chat.slot-wait`(5s). 서버 1대 메모리로 세므로 서버가 여러 대로 늘면 대수만큼 늘어난다.

**서버 전체 질문 상한(S18-d)**: 모든 회원을 합쳐 **분당 N질문 + 하루 M질문**까지만 받고, 넘으면 `503`이다(AI를 부르지 않고 동시 질문 자리도 잡지 않는다). 구글 무료 한도(분당 15·하루 500 호출)를 다 쓴 뒤에도 구글을 계속 부르는 헛호출을 막고, "양식 호출은 됐는데 답 호출에서 한도 초과"를 줄이려는 것이다.
- **단위는 질문**이다(질문 하나 = AI 호출 최대 2번). 운영 값: **분 7**(= 15÷2), **하루 200**(= 500×0.8÷2, 여유 20%). 설정 `app.chat.global-limit.per-minute`·`per-day`(환경변수 `CHAT_GLOBAL_PER_MINUTE`·`CHAT_GLOBAL_PER_DAY`). **기본은 0 = 검사하지 않음**(로컬 ollama 개발에 영향 없음), 음수면 서버가 시작하지 않는다. 운영 값은 docker-compose.yml 기본값으로 넣는다(S18-e). **모드(`LLM_MODE`)와 상관없이 값이 0보다 크면 센다**(ollama 모드도 포함. `off`는 그 전에 바로 `503`이라 안 센다).
- **창 규칙**: 회원별 제한과 같은 고정 창이다. 분 한도는 시계의 분 단위, **하루 한도는 태평양 시간(America/Los_Angeles) 자정 기준**이다(구글 하루 한도가 리셋되는 시각 = 한국 오후 4~5시, 서머타임에 따라 다름). 회원별 하루(서울 자정)와 다르다.
- **무엇을 세나**: 회원별 검사(429)를 **통과한** 질문만 센다. 막힌 요청(전체 `503`)은 전체 카운터를 늘리지 않는다. 회원별 카운터는 그 전에 이미 1 늘어 있다(자리 `503`도 횟수 1회로 세는 기존 규칙과 같음). `400`·`401`·`403`·`LLM_MODE=off`(바로 `503`)·회원별 `429`는 전체 카운터를 만들지도 늘리지도 않는다.
- **본문·로그**: `503` 응답 본문에 원인 문구는 없다(다른 `503`과 구분되지 않는다. 화면은 같은 문구). 서버 로그에는 "챗봇 서버 전체 상한(분|하루) 넘음 -> 503" 한 줄만 남는다(회원 id·질문 내용 없음).
- **Redis 장애**: 회원별 제한과 같다. 카운터를 확인하지 못하면 `500`이다.
- **알려진 한계**: (1) 회원 한 명이 분당 5번(회원별 한도)을 쓰면 분 7질문 중 5개를 혼자 차지할 수 있고, 회원 7명이 30개씩 쓰면 하루 200질문이 찬다. 상한이 없어도 그때는 구글이 먼저 429를 줘 같은 `503`이 나므로 더 나빠지지는 않는다. (2) 전체 상한에 막힌 재시도도 회원별 카운터(서울 자정 기준 하루 30번)를 깎는다. 그래서 태평양 자정에 전체 상한이 풀려도 그 회원은 회원별 `429`를 볼 수 있다. (3) 고정 창이라 분 경계(59초 + 다음 분 0초)에 순간 최대 분 14질문(= 호출 28번)이 통과할 수 있다.

**안전망(S17-f3)**: AI 호출 스레드는 (동시 질문 상한 + 2)개까지만 만든다. 꽉 차면 대기 없이 `503`이다. 정상 운영에서는 f2 자리 제한이 먼저 걸려 나오지 않는다.

검사 순서: CSRF 403 → 로그인 401 → 본문 검증 400 → (`LLM_MODE=off`면 바로 503, 횟수 안 셈) → **횟수 제한 429** → **서버 전체 상한 503(S18-d, 설정이 0이면 건너뜀)** → **동시 질문 자리(5초 기다려도 없으면 503)** → (자리 대기로 예산을 다 썼으면 AI를 부르지 않고 504) → 양식 호출(AI, 503·504) → (keyword가 비면 바로 200 범위 안내 문구) → 글 검색 → (0건이면 200 "관련 글 없음" 문구) → 남은 시간 확인(1초 미만이면 504) → 답 호출(AI, 503·504).

| 429 | 회원별 질문 횟수 초과: 1분에 5번 또는 하루(서울 자정 기준)에 30번을 넘김. 본문에 안내 문구 없음, `Retry-After` 없음(상태코드로 판단). 위 "회원별 질문 횟수 제한" 참고 |
| 503 | AI를 쓸 수 없음(양식 호출·답 호출 어느 쪽이든): `LLM_MODE=off`(AI 꺼짐), Ollama 서버에 연결 실패, **구글(gemini) 연결 실패·한도 초과(429)·키 오류(401/403)·모델 오류(404 등)·안전 차단·빈 답(구글이 어떤 오류로 답하든 전부 503)**, AI 서버가 오류로 답함, **동시 질문 2개가 꽉 차 5초 안에 자리가 안 남(S17-f2)**, **서버 전체 질문 상한 초과(S18-d: 모든 회원 합계 분당 N질문·하루(태평양 자정 기준) M질문, 설정값. 운영 분 7·하루 200. 위 "서버 전체 질문 상한" 참고)**. **응답 본문에 안내 문구는 없다. 화면은 상태코드로 보여 줄 문구를 정한다.** 응답 본문·서버 로그에 원인 메시지(AI 주소·구글 오류 본문·키)를 넣지 않는다(로그에는 상태 숫자·예외 종류만 한 줄) |
| 504 | AI가 제한 시간 안에 답하지 못함(양식 호출·답 호출 어느 쪽이든, 또는 자리 대기가 질문 전체 시간을 다 써서 AI를 부르지 않음, 또는 양식 호출이 질문 전체 시간을 거의 다 써서 답 호출을 못 함) (503과 같이 본문에 안내 문구·원인 메시지 없음, 상태코드로 판단) |
| 500 | 예상 밖 오류(버그 등). 503/504로 숨기지 않는다 |

## 푸시 알림 기기 토큰 (Device token)

푸시 알림(FCM)을 보낼 "휴대폰 주소"(기기 토큰)를 서버에 적어 두는 API. 안드로이드 앱이 쓴다(S24). 알림 발송은 아직 없다(S24-b 이후). 토큰 값은 비밀 값처럼 다뤄 서버 로그·응답에 남기지 않는다.

### 52. 기기 토큰 등록 `PUT /users/me/device-tokens`

로그인과 CSRF 헤더 필요. 학교 인증은 필요 없다.

요청 본문

```json
{ "token": "fcm-device-token-string" }
```

| 필드 | 규칙 |
|------|------|
| token | 필수, 비어 있거나 공백뿐이면 안 됨, 4096자 이하 |

동작
- 없는 토큰이면 이 회원 것으로 추가한다.
- 같은 토큰이 이미 있으면(내 것이든 남의 것이든) 주인을 지금 로그인한 회원으로 바꾸고 `updated_at`을 갱신한다(폰을 다른 사람이 쓰게 된 경우). 같은 토큰을 동시에 보내도 500이 나지 않는다.
- 회원당 최대 10개다. 새로 넣어 11개가 되면 그 회원 것 중 가장 오래된(`updated_at` 기준, 같으면 `id` 작은 것) 것부터 지워 10개로 맞춘다.

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `token`이 없음·`null`·빈 값·공백뿐, 4096자 초과, NUL 문자 포함, JSON 형식 오류·본문 없음 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조, 회원이 DB에 없음) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |

회원 탈퇴(14번) 때 기기 토큰은 DB가 함께 지운다(`ON DELETE CASCADE`).

### 53. 기기 토큰 삭제 `DELETE /users/me/device-tokens`

로그인과 CSRF 헤더 필요. 앱이 로그아웃하기 전에 부른다(실패해도 앱은 로그아웃을 진행한다).

요청 본문: 52번과 같다 `{ "token": "..." }` (같은 검증 규칙)

내 토큰이면 지운다. 없는 토큰이거나 남의 토큰이면 아무것도 하지 않고 똑같이 성공한다(남의 토큰이 있는지 알려 주지 않기 위해).

성공 응답 `204 No Content` (본문 없음)

실패

| 상태코드 | 언제 |
|----------|------|
| 400 | `token`이 없음·`null`·빈 값·공백뿐, 4096자 초과, NUL 문자 포함, JSON 형식 오류·본문 없음 |
| 401 | 로그인 안 됨 (쿠키 없음, 토큰 만료·변조) |
| 403 | `X-XSRF-TOKEN` 헤더가 없거나 틀림 |
