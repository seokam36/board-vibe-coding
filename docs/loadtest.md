## 원인·증거
**원인: 리눅스 연결 장부(conntrack 표)가 꽉 차서 새 연결을 버렸다.** 장부 칸이 7,680개뿐인데(1GB 서버 기본값), nginx가 앱에 요청을 보낼 때마다 연결을 새로 만들고 끊어서(upstream keepalive 없음) 끊긴 연결 기록이 장부에 1~2분씩 쌓였다.

하나씩 지운 과정(가설 → 확인 → 결과):

| 메모리 부족·스왑 | 무너지는 동안 5초 기록 | 앱 406~410MiB 그대로, 스왑 102~104MB 그대로 → **아님** |
| 앱이 죽음(OOM) | `docker inspect` 재시작 수, `dmesg` OOM | 재시작 0, OOM 기록 없음 → **아님** |
| CPU 부족·GC 멈춤 | 무너진 순간의 CPU | 10:26:00~10:26:23(UTC) 앱 0.2%·nginx 0% — 손님이 기다리는데 서버는 놀고 있음 → **아님** |

추가 증거:
- nginx 로그 `upstream timed out (110) while connecting to upstream` — nginx가 앱에 **연결을 거는 단계**에서 막힘(앱이 느리게 답한 게 아님). 리눅스가 연결 첫 패킷(SYN)을 장부 부족으로 버려서 연결이 안 된 것.
- k6 쪽 19:27:08 `dial tcp ...:443 ... failed to respond` — 바깥 손님의 443 연결도 같은 이유로 버려짐.
- 끝난 뒤 장부 사용 27칸 — 부하가 사라지자 바로 비워짐(기록이 1~2분 뒤 만료).

왜 80명은 괜찮고 160명에서 터졌나: 끊긴 연결 하나가 장부에 약 1~2분 남는다. 초당 80건이면 대략 5천~1만 칸, 초당 100건 넘게 새 연결이 생기면 7,680칸을 넘는다(도커 안팎 이중 기록 포함). 그래서 CPU·메모리는 남는데 "문 앞에서" 막혔다.

## 고친 내용
**nginx → 앱 연결 재사용(upstream keepalive).** 요청 수가 가장 많은 `/api/` 길만 바꿨다(한 번에 하나만 바꿔 전후 비교를 깔끔하게).
- `flutter_app/nginx.conf` 맨 위에 `upstream board_app { zone …; resolver 127.0.0.11 …; server app:8080 resolve; keepalive 16; }` — 연결을 열어 두고 돌려 쓰는 묶음. `resolve`로 앱 컨테이너 IP가 바뀌어도 따라간다(예전 변수 방식과 같은 효과).
- `flutter_app/board-locations.conf`의 `location /api/`: `proxy_pass http://board_app;` + `proxy_http_version 1.1;` + `proxy_set_header Connection "";` — nginx 기본(HTTP/1.0 + close, 매번 끊음)을 바꿔 연결을 유지.
- 챗봇·사진 업로드·허가서·헬스 길은 요청이 적고 시간 설정이 따로 있어 그대로 둠.

로컬 리허설(같은 nginx 1.30 이미지 + 로컬 백엔드, 80명 1분 부하 중 nginx→앱 연결 수, `netstat`):
| 설정 | 열린 연결(ESTABLISHED) | 끊긴 뒤 대기 연결(TIME_WAIT) | 결과 |
|------|------------------------|-------------------------------|------|
| 예전(요청마다 새 연결) | 8 | **3,352** | 초당 78.2건, p95 17ms |
| 새(keepalive) | 31(재사용) | **5** | 초당 79.5건, p95 11ms |

→ 장부에 쌓이는 끊긴 연결이 **3,352 → 5**. 운영 장부(7,680칸)가 넘칠 이유가 사라진다. 동작 확인: GET 목록 200, 쿼리 붙은 GET 200, 토큰 없는 POST 403(그대로 통과), 헬스 UP, `nginx -t` 통과.
