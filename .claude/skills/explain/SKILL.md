# 코드 흐름 설명

사용자는 개발 입문자다. 실제 코드를 읽고, 요청 하나가 서버 안에서 지나가는 길을 **자세하게, 사용자가 이해할 수 있게** 설명한다. 짧게 줄이지 않는다.

## 순서
1. 설명할 대상을 정한다. 인자가 없거나 애매하면 "어떤 기능(API)?"만 짧게 묻는다.
2. 관련 코드를 직접 읽는다: 컨트롤러 → 서비스 → 리포지토리/Redis, DTO 검증, config/SecurityConfig.java(필터·공개 경로). 기억이나 추측으로 설명하지 않는다.
3. 화면(Flutter 웹)이 관련 있으면 flutter_app/lib에서 그 API를 부르는 곳만 찾아 흐름 정도만 본다.
4. 아래 형식으로 답한다.
5. 다 설명한 뒤 "Notion에 저장할까?"를 묻는다. 예라고 하면 저장한다(아래 "Notion 저장").

## 답변 형식
1. **한 줄 비유**: 이 기능을 일상의 장면 하나로 (예: 로그인 = 매표소에서 팔찌·교환권 받기). 같은 대화 안에서는 같은 비유를 이어 쓴다.
2. **화면에서 시작 (흐름만)**: 사용자가 무엇을 누르면 → 화면이 어떤 요청(메서드·주소·보내는 값)을 보내고 → 응답을 받아 무엇을 하는지 2~4줄. 화면(Flutter) 코드 설명은 하지 않는다.
3. **공통 입구**: 컨트롤러 전에 지나는 길(nginx/Flutter 개발 서버 프록시 → CSRF 검사 → JWT 쿠키 검사 → 출입 규칙)을 이 요청 기준으로. 공개 경로인지, 각 검사에서 막히면 몇 번이 나는지 적는다.
4. **흐름 표**: `순서 | 어디서(클래스.메서드) | 하는 일` — 성공 경로를 위에서 아래로 빠짐없이. 실패하면 몇 번(400/401/403/404/409/500)이 어디서 나는지 그 줄에 적는다. DB·Redis에 무엇이 저장·조회·삭제되는지도 적는다.
5. **포인트별 풀이**: 표에서 어려운 줄마다 "왜 이렇게 했나"를 쉬운 말과 비유로 푼다 (예: 아이디 없음·비번 틀림을 구분 안 하는 이유, 확인했는데 DB 제약을 또 두는 이유). 필요한 코드 한두 줄을 인용하고 한 줄씩 해설한다.
6. **응답이 브라우저에 도착한 뒤**: 상태 코드, 본문, 쿠키가 어떻게 되는지.
7. **알아둘 한계**: 있으면 적는다. 없으면 생략.
8. **한눈에 정리**: 마지막에 짧은 표나 3줄 요약.
9. 이어서 물어볼 만한 것 하나를 제안하고, Notion 저장 여부를 묻는다.

## 규칙
- 한국어 반말. 쉬운 말 먼저, 용어는 처음 나올 때 괄호로 풀이한다. 용어만 늘어놓지 않는다.
- 파일은 [파일명](경로:줄) 링크로 건다.
- 질문한 기능만 설명한다. 관련 없는 기능으로 넓히지 않는다.
- 설명 중 버그나 이상한 점을 발견하면 고치지 말고 끝에 "발견한 점"으로 따로 알린다. 고칠지는 사용자가 정한다.
- 비밀 값(.env 값, 서버 IP, 계정 ID, DB 사용자명·비밀번호)은 쓰지 않는다.

## Notion 저장
- 사용자가 저장하자고 할 때만 저장한다.
- 위치: docs/notion-guide.md의 "학습 리뷰" 데이터베이스에서 그 기능이 속한 파트 카드(S1, S4 등) 안에 하위 페이지 "흐름 설명: <기능>"으로 만든다. 같은 제목이 있으면 새로 만들지 않고 고친다.
- 내용은 답변 그대로 옮기되 셸 명령어는 빼고, 이모지·색은 최소로 한다.
- 저장 후 페이지 링크를 알려준다.
